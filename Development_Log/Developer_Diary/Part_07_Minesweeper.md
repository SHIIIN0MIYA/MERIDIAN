# 第七部分：第一次处理隐藏信息——扫雷

---

## 记录 69｜这次不做追逐速度，而是做判断和风险

2048 完成以后，桌面上已经有鼠标回合制、键盘即时、连续碰撞和数字合并几种玩法。

下一款我决定做扫雷。

它的难点不在物体移动，而在隐藏信息。玩家点击前看不到地雷位置，只能根据已经翻开的数字推断；程序则必须同时保存真实棋盘、玩家已经看到的区域和玩家自己插下的旗子。

同一个格子因此有两种状态：内部到底是什么，以及界面现在允许玩家看见什么。只用一张二维列表已经不够。

我先把最小循环定成：

```text
左键翻开格子
右键插旗或取消旗子
数字表示周围地雷数量
空白区域自动展开
翻开全部安全格后胜利
点到地雷后失败
```

---

## 记录 70｜真实棋盘、翻开状态和旗子必须分开保存

扫雷使用三张同样大小的二维列表：

```python
mines_grid      # -1 表示地雷，0—8 表示邻近地雷数量
mines_revealed  # 这个位置是否已经翻开
mines_flags     # 这个位置是否插旗
```

如果把旗子直接写进真实棋盘，取消旗子时还要恢复格子原来的数字；如果把翻开状态和数字混在一起，也很难区分“数字为 0”和“尚未翻开”。

分开以后，每一层职责很清楚：

- `mines_grid` 只负责正确答案；
- `mines_revealed` 决定当前可以显示哪些答案；
- `mines_flags` 保存玩家的判断，不保证一定正确。

这点很重要。旗子只是玩家做的标记，不能因为插了旗就修改地雷的真实位置，也不能直接拿“旗子全对”作为胜利条件。

---

## 记录 71｜同一块 504 像素区域要容纳两种棋盘大小

设置页提供两种棋盘：`9×9` 和 `16×16`。

地雷数量随棋盘大小提供不同选项：

```text
9×9     10 / 15 / 20 枚地雷
16×16   40 / 50 / 60 枚地雷
```

两种棋盘都放进同一个 504 像素区域，不能分别写死格子尺寸。格子大小根据棋盘边长和间隔重新计算：

```python
gap = 4 if board_size <= 9 else 2
cell_size = (504 - gap * (board_size + 1)) // board_size
```

9×9 使用 4 像素间隔，让大格子之间保持清楚分隔；16×16 改成 2 像素，避免间隔占掉太多空间。

更换棋盘大小时，地雷数量自动回到该尺寸的第一个有效选项。否则从 `16×16 / 60` 切回 `9×9` 后，设置页可能保留一个不属于 9×9 的雷数。

设置变化只影响下一张新棋盘，不在一局已经开始后修改现有地雷布局。

## 记录 72｜棋盘不能在进入游戏时就生成，否则第一下可能直接失败

第一版进入对局时就随机放置地雷。测试时出现过刚开始第一下就点中地雷的情况。

规则上这不算程序错误，但体验很差。玩家还没有获得任何信息，也没有做出一次判断，整局就结束了。

我把地雷生成推迟到第一次真正翻开格子时。第一次点击的格子以及周围一圈 `3×3` 区域都从候选地雷位置中排除：

```python
positions = [
    (row, column)
    for row in range(board_size)
    for column in range(board_size)
    if not (
        abs(row - first_row) <= 1
        and abs(column - first_column) <= 1
    )
]
```

然后打乱候选位置，从中取出设定数量放置地雷。

这样第一格不仅不会是地雷，它周围也不会紧贴地雷，通常可以展开一小块安全区域。计时器也从这次点击才开始，而不是玩家刚进入对局页面就开始计时。

## 记录 73｜放完地雷以后，再统一计算 0—8

真实棋盘先全部设为 0，地雷位置写成 `-1`。所有地雷放完以后，再遍历每个非雷格子，统计周围八个方向有多少个 `-1`。

```python
count = 0

for dr in (-1, 0, 1):
    for dc in (-1, 0, 1):
        if dr == 0 and dc == 0:
            continue

        near_row = row + dr
        near_column = column + dc

        if inside_board(near_row, near_column):
            if grid[near_row][near_column] == -1:
                count += 1
```

边缘格和角落格不能直接访问完整八邻域，所以每次都先检查新坐标是否仍在棋盘内。

我没有在玩家点击时临时计算数字。棋盘生成后一次性写好所有邻雷数量，后续翻开和连锁展开只读取结果，规则更容易验证。

## 记录 74｜点击格子间隙时，不能自动算到旁边一格

有间隔的棋盘不能简单用鼠标位置除以格子宽度。间隔本身并不属于任何格子，如果直接整除，玩家点在两格中间的空隙，也可能被换算成旁边某个坐标。

第一次测试时，这种误判在 16×16 棋盘上尤其明显。格子更小，玩家本来只是移动鼠标，稍微偏一点就可能翻开不想点的位置。

最后的处理方式是先确认鼠标位于整个棋盘区域，再遍历每个格子的实际矩形，只在某个矩形真正包含点击位置时返回行列：

```python
for row in range(board_size):
    for column in range(board_size):
        if get_cell_rect(row, column).collidepoint(mouse_pos):
            return row, column

return None, None
```

这样格子之间的 2 或 4 像素间隔就成为真正的无效区域，悬停高亮和点击命中也使用同一组矩形。

## 记录 75｜空白区域展开不能递归到失去控制

翻开数值为 0 的格子时，需要继续翻开周围格子；如果周围又有 0，就继续向外扩散，直到遇到带数字的边界。

最直接的方法是递归调用翻开函数。但大块空白区域可能产生很深的调用链，而且同一个位置会从不同邻居被重复加入。

我改用显式栈：

```python
stack = [(start_row, start_column)]

while stack:
    row, column = stack.pop()

    if outside_board(row, column):
        continue
    if revealed[row][column] or flags[row][column]:
        continue

    revealed[row][column] = True

    if grid[row][column] == 0:
        push_all_neighbors(stack, row, column)
```

已经翻开的格子和插旗格都会被跳过。数字格会被翻开，但不会继续向外扩散。

显式栈让展开过程仍然是一条普通循环，也能在每个实际翻开的格子上分别增加计数和创建动画。

## 记录 76｜插旗不是判定答案，胜利只看安全格是否全部翻开

右键点击未翻开的格子时切换旗子状态。插旗后，左键翻开会直接忽略这个位置，防止玩家误触自己已经标记的地雷。

再次右键则取消旗子。旗子计数单独维护，右侧面板同时显示：

```text
MINES   预计还剩多少枚未标记地雷
FLAGS   当前已经插下多少面旗
```

`MINES` 使用“总雷数减去旗子数”显示，但最低只到 0，避免玩家插入过多旗子后出现负数。

胜利条件不检查旗子是否全部正确，而是检查翻开的安全格数量：

```python
revealed_count >= board_size * board_size - mines_count
```

玩家可以在不插任何旗子的情况下翻开所有安全格并获胜；也可以插错旗导致剩余安全格一直无法翻开。旗子服务于推理，不是程序替玩家提交的答案。

---

## 记录 77｜加入双击展开以后，错误旗子也必须承担后果

格子越来越多以后，已经确认周围地雷的数字格需要逐个点击剩余邻居，操作比较重复。

我加入了双击展开：在 320 毫秒内连续左击同一个已经翻开的数字格，程序检查周围旗子数量。如果旗子数正好等于数字，就自动翻开其余未插旗的邻居。

```python
same_cell = last_click_cell == current_cell
is_double = same_cell and now - last_click_time <= 320
```

如果周围旗子数量与数字不相等，不执行展开，只让棋盘轻震 8 帧，提示条件还没有满足。

如果旗子数量相等但位置插错，自动展开仍可能翻到真正的地雷。这是玩家推理错误产生的结果，程序不能因为数量正确就偷偷修正旗子位置。

双击功能减少的是重复操作，不替代扫雷本身的判断。

## 记录 78｜计时从第一步开始，最佳成绩必须按模式分开

玩家进入对局后可能先观察设置或停留一会儿，所以计时不能从页面出现时开始。它与延迟生成棋盘使用同一个起点：第一次翻开格子时记录当前时间。

之后每帧更新：

```python
elapsed_ms = pygame.time.get_ticks() - start_ticks
```

显示时把毫秒转换为 `MM:SS`。胜利后停止更新，并比较当前模式的最好时间。

不同棋盘大小和雷数不能共用一个 `BEST`。`9×9 / 10` 与 `16×16 / 60` 的难度和完成时间差异太大，所以最好时间使用 `(board_size, mines_count)` 作为键分别记录。

当前最好时间只在本次运行中保留，重新开始同一模式时仍能看到；切换模式后，状态栏显示对应模式自己的记录，没有成绩时显示 `--:--`。

## 记录 79｜高雷量模式卡住时，我增加了一个只给线索的 HINT

在雷数较高的模式中试玩时，有时会长时间停在一个无法确定下一步的位置。直接替玩家翻开安全格会破坏推理，我也不想让提示按钮自动完成整片区域。

最后的提示只指出一枚尚未插旗的真实地雷。

程序从最后翻开的格子出发，在所有未标记、未翻开的地雷中选择曼哈顿距离最近的一枚，用闪烁边框和问号标记 90 帧，并产生 18 个亮色粒子。

提示不会自动插旗，也不会改变棋盘答案。玩家仍然要自己判断是否相信提示并右键标记。

在第一步还没有生成棋盘时，`HINT` 不能使用；死亡演出和结果状态中也不能使用。连续点击则受到 30 帧冷却限制，冷却期间只给出短震动，不重复叠加提示。

这个按钮解决的是完全停滞，不是把每一步推理都交给程序。

## 记录 80｜翻格和插旗需要两种不同的反馈

第一版格子状态瞬间切换。翻开一大片空白时，几十个格子同一帧从深色变亮，玩家很难看清展开从哪里开始；插旗时也只是多出一面小旗，点击感很弱。

我分别记录翻开动画和旗子动画：

- 翻开格子用 10 帧回弹，从较小比例放大到正常尺寸；
- 插旗或取消旗子用 10 帧轻微鼓起再恢复；
- 插下一面旗时额外生成 8 个红色像素粒子。

每个格子的动画用行列作为标识。绘制时先建立 `(row, column) → animation` 的查找表，再决定当前格子的缩放比例，避免每画一格都遍历完整动画列表。

数字颜色也按风险程度区分：较小数字使用亮青色，较大数字改用更醒目的红色。9×9 的数字可以使用较大缩放，16×16 则缩小，避免文字挤出格子。

## 记录 81｜点到地雷后，我不想让结果页立即盖住原因

最初点到地雷就直接显示 `BOOM` 结果面板，和五子棋早期立即跳结束页的问题很像：程序知道发生了什么，玩家却还没来得及看清自己点中了哪一格。

我把死亡拆成四个连续阶段，并在演出期间停止处理棋盘输入：

```text
FLASH    70 帧：地雷交替闪烁，震动逐渐增强
EXPLODE  95 帧：主爆炸、冲击环、余烬和持续火花
REVEAL   45 帧：翻出所有地雷，让玩家看到完整布局
FADE     38 帧：画面压暗并显示 BOOM...
```

主爆炸生成 140 个爆炸粒子和额外的高速亮点；第 22 帧加入 72 个环形粒子，第 48 帧加入 90 个向上飘散的余烬。震动在爆炸开始时最强，随后逐渐衰减。

只有四个阶段结束后，状态才进入正式结果页。这样失败不是一张突然出现的弹窗，而是先明确指出触发位置，再展示其他地雷，最后收住整局。

胜利不播放爆炸流程，直接记录时间并使用 22 帧回弹结果面板显示 `YOU WIN`。

## 记录 82｜扫雷替换新的预留栏，并完成整条鼠标交互测试

扫雷稳定后，我给桌面增加 `MINES` 图标。图标内部画一块缩小的格子区域，部分格子处于翻开状态，其中一格插着红旗。

点击图标先进入扫雷开始页。开始页可以进入设置、开始新局或返回桌面；结束页则显示用时、翻开格数，以及再来一局、返回菜单和返回桌面。

接入测试不只检查输赢，还覆盖了容易出错的交互边界：

- 第一次翻开的位置及周围 3×3 区域不会生成地雷；
- 9×9 与 16×16 的格子和间隔都能正确命中；
- 点击格子间隙不会误开相邻位置；
- 空白区域会持续展开到数字边界，不会翻开旗子；
- 已翻开的格子不能再插旗，插旗格不能被普通左键打开；
- 双击只在同一格、320 毫秒内成立，旗子数量不符时不展开；
- 插错旗后使用双击仍可能踩雷，不会被程序自动纠正；
- 计时从第一次翻格开始，不同模式使用各自的最佳时间；
- 死亡演出期间鼠标输入不会继续修改棋盘；
- 返回桌面后计时和棋盘输入停止，再次进入先回到扫雷菜单。

这款游戏让我第一次完整处理“真实数据”和“玩家可见数据”之间的差别。桌面上又少了一个 `COMING SOON`，但这次增加的不只是一个图标，还多了一套延迟生成、区域展开、双键操作和分阶段失败反馈。
