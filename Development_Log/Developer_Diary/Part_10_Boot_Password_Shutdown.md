# 第十部分：我给掌机补上开机、解锁和关机

---

## 记录 106｜桌面已经像掌机了，但打开和离开的方式仍然像普通程序

停止增加新游戏以后，我重新从头走了一遍完整使用过程。

当时最明显的割裂并不在某一款游戏内部，而是在整段体验的两端：程序一启动，掌机桌面几乎立刻出现在眼前；想离开时，又像关闭普通窗口一样直接结束。

桌面上已经有外壳、屏幕、时间、电量和软件图标，玩家看到的是一台设备；但程序的开始和结束都没有设备应有的过程。结果就是，掌机只在桌面这一张画面里成立。一旦把“打开程序”和“关闭程序”也算进体验，它仍然只是一个装着几款小游戏的窗口。

我先没有继续修改任何单款游戏，而是把目标改成补齐一条最外层的使用路径：

```text
启动程序
   ↓
开机
   ↓
等待系统就绪
   ↓
输入密码
   ↓
进入桌面
   ↓
选择是否关机
   ↓
完成关机后退出程序
```

这里的重点不是多增加几张页面，而是让玩家第一次看见桌面以前、最后一次离开桌面以后，都仍然感觉自己在操作同一台掌机。

---

## 记录 107｜我先把最外层流程改成互相排斥的状态

原来的主循环主要围绕桌面和各款游戏工作。如果只在程序最前面播放一段动画，动画结束后再沿用原来的逻辑，开机期间仍可能接收到桌面输入，隐藏在后面的游戏状态也可能继续更新。

我没有把开机、密码和关机当成盖在桌面上的三层图片，而是把它们加入最外层状态：

```python
BOOT = "boot"
SYSTEM_READY = "system_ready"
PASSWORD = "password"
DESKTOP = "desktop"
SHUTDOWN = "shutdown"

state = BOOT
```

每一帧先根据 `state` 决定当前可以接收什么输入、更新哪些计时器、绘制哪一张画面。处于开机状态时只推进开机阶段；处于密码状态时只处理数字输入；进入关机状态以后则停止桌面交互，只推进关机动画。

这样做以后，流程才真正具备顺序约束：没有完成开机就不能直接操作桌面，没有通过密码就不能打开游戏，一旦开始关机也不能再点后面的图标。

第一次完整接入时，我重点检查的不是画面是否好看，而是这些状态会不会串在一起。只要开机画面仍能误触桌面，或者关机时游戏仍在运行，这套系统就只是视觉遮罩，不是真正的掌机流程。

## 记录 108｜开机的第一步不是显示文字，而是让屏幕真正亮起来

如果程序启动后立刻显示完整欢迎语，即使前面多了一张页面，感觉仍然像普通的标题页。我希望玩家看到的是一块刚刚通电的屏幕，而不是已经准备好的菜单。

开机最初进入 `fade` 阶段。画面从全黑开始，在 42 帧内逐渐显露屏幕边框、深色底面和少量闪烁像素点。按 60 帧运行时，这段淡入大约持续 0.7 秒。

我没有把整个掌机桌面直接放在黑幕后面，因为那样淡入完成的一刻就已经能看见软件图标。开机页使用独立的屏幕框架，保留与桌面相同的深色和金色描边，但内部只显示启动信息需要的内容。

测试时我发现，淡入太快会像窗口刷新，太慢又会让第一秒只有黑屏，容易被误认为程序没有响应。42 帧最后成为一个折中：能看见屏幕逐渐点亮，又不会让玩家在什么都看不到的情况下等待太久。

这一步解决的是一个很小但很关键的感受——不是“页面出现了”，而是“设备醒了”。

---

## 记录 109｜欢迎语改成逐字出现以后，我又处理了打字节奏

屏幕亮起后，我显示的欢迎语是：

```text
WELCOME TO HAO'S GAME DECK
```

最直接的实现是每隔固定帧数增加一个可见字符。这样功能没有问题，但完整句子以完全相同的间隔打印时很像机械计数，单词之间没有停顿，`HAO'S` 中的撇号也会和普通字母一样匀速掠过。

我把当前显示长度单独保存下来：

```python
shown_text = boot_text[:visible_chars]
```

每次计时归零只增加一个字符，再根据刚刚出现的内容决定下一个等待时间。普通字符大约等待 5 到 9 帧，空格等待 10 到 16 帧，撇号等待 8 到 12 帧；在 `WELCOME`、`WELCOME TO` 和 `WELCOME TO HAO'S` 这些词组结束的位置，再加入 22 到 34 帧的停顿。

延迟不是完全固定值，而是在范围内变化。这样同一句话仍然可以稳定完成，却不会像进度条一样匀速增长。文字右侧还保留一个闪烁光标，让玩家知道系统仍在工作。

这次调整以后，开机不再只是把标题拆成很多帧显示。词与词之间开始有呼吸，掌机名称也获得了比普通字符更明确的出现时刻。

## 记录 110｜进度条不是按真实资源计算的，我把它当作开机演出的一部分

欢迎语打印完成后，我没有立刻跳到密码页。文字先停留 22 帧，然后进入 `STARTING SYSTEM...` 的加载阶段。

这时程序中的几款游戏并没有真的需要十秒才能载入，所以进度条不能假装自己在精确反映文件加载量。它本质上是掌机的开机演出，用来把“出现欢迎语”和“系统可以操作”连接起来。

我仍然不想让百分比从 0 到 100 匀速爬完。匀速进度非常容易看出是计时器，也没有系统启动时逐项检查的感觉。最后我把 600 帧拆成几段：

```text
0 ～ 90 帧      0%  → 12%
91 ～ 150 帧    停在 12%
151 ～ 300 帧   12% → 41%
301 ～ 345 帧   停在 41%
346 ～ 480 帧   41% → 73%
481 ～ 525 帧   停在 73%
526 ～ 600 帧   73% → 100%
```

三次短暂停顿让进度不再像一条匀速动画，但每个停顿都有明确上限，不会真的卡死。填充宽度始终由 `boot_progress_value` 计算，百分比文字和进度条读取同一个值，避免画面显示 41% 时条形长度却已经过半。

测试这一段时，我专门等到每个停顿位置，确认数字会继续前进，也确认到达 100% 后只切换一次状态。因为对玩家来说，模拟加载最危险的问题不是慢，而是看起来像程序真的卡住了。

## 记录 111｜加载完成后没有直接进入密码页，而是先交还一次控制权

进度达到 100% 后，如果画面自动切到密码输入，整段开机依然只是一段必须被动看完的动画。玩家直到数字键盘出现才第一次参与其中，前面的十几秒与自己没有任何关系。

我在开机和密码之间加入了 `SYSTEM READY` 状态。页面中央显示系统已经准备完成，并提供 `ENTER SYSTEM` 按钮；玩家可以按回车、空格，或者用鼠标点击继续。

这张页面的内容很少：中心标记、缓慢明暗变化的方框、`SYSTEM READY` 和继续按钮。它不承担新的功能，只负责把流程从自动播放交回给玩家。

```text
自动阶段：屏幕淡入 → 欢迎语 → 加载
                              ↓
主动阶段：              ENTER SYSTEM
                              ↓
                           密码页
```

试玩时，这个停顿点比我预想得重要。没有它时，开机和密码像两段自动拼接的动画；加入确认以后，玩家会先看到“系统已经准备好”，再主动决定进入。掌机第一次不只是展示自己，而是在等待操作。

---

## 记录 112｜密码系统的目的不是安全，而是建立“解锁自己的设备”的仪式

我加入密码页时，并没有把它设计成真正的账户验证。密码直接保存在本地程序里，也没有用户注册、加密或找回流程。它要解决的是体验问题，而不是数据安全问题。

开机结束后直接进入桌面，只能说明程序加载完了；多一次解锁动作，玩家才会产生“这台设备现在归我使用”的感觉。

我把密码长度限制为四位，目标数字固定为：

```python
password_target = ["0", "4", "2", "5"]
password_max_length = 4
```

四位数字足够形成一次明确输入，又不会让每次启动都变成长密码练习。页面上方放四个独立数字槽，输入一位就填入一格。这里没有用圆点遮住数字，因为它不是防止旁观者看到密码的登录界面；让玩家清楚看见自己输入了哪一位，比模拟安全系统更重要。

我也因此没有给它添加用户名、账户列表或复杂权限。这一阶段需要的是一扇有反馈的门，而不是一套与小游戏合集无关的用户系统。

## 记录 113｜数字键盘同时支持鼠标和实体键盘，但只使用一套输入结果

密码页中央使用常见的三列布局：

```text
1  2  3
4  5  6
7  8  9
   0
```

鼠标按下数字按钮时，按钮向下移动几像素；直接按键盘数字时，则把相同数字写入同一个 `password_input` 列表。两种输入方式最后都经过相同的长度检查和密码判断，没有分别维护“鼠标密码”和“键盘密码”。

最初我考虑过再放一个 `ENTER` 按钮，但四位长度已经固定，继续要求一次确认只会增加操作。最后的规则是：输入达到四位后自动校验。

```python
if len(password_input) >= 4:
    if password_input == password_target:
        state = DESKTOP
    else:
        show_password_error()
```

测试时我交替使用鼠标和键盘，例如先点击 `0`、再按键盘 `4`、最后点击 `2` 和 `5`。只要最终列表一致，就应该得到相同结果。这样密码页不会因为玩家临时换了一种输入方式而失去前面的内容。

## 记录 114｜自动提交带来了一个很实际的问题：输错第四位以前必须能够修改

四位自动提交让正确输入很快，但也放大了输错的问题。如果前三位中有一位点错，而页面只有数字键，玩家只能故意补满四位，等待错误动画结束后再全部重输。

功能上这样仍然能回到正确流程，实际使用却很别扭。玩家明明已经发现错误，系统却要求他继续制造一次失败。

我给数字区补上 `DEL`，键盘端同时接受退格键和删除键。只要当前没有处于错误反馈阶段，就移除最后一位：

```python
if pressed_backspace and password_input:
    password_input.pop()
```

删除按钮没有做成与普通数字完全相同的样式。它放在数字 `0` 的右侧，使用偏红的边框和退格箭头，避免玩家把它误认为另一枚数字键。

这次改动没有改变密码规则，却修复了自动提交方案留下的操作死角。自动判断仍然节省一次确认；在达到四位以前，玩家也能够主动纠正输入。

## 记录 115｜密码错误不能只是清空数字，否则玩家不知道刚才发生了什么

最简单的错误处理是发现四位数字不匹配后立刻清空列表。第一次测试时，这种结果很像输入丢失：数字刚填满就突然消失，玩家无法判断是程序没有收到输入，还是密码真的错误。

我把错误反馈拆成三件同时发生的事：

- 四个数字槽左右抖动；
- 边框变成红色，并每 6 帧切换一次明暗；
- 页面显示 `PASSWORD INCORRECT`。

错误状态持续 30 帧。在这段时间内，新的数字输入会被忽略，防止玩家还没看清提示就把下一次密码输进正在抖动的页面。30 帧结束后解除错误状态，输入重新从第一位开始。

```text
输入四位错误密码
   ↓
清空本次输入
   ↓
红色闪烁 + 横向抖动 + 错误文字
   ↓
30 帧后恢复输入
```

这里我刻意把“规则拒绝”和“画面反馈”绑定到同一个 `password_error` 状态。只画红色文字但仍允许继续输入，会让新数字落在旧的错误演出里；只禁止输入却不显示原因，又会像键盘失灵。

## 记录 116｜正确密码进入桌面，密码页本身也必须被完整清理

输入 `0、4、2、5` 后，程序把外层状态切换到桌面。这个过程看起来只有一次页面变化，但测试时还需要检查密码页留下的临时值。

我先后验证了几种情况：

- 一次输入正确，能够进入桌面；
- 先输入错误密码，等反馈结束后再输入正确密码，仍能进入；
- 输入两位后删除，再补成正确四位，不会把被删除的数字留在列表里；
- 鼠标按下数字后把指针移开再松开，按钮不会一直保持按下外观；
- 密码错误期间连续敲数字，错误结束后不会突然一次性出现。

密码页还保留了 `ESC: Shutdown`。如果玩家开机后不想继续，不需要先输入密码进入桌面才能退出。此时没有正在进行的游戏，所以按下 `ESC` 可以直接进入关机过程；真正需要二次确认的是已经进入桌面以后。

这条支路避免密码页变成只能前进、不能退出的死路。

## 记录 117｜桌面上的 ESC 不能再直接结束程序，我先加入关机确认

进入桌面后，`ESC` 原本最容易被理解成退出程序。如果它立即关闭窗口，掌机仍然没有一个可见的关机动作，而且玩家从游戏返回桌面后很可能顺手多按一次，直接把整个程序关掉。

我把桌面上的 `ESC` 改为打开确认面板：

```text
POWER OFF?
UNSAVED PROGRESS MAY BE LOST

[ MISCLICKED~ ]    [ SHUT DOWN ]
```

左侧的 `MISCLICKED~` 不是普通的 `CANCEL`。我希望它延续掌机原本略带玩笑的语气，同时明确告诉玩家：如果刚才是误触，可以安全回去。右侧才真正开始关机。

确认面板出现后，桌面图标和翻页按钮全部停止接收输入。事件处理先检查关机面板，只处理取消、确认和 `ESC` 关闭面板，然后直接结束本次事件。否则玩家在点击确认按钮的同时，还有可能点到遮罩后面的游戏图标。

这一步让关机不只是多了一个弹窗，也建立了输入优先级：只要模态面板存在，背景桌面就不再是当前可操作页面。

## 记录 118｜关机按钮使用“按下和松开必须是同一项”的规则

确认面板有两个相邻按钮。如果只在鼠标按下时判断位置，手指刚压到 `SHUT DOWN`，程序就会立即关机，玩家没有撤回动作的机会。

我继续沿用其他按钮已经验证过的按压逻辑：鼠标按下时只记录动作，鼠标松开时再检查指针是否仍在同一按钮内。

```python
mouse_down:
    pressed_action = hovered_action

mouse_up:
    if hovered_action == pressed_action:
        run_action(pressed_action)
    pressed_action = None
```

这样玩家在关机按钮上按下后，如果意识到点错，可以把鼠标移出按钮再松开，关机不会发生。按下时按钮向下偏移，悬停时边框和阴影变化，视觉状态与真正记录的 `pressed_action` 保持一致。

测试时我还从一个按钮按下、拖到另一个按钮再松开。最终两边都不应执行，因为“按下的关机”不能被“松开时碰巧位于取消”替换，反过来也一样。

## 记录 119｜从游戏返回桌面时，同一次 ESC 会继续触发关机确认

接入关机面板后出现了一个很隐蔽的问题：玩家在游戏页面按 `ESC` 返回桌面，桌面刚出现，关机确认也跟着弹出来。

单独测试桌面时无法复现，因为问题来自两个层级对同一个按键的理解：

```text
游戏收到 ESC      → 返回桌面
桌面紧接着收到 ESC → 打开关机确认
```

从玩家角度看，他只按了一次返回，却像连续执行了“离开游戏”和“关闭掌机”两个动作。确认面板虽然挡住了真正退出，但仍会让每次返回都多一步取消。

我没有彻底禁用桌面的 `ESC`，而是在回到桌面时设置一个 15 帧的输入保护：

```python
desktop_esc_lock_frames = 15

if key == ESC and desktop_esc_lock_frames <= 0:
    shutdown_confirm_open = True
```

每帧把保护值减一。刚返回桌面的短时间内只忽略 `ESC` 的关机含义，图标和桌面本身仍然正常显示；保护结束后，再按一次 `ESC` 就能正常打开确认。

这个问题让我确认，返回键不能只在每张页面里分别测试。只要一个按键跨越了页面边界，就必须检查它会不会被新页面再次解释。

## 记录 120｜真正关机后，我让告别文字像被系统逐字收回

点击 `SHUT DOWN` 后，我没有立刻把画面淡黑。桌面先被半透明暗层压住，中间显示一条告别文字：

```text
BYE BYE SEE U NEXT TIME~
```

文字完整停留 45 帧，然后从最后一个字符开始删除。每经过 4 帧减少一个可见字符，右侧保留闪烁光标。全部删除后，再用 60 帧把整张画面逐渐压到黑色，最后才结束主循环。

```python
if shutdown_phase == "show":
    wait(45)
elif shutdown_phase == "deleting":
    visible_chars -= 1       # 每 4 帧一次
elif shutdown_phase == "fade":
    fade_to_black(60)
```

开机时文字从无到有，关机时则从完整句子逐字消失。两段动画没有使用完全相同的方向，却形成了明确的首尾关系：开机像系统开始说话，关机像系统收回最后一句话。

进入关机状态时，我还会清除桌面按钮的按下记录、普通按钮的按下记录，并关闭确认面板。否则关机画面绘制桌面背景时，后面的某个按钮可能一直保持按下样式，看起来像关机仍没有真正接管系统。

## 记录 121｜点击窗口关闭按钮也要进入同一条关机路径

只处理桌面里的 `SHUT DOWN` 还不够。实际使用时，很多人会直接点击窗口右上角的关闭按钮。如果系统事件一到就把 `running` 设为 `False`，精心做好的关机过程只会在特定入口出现，最常见的退出方式反而继续瞬间消失。

我把窗口关闭事件也改为调用同一个关机入口。只要当前还没有处于 `SHUTDOWN`，关闭窗口就先进入关机状态；如果已经在关机，就不重复初始化计时器。

```python
if event.type == QUIT and state != SHUTDOWN:
    start_shutdown()
```

这个统一入口还解决了另一类重复问题：不管从密码页按 `ESC`、从桌面确认关机，还是点击窗口关闭，最终都使用相同的文字停留、逐字删除和淡出计时，不需要维护三套相似动画。

我分别从密码页和桌面测试窗口关闭，并在关机动画进行到一半时再次点击关闭。预期结果不是立即跳出，也不是动画从头播放，而是继续完成当前关机过程。

## 记录 122｜最后一次测试不再从桌面开始，而是从程序启动一直走到完全退出

这一阶段的最终测试路径变成了：

```text
启动程序
   ↓
确认黑屏淡入、欢迎语节奏和加载停顿
   ↓
在 SYSTEM READY 主动继续
   ↓
输入一次错误密码
   ↓
等待错误反馈结束并修正输入
   ↓
输入 0425 进入桌面
   ↓
打开游戏并返回桌面
   ↓
确认返回用的 ESC 不会连带打开关机面板
   ↓
再次按 ESC，先取消关机
   ↓
重新打开确认并选择 SHUT DOWN
   ↓
等待告别文字删除、画面淡黑、程序退出
```

我还补测了鼠标与键盘混合输入、错误状态期间连续按键、关机面板遮住桌面后的误点，以及窗口关闭按钮是否走同一条路径。

这些功能都完成以后，单款游戏的规则没有变化，桌面上也没有增加新的图标。但整台掌机第一次拥有了完整的开头、进入条件和结尾。

在这之前，`HAO'S GAME DECK` 更像一个画成掌机样子的小游戏集合；完成这一段以后，玩家从程序启动的第一帧开始就在“开机”，直到最后一帧才真正“关机”。这正是我停止继续堆游戏后，最先补上的那部分完整感。
