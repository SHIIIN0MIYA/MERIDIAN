# 第十六部分：设置和存档稳定以后，我开始让长期游玩留下阶段性结果

---

## 记录 221｜最佳分数只能告诉玩家“最高到哪里”，不能告诉他曾经怎样玩过

设置中心建立本地保存以后，部分成绩已经能够跨启动保留：贪吃蛇最高分、2048 最高分、扫雷最佳时间、俄罗斯方块最高等级和空袭行动关卡进度。

但这些数字主要用于比较结果，不会主动指出某一次有意义的经历。

例如五子棋分别用黑棋和白棋获胜、打砖块在困难难度无损过关、俄罗斯方块一次消除四行、空袭行动把三条武器路线升满，都不是一个总分能够完整表达的事情。

我希望长期游玩不再只是几个越来越大的数字，而是能在达到某个明确条件时得到一次阶段性确认。

因此我开始开发成就系统。它不改变游戏规则，也不直接给玩家额外能力，只负责观察已经发生的玩法事件，在条件满足时记录一次永久结果并给出通知。

---

## 记录 222｜成就条件不能直接散落在每款游戏里，否则数量增加后无法统一检查

最直接的写法是在贪吃蛇吃到第五个食物时直接写：

```python
unlock("SMALL BITE")
```

这种方式能工作，但每款游戏会自己判断是否已经解锁、怎样保存、怎样播放通知。修改阈值时还要进入具体玩法代码。

我把系统拆成两层：

```text
游戏层
  只记录事实：开始一局、完成一局、吃到食物、消除行、达到最高分……

成就层
  读取统计，根据数据定义判断条件，负责一次性解锁和通知
```

游戏不需要知道“吃一百个食物”对应哪个标题，只调用：

```python
record_stat("snake", "food_eaten")
```

条件表再决定这个累计值达到多少时产生结果。

这样统计数据既能服务成就，也保留为对开发过程有用的真实游玩记录；成就定义则可以独立增加或调整。

---

## 记录 223｜建立统计结构时，我先区分累计值、单局最高值和布尔条件

不同成就需要的数据语义并不相同。

```text
累计值
  总食物、总砖块、总合并、总消行、完成局数

最高值
  单局最高分、最高方块、最高等级、单局最多消行

条件状态
  黑白双方是否都赢过、某个扫雷模式是否完成、所有关卡是否达到指定评级
```

如果把所有数字都当作加法，贪吃蛇两局各得 5 分会被记录为最高分 10；如果全部使用最大值，总食物每局只会保留较大的一次，永远无法累计到一百。

我给统计入口增加 `mode`：

```python
record_stat(game, key, amount=1, mode="add")
record_stat(game, key, value, mode="max")
```

`add` 负责累计，`max` 只在新值更高时替换。条件型数据则由成就进度计算器根据多项统计组合得到。

## 记录 224｜先记录事实，再检查条件；顺序反过来会让成就晚一次触发

成就判断必须发生在统计更新之后。

```python
target[key] = target.get(key, 0) + amount
check_achievements()
```

如果先检查再把贪吃蛇最高分从 4 更新到 5，五分成就不会在本次出现，只能等下一次任意统计变化重新检查。玩家已经完成目标，通知却延迟到一个无关动作之后。

我让所有 `_record_stat()` 调用在数据写入后统一执行检查。游戏层不再分别决定什么时候刷新成就。

全局开始局数和完成局数也在这里同步更新，但不会替代各游戏自己的统计。这样以后既能知道整台掌机进行了多少局，也能准确区分是哪款游戏贡献了数据。

## 记录 225｜每款游戏都要补齐关键事件，但不能为了统计改变原有规则

我逐款检查成就条件真正需要哪些事实：

```text
五子棋
  开始、完成、黑胜、白胜、和棋、撤销、19 路获胜

贪吃蛇
  开始、完成、食物总数、死亡、最高分、快速模式最高分

打砖块
  击碎砖块、丢失生命、通过关卡、最高关卡、困难通关、无损通关

2048
  有效移动、合并次数、最高方块、最高分、达到目标数字

扫雷
  翻开格子、插旗、胜利、失败、不同棋盘模式胜利

俄罗斯方块
  锁定方块、消除总行数、单次四行、单局行数、最高等级、最高分

空袭行动
  击毁敌机、Boss、武器等级、导弹击破数、评级、关卡与流程完成
```

这些记录点放在规则结果已经确定的位置。例如砖块确实从存活变为破坏后才增加计数，2048 只有发生有效移动才记录，扫雷胜利只在安全格全部翻开后统计。

统计不能反过来驱动规则，否则关闭或修改成就系统可能改变游戏结果。

## 记录 226｜成就定义使用数据表，不为每一项单独写判断函数

初版成就使用统一六元组：

```python
(
    achievement_id,
    title,
    description,
    game_id,
    statistic_key,
    target,
)
```

例如：

```python
(
    "snake_20",
    "LONG TRAIL",
    "Reach 20 points in Snake",
    "snake",
    "best_score",
    20,
)
```

`achievement_id` 是稳定存档键，标题和说明负责显示，后三项用于计算进度。

不能把标题直接作为存档键。以后修改显示文字或切换语言时，已经解锁的记录会因为标题改变被当成新成就；稳定 ID 与显示内容分开以后，文案可以调整，存档身份保持不变。

我先检查所有 ID 是否唯一。只要两个定义误用相同 ID，解锁其中一个就会让另一个永远无法单独记录，即使标题完全不同。

## 记录 228｜五子棋的六项不只奖励胜场，还记录双方与棋盘规模

五子棋成就包括：

```text
FIRST STONES   完成第一局
FIVE IN LINE   获得第一次胜利
TWO COLORS     黑棋和白棋都至少获胜一次
GRAND BOARD    在 19×19 棋盘获胜
STONE MASTER   累计获胜 10 局
OLD RIVALS     完成 50 局
```

这里只记录总胜场会漏掉 `TWO COLORS`。我没有额外维护一个 `both_sides` 数字，而是读取黑胜与白胜：

```python
value = int(black_wins > 0 and white_wins > 0)
```

`GRAND BOARD` 只在结算时检查本局棋盘大小为 19 且确实存在赢家，和棋不会算入。

这样六项分别鼓励完成一局、获胜、交换先后手、尝试大棋盘和长期对弈，不是同一个“多赢几局”目标重复六次。

## 记录 229｜贪吃蛇同时保留分数阶梯、快速模式和累计食物

贪吃蛇成就包括：

```text
SMALL BITE       单局达到 5 分
HUNGRY           单局达到 10 分
LONG TRAIL       单局达到 20 分
GREEN LIGHTNING  快速模式达到 30 分
FULL PANTRY      累计吃到 100 个食物
ENDLESS COIL     单局达到 40 分
```

5、10、20、40 形成清晰分数阶梯，使用 `best_score` 的最大值，不会因为多局累计错误解锁。

`GREEN LIGHTNING` 只在当前速度为 `fast` 时更新 `best_fast_score`；玩家在普通速度达到 30 不会触发。

`FULL PANTRY` 则使用 `food_eaten` 累加。它给没有追求单局高分、但长期反复游玩的玩家另一条进度。

## 记录 230｜打砖块的条件要区分“打得久”和“这一关打得干净”

打砖块成就包括：

```text
CLEAR SKIES    通过第一关
THIRD FLOOR    到达第 3 关
FOUR DIGITS    单局达到 1000 分
HARD HITTER    困难难度通过一关
UNTOUCHABLE    一条生命都没丢地通过一关
DEMOLITION     累计击碎 500 块砖
```

`UNTOUCHABLE` 需要知道本关开始后是否丢失过生命。如果只检查通关瞬间剩余生命大于零，丢过一次以后仍可能被错误判定为无损。

我在关卡开始时保存入口生命，通关时比较是否发生过损失。困难通关则读取当前难度，普通模式刷再多关也不会替代。

累计砖块和最高关卡继续分别使用 `add` 与 `max`，避免统计语义混淆。

## 记录 231｜2048 的成就围绕“最高方块”和长期合并，而不是只看结束分数

2048 成就包括：

```text
POWER OF SEVEN  合成 128
HEAVY TILE      合成 512
THE NUMBER      合成 2048
BEYOND          合成 4096
FIVE DIGITS     单局达到 10000 分
FUSION ENGINE   累计完成 1000 次合并
```

最高方块只在真正生成新合并值时更新。滑动但没有合并不会虚增，棋盘初始化随机出现的数字也不会越过合并过程。

达到 2048 后游戏仍允许继续，因此 4096 作为额外目标存在。它不要求另开一种模式，只复用已有继续游戏规则。

总合并次数为长期累计，分数与最高方块使用最大值。三种指标分别反映持续游玩、单局表现和真正达到的数字层级。

## 记录 232｜扫雷的关键不是总点击数，而是在明确密度下真正获胜

扫雷成就包括：

```text
SAFE STEP     获得第一次胜利
SCOUT         完成 9×9 / 10 雷
DENSE FIELD   完成 9×9 / 20 雷
WIDE FIELD    完成 16×16 / 40 雷
RED ZONE      完成 16×16 / 60 雷
BOMB SQUAD    累计获胜 10 局
```

不同模式胜利保存在 `wins_by_mode` 中，键使用例如 `9x10`、`16x60` 的稳定组合。

成就进度看到 `mode:9x20` 时，不是从普通统计字典取同名字段，而是进入模式胜利表读取：

```python
value = wins_by_mode.get("9x20", 0)
```

插旗数量和翻格数量虽然会统计，但没有直接作为第一批成就目标。因为反复插旗和随意点击都能增加数量，未必代表完成了一次有效扫雷。

## 记录 233｜俄罗斯方块同时记录一次四行、单局行数和长期消行

俄罗斯方块成就包括：

```text
FIRST FLOOR    消除第一行
FOUR AT ONCE   单次消除四行
STACK CONTROL  单局消除 20 行
FASTER FALL    到达等级 5
BLOCK BANK     单局达到 10000 分
CITY BUILDER   累计消除 200 行
```

一次锁定可能消除 1 到 4 行。`lines_cleared` 增加本次行数，若 `count == 4` 再单独增加 `tetrises`。

单局总行数每次消行后用 `max` 更新 `best_lines`，长期行数用 `add` 累计。同一个动作因此会更新两个不同语义的数据，但不会重复计算同一项。

等级与分数也使用最高值，结束时再写一次作为保险；不能只在结束页统计，否则玩家达到目标后程序异常退出会丢失整局进度。

空袭行动成就包括：

FIRST SORTIE      完成第一项任务
COMMAND BREAKER   击败第一个 Boss
GUNLINE           CANNON 升到 5 级
WIDE SKY          SPREAD 升到 5 级

这些条件全部读取空袭行动已经存在的数据，不为了解锁结果修改关卡难度或掉落概率。

## 记录 235｜少数条件无法由单个统计键表达，我给进度计算器增加组合规则

大部分定义可以直接读取 `statistics[game][key]`，但三类条件需要组合：

```text
wins
  五子棋读取 black_wins + white_wins

both_sides
  黑胜与白胜都大于零才得到 1

mode:尺寸与地雷数
  从扫雷 wins_by_mode 读取

standard_all_s
  检查空袭行动十六个普通关评级
```

进度计算器最后返回：

```python
min(current_value, target), target
```

显示或判断时，已经超过目标的累计值不会让进度出现 `137 / 100`；真实统计仍然保留 137，成就进度只封顶到目标。

我没有把这些组合条件重新塞回各游戏。它们仍然集中在成就层，保持游戏只记录事实的原则。

## 记录 236｜达到条件以后必须先检查稳定 ID，防止每次统计变化都重复解锁

成就数据保存为：

```python
achievements[achievement_id] = {
    "unlocked_at": "本地时间字符串",
}
```

判断条件满足后，还必须确认 ID 不在已解锁字典中：

```python
if progress >= target and achievement_id not in unlocked:
    unlock_once()
```

如果没有这个检查，贪吃蛇最高分达到 20 以后，每吃一个新食物都会再次满足 `best_score >= 20`，顶部通知会反复出现。

解锁时记录到秒的时间，并立即保存。通知动画可以稍后结束，但永久状态不能等动画播完才写入；如果玩家在弹窗出现后立刻退出，下一次启动也不应该再次解锁同一项。

---

## 记录 237｜通知从屏幕顶部弹入，停留后再退出，不打断当前游戏

成就达成经常发生在对局中。如果弹出一个必须确认的模态窗口，贪吃蛇、打砖块和空袭行动都会在玩家无法操作时继续运行，或者被迫暂停节奏。

我把通知做成不接管输入的顶部面板：

```text
ACHIEVEMENT UNLOCKED
成就标题
```

面板前 18 帧使用带轻微回弹的缓动从屏幕外滑入，保持到约第 205 帧，再用最后 35 帧退出；总持续时间 240 帧。

它在当前页面绘制完成后叠加，因此桌面、菜单和所有游戏中都能显示，但不会改变 `state`，也不会阻止键盘和鼠标。

标题过宽时先缩小像素倍率，面板宽度限制在合理范围内；中文模式使用稍高面板，避免字体上下空间不足。

---

## 记录 238｜短时间连续满足多个条件时，通知要排队，不能互相覆盖

某些动作可能同时达到多个条件。例如贪吃蛇从 19 分吃到 20 分时，既可能完成 20 分目标，也可能让累计食物达到 100；空袭行动最后一关获得 S 时，可能同时完成关卡、流程和全 S 条件。

如果系统只有一个 `current_notification`，后写入的标题会覆盖前一个，玩家只看到最后一项。

我使用通知列表保存新解锁项。初版界面一次只显示队首，队首完成 240 帧后移除，下一项再开始计时。

```python
notifications.append({"title": title, "frame": 0})

notifications[0]["frame"] += 1

if notifications[0]["frame"] >= 240:
    notifications.pop(0)
```

这种方案不会让多个面板同时遮住画面，也不会丢失同一帧达成的后续项目。缺点是一次解锁很多项时，通知可能排队较久，我把它保留为初版需要继续观察的体验问题。

---

## 记录 239｜结束逻辑可能被调用不止一次，统计必须有自己的幂等保护

五子棋胜利后会启动连线、棋子闪烁和延迟结束页。动画更新期间，如果胜利处理入口因为状态判断再次执行，胜场和完成局数可能重复增加，从而提前解锁累计成就。

我给单局统计增加完成标记：

```python
if not gomoku_stats_completed:
    gomoku_stats_completed = True
    record_completion_stats()
```

开始新局时才重置标记。

我在测试中对同一胜局连续调用两次结算入口，预期完成局数和赢家胜场都只增加一次。

同样的原则用于其他游戏：结束页可以重复绘制，结束事件也可能被多条路径检查，但“本局已经计入统计”必须成为明确状态，不能依赖函数通常只会被调用一次。

---

## 记录 240｜调试快捷方式不能污染真实长期记录

为了测试较后关卡、快速制造高分或观察结束页，我会使用调试入口修改状态。如果这些操作继续写入正式统计，很多条件会在没有真实完成时被解锁。

我在统计与成就检查的公共入口增加调试保护。只要当前属于调试运行：

```text
不增加统计
不检查新条件
不写正式存档
```

这比要求每款游戏的每一个调试按钮分别记住“不要统计”更可靠。

测试时我先记录完整统计和已解锁字典，再开启调试、写入一个极高贪吃蛇分数并执行检查。结束后两份数据都必须与之前完全一致。

长期系统只有在数据可信时才有意义。调试可以帮助到达任何页面，但不能伪装成玩家真正完成过这些目标。

## 记录 241｜初版完成了“达成与通知”，但还没有提供长期查看这些结果的地方

最后测试覆盖：

```text
从零数据开始完成一个入门条件
  → 统计先更新
  → 稳定 ID 写入存档
  → 顶部通知出现并播放提示音
  → 通知结束后不影响当前页面
  → 再次满足条件，不重复解锁
  → 重启程序，结果仍然存在

连续满足多个条件
  → 每项都写入
  → 通知按顺序显示

重复调用同一局结算
  → 完成局数只增加一次
```

我还检查了 48 个定义的 ID 唯一性，以及普通统计、模式统计和组合条件是否都能返回正确进度。

初版成就系统完成后，玩家在达成目标的一刻能够得到清楚反馈，结果也会永久保存。但它仍然有一个明显缺口：通知消失以后，掌机里没有一个专门位置让玩家重新查看已经获得和仍未完成的项目。

我没有在这一阶段把这个缺口写成已经解决。当前完成的是可靠记录与一次性通知；长期展示仍然需要单独设计。
