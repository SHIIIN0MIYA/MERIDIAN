# 第十二部分：我不再把声音当作单个游戏的附属品

---

## 记录 144｜画面之间已经有专属转场，但整台掌机仍然是安静的

六款游戏拥有各自的界面、反馈动画和桌面转场以后，我重新完整玩了一遍。

这次最明显的问题不是看见了什么，而是什么都没有听见。棋子落下、蛇吃到食物、球击中砖块、数字合并、地雷爆炸和方块消行，在画面上都有动作，耳朵里却没有任何确认。

静音不会让规则失效，但会削弱动作的重量。打砖块里球碰墙和击碎砖块都只靠画面判断，连续发生时很难马上区分；俄罗斯方块硬降已经完成，玩家却要看着方块位置变化才能确认；扫雷踩中地雷的整段演出也缺少一个真正的冲击点。

桌面与游戏之间同样存在问题。专属转场让玩家知道自己打开了不同软件，可进入六款游戏以后，听觉上仍然像同一片空白。

我决定先不继续增加视觉特效，而是补一套贯穿开机、桌面、游戏事件和关机的音频系统。

---

## 记录 145｜我没有把每个声音直接写进各游戏，而是先规定统一调用入口

最直接的做法是在每个碰撞或得分位置临时创建一个声音对象：五子棋落子时生成一次，贪吃蛇吃食物时再生成一次，打砖块碰撞时继续增加。

这种写法短期能响，问题是每款游戏都会重复处理相同事情：音量、静音、声道不足、音频设备不可用和声音是否已经生成。以后想统一调整整体响度，就必须回到所有游戏里逐个修改。

我把游戏代码能够看到的接口压缩成几种调用：

```python
audio.play("gomoku_place")
audio.play("snake_eat")
audio.play_gameover("tetris")
audio.sync_state(current_state)
audio.begin_shutdown()
```

游戏只说明“发生了什么”，不负责决定采样率、波形、缓存和声道。背景音乐也不由页面主动停止上一首再播放下一首，而是把当前状态交给音频管理器判断。

这一步让声音从散落在事件分支里的副作用，变成了一套能够统一调试的系统。

## 记录 146｜没有直接加入一批音频文件，而是使用程序生成声音

我考虑过为每个事件准备独立音频文件。这样容易试听，也能直接使用外部音频编辑器处理。但项目里的画面主要由几何图形和像素色块实时绘制，如果声音全部来自风格不一致的素材，很容易出现某个按钮像现代界面、某个爆炸又像写实战争游戏的情况。

我最后选择程序化生成。

```text
音高序列  → 菜单提示、胜利、开关机
频率滑动  → 落子、碰撞、移动、错误
方波      → 更明确的掌机电子感
三角波    → 较柔和的旋律和低频
噪声混合  → 砖块破碎、爆炸和打击
```

这也减少了资源文件缺失和打包路径错误。只要音频设备可以初始化，程序就能按相同参数生成同一批声音。

代价是所有音色都必须由代码控制。频率、时长、包络和混合比例稍有问题，就会出现刺耳、爆音或毫无区别的电子哔声。因此这一阶段的工作并不是“找几个声音放进去”，而是建立一组足够简单、又能覆盖六种玩法的合成规则。

---

## 记录 147｜音频设备初始化失败时，游戏不能跟着启动失败

音频不是所有运行环境都一定具备的条件。没有声卡、系统设备被占用，或者在无界面的测试环境中启动时，混音器都可能初始化失败。

我使用 44100 Hz、16 位有符号采样、双声道和 512 的缓冲区初始化混音器：

```python
try:
    pygame.mixer.init(
        frequency=44100,
        size=-16,
        channels=2,
        buffer=512,
    )
except pygame.error:
    pass
```

音频管理器启动时再次检查 `pygame.mixer.get_init()`。如果没有可用设备，就把自身设为不可用；后续的 `play()`、背景音乐切换和停止调用全部安全返回。

我专门在虚拟音频环境中启动掌机，确认没有声音时开机、桌面和六款游戏仍然可以正常运行。音频负责增强反馈，不能反过来成为整个程序的启动前提。

## 记录 148｜每个声音先生成采样，再转成双声道 PCM；同名声音只生成一次

程序化声音最终仍然要交给混音器一段 PCM 数据。

我以浮点数计算每个采样点，范围控制在 `-1.0` 到 `1.0`，随后映射到 16 位整数。项目生成的是单条波形，所以写入缓冲区时把同一个值连续写入左右声道：

```python
pcm = array("h")

for sample in samples:
    value = int(clamp(sample, -1.0, 1.0) * 32767)
    pcm.extend((value, value))

sound = pygame.mixer.Sound(buffer=pcm.tobytes())
```

这里的限制很重要。背景旋律、低音与节拍叠加后可能超过正常范围，如果不在写入前截断，整数转换会产生失真，连续播放时会出现明显爆音。

生成背景音乐需要遍历数十万采样点。如果每次进入游戏都重新计算，转场结束后会出现短暂停顿。我增加了声音缓存，以名称作为键：第一次构建后保存 `Sound` 对象，之后直接复用。

测试时我连续返回桌面并重复打开同一游戏，确认第二次进入不会再次承担整首曲目的生成成本。

## 记录 149｜短音效只使用两种基础生成器，但参数必须能表达不同动作

我没有为每一种声音单独写一套采样循环，而是先做了两个基础生成器。

第一种是音高序列。它按固定时长切换音符，并给每个音符加衰减包络：

```python
note_index = int(time / note_seconds)
envelope = (1.0 - note_time / note_seconds) ** decay
sample = oscillator(frequency, time) * envelope * volume
```

第二种是频率滑动。起始频率向结束频率连续插值，还可以加入确定性噪声或脉冲：

```python
frequency = start + (end - start) * progress
sample = tone * (1.0 - noise) + generated_noise * noise
sample *= (1.0 - progress) ** 1.5
```

同样是滑频，向上滑适合吸收、转向和确认，向下滑更像落下、碰撞和失败；短而高的声音适合高频操作，带噪声的低频长音适合爆炸。

第一轮试听时，部分声音没有衰减，结束位置会突然从一个非零采样跳回静音，形成细小爆点。把包络统一收进生成器以后，各游戏不需要再分别处理尾音。

## 记录 150｜不能只给所有按键播放同一个“滴”声，关键动作必须有自己的声音

我先给键盘按下和鼠标点击接入了一个很短的通用按键声。它能证明事件入口工作正常，也让桌面按钮不再完全安静。

但如果游戏里的所有动作都只使用这一声，反馈会变得含糊。五子棋落子、菜单确认和俄罗斯方块旋转听起来完全一样，玩家仍然要依赖画面判断动作性质。

所以我把声音分成两层：

```text
通用输入层
  键盘按下、鼠标按下、普通按钮

玩法事件层
  落子、连线、吃食物、碰墙、击砖、合并、爆炸、消行……
```

通用输入声只说明“掌机收到了操作”；玩法音效说明“游戏规则产生了结果”。

测试时我特别比较连续操作：贪吃蛇快速转向不能抢过吃到食物的提示，打砖块碰墙不能和击碎砖块一样重，俄罗斯方块普通移动也不能和硬降、四行消除使用相同长度。

## 记录 151｜六款游戏的首批事件音效逐个接入，而不是一次性铺满所有代码

我按已经存在的关键反馈点分步接入声音：

```python
game_effects = {
    "gomoku": ("gomoku_place", "gomoku_line"),
    "snake": ("snake_turn", "snake_eat"),
    "breakout": ("breakout_wall", "breakout_paddle", "breakout_brick"),
    "2048": ("2048_slide",),
    "mines": ("mines_pulse", "mines_explosion"),
    "tetris": (
        "tetris_move", "tetris_rotate", "tetris_drop", "tetris_hold",
        "tetris_clear1", "tetris_clear2", "tetris_clear3", "tetris_clear4",
    ),
}
```

```text
五子棋
  落子：210 Hz 向 105 Hz 的短滑频，混入少量噪声
  五连线：五个上行音组成短句

贪吃蛇
  转向：短促上滑
  吃食物：三个快速上行音

打砖块
  碰墙：向下的轻碰撞
  挡板反弹：由低到高，强调重新向上
  击碎砖块：更强的向下滑频并加入噪声

2048
  有效滑动与合并：低频向上滑动，保留轻微摩擦感

扫雷
  探测脉冲：较长的低频脉冲
  地雷爆炸：低频下降并混入较高比例噪声

俄罗斯方块
  移动、旋转、硬降、暂存分别使用不同长度和方向
  消除一至四行使用逐级增加的音符数量
```

消行音效没有只靠放大音量区分。一行是一个音，二行是两个，三行继续上升，四行则用四个音完成完整句子。玩家即使没有盯着计分，也能听出本次消除的等级。

每款游戏的结束音都由自身根音生成一段下降序列，保持相似的失败语法，同时避免六款游戏完全使用同一个结束声。

## 记录 152｜背景音乐先确定一条共同主旋律，再决定每款游戏怎样偏离它

如果六款游戏完全使用无关旋律，它们会重新变成六个独立程序；如果全部循环同一首音乐，又会让玩法差异消失。

我先写下一条 16 个音的主旋律：

```python
THEME_MELODY = [
    261.63, 329.63, 392.00, 523.25,
    392.00, 329.63, 293.66, 392.00,
    261.63, 349.23, 440.00, 523.25,
    440.00, 349.23, 293.66, 246.94,
]
```

它先上行建立记忆点，再回落并换一组音程，最后收在更低的位置。桌面使用这条旋律的基础形态，让玩家先认识整台掌机的声音。

各游戏不重新写一首完全无关的曲子，而是从这 16 个音出发，改变八度、速度、低音、波形、和声和节拍。这样玩家可能不会主动哼出相同旋律，但从桌面进入不同游戏时，音乐仍然像来自同一台设备。

## 记录 153｜每款游戏的主旋律变奏先从音高关系开始

我给六款游戏分别设定了最基础的旋律变化：

```text
五子棋
  所有音乘以 0.75，整体更低、更慢

贪吃蛇
  每四拍最后一个音提高一个八度，形成周期性抬头

打砖块
  每四拍最后一个音乘以 1.5，强调反弹点

2048
  每四拍第一个音降低一个八度，像方块先落稳再展开

扫雷
  所有音降低一个八度，维持低压和谨慎感

俄罗斯方块
  每组第一、第四个音提高，其余音降低，形成更跳跃的堆叠节奏
```

只调整音高还不够。第一次把这些旋律用同一速度、同一方波播放时，确实能听出高低差，但整体仍像把一首曲子简单变速。

我随后继续调整每款游戏的节拍时长、低音序列和波形组合，让变奏对应实际操作节奏，而不是只做数学上的倍率变化。

## 记录 154｜速度、低音和音色共同决定每款游戏的听觉身份

桌面每拍约 0.24 秒，使用方波主音、低八度和声和较轻低音，保持稳定循环。

六款游戏则分别调整：

```text
五子棋       0.32 秒/拍   三角波主音，节奏最从容
贪吃蛇       0.17 秒/拍   方波带轻微摆动，低音更明显
打砖块       0.145 秒/拍  速度最快之一，噪声承担击打节拍
2048         0.22 秒/拍   三角波与正弦低音，减少尖锐感
扫雷         0.29 秒/拍   低八度旋律，节拍克制
俄罗斯方块   0.16 秒/拍   方波摆动与轻噪声节拍，持续推动下落
```

我逐款进入游戏并至少停留两个完整循环，检查旋律首尾是否突然断开、低音是否压住音效，以及高频操作时背景音乐会不会让反馈听不清。

这里没有追求复杂编曲。每首音乐只保留主音、和声、低音和短节拍，目标是让循环稳定、风格明确，并给玩法音效留下空间。

## 记录 155｜音乐不由按钮决定，而是由当前页面状态决定

同一款游戏有开始菜单、对局、结束页和自己的设置页。如果只在点击桌面图标时切换音乐，从结束页返回菜单、从游戏返回桌面或通过其他路径进入页面时，都可能留下上一首曲目。

我建立了页面状态到音乐名称的映射：

```python
STATE_TRACKS = {
    "desktop": "desktop",
    "system_ready": "desktop",
    "password": "desktop",

    "menu": "gomoku",
    "playing": "gomoku",
    "end": "gomoku",

    "snake_menu": "snake",
    "snake_playing": "snake",
    "snake_end": "snake",

    # 其余四款游戏采用相同映射方式
}
```

主循环每帧调用 `sync_state(state)`。如果页面仍属于同一款游戏，当前音乐保持不变；只有映射结果改变时才开始切换。

这样音乐属于页面状态，而不是属于某个按钮。无论玩家通过鼠标、键盘、结束页还是返回路径改变页面，音频系统都会得到相同结果。

## 记录 156｜直接停止上一首再播放下一首会产生断口，我改成两个声道交叉淡化

第一版音乐切换采用最直接的顺序：停止旧曲，立即循环新曲。

从桌面进入贪吃蛇时，旧音乐会突然被截断，新旋律又从满音量第一拍开始。视觉上正在播放转场，听觉上却像音频设备被重新打开了一次。

我为背景音乐保留两个专用声道。切换时，新曲在另一个声道以零音量开始循环，旧声道继续播放；随后在 700 毫秒内一个升高、一个降低：

```python
new_volume = music_volume * progress
old_volume = music_volume * (1.0 - progress)
```

进度达到 100% 后才真正停止旧声道，并清除旧声道索引。

测试中我快速在桌面和游戏菜单之间来回，确认新切换会接管当前活动声道，不会出现两首旧曲都没有停止的叠加。交叉淡化不是为了让切换拖得更长，而是让视觉转场和音乐变化发生在同一段连续时间里。

## 记录 157｜开机与关机使用同一组音高的正序和倒序

开机系统已经有屏幕亮起、欢迎文字和加载过程，但加入音频后，如果第一声直到桌面出现才播放，前面的系统流程仍然像静音动画。

我使用五个音组成开机提示：

```python
power_theme = [261.63, 329.63, 392.00, 523.25, 659.25]
```

开机按由低到高的顺序播放，像设备逐层通电；关机直接使用同一列表的倒序，由高到低收回。

两者都使用较柔和的三角波，并让每个音快速衰减。这样它们和游戏里的方波碰撞声不同，却仍然来自同一套程序化合成方式。

我分别测试正常关机、密码页退出和窗口关闭路径，确保它们最终都调用同一个关机音频入口；不能只有从桌面按钮退出时才听到关机声。

## 记录 158｜完整测试从“有没有声音”改成检查声音是否和规则结果一致

最后一轮测试按整台掌机的使用顺序进行：

```text
启动程序
  → 听见开机上行音
  → 进入桌面，桌面主题开始循环
  → 打开六款游戏，确认音乐交叉切换
  → 分别触发各款游戏的关键操作音效
  → 失败或结束，确认使用对应结束音
  → 返回桌面，确认旧游戏曲目停止
  → 关机，确认桌面音乐淡出并播放倒序关机音
```

我还在没有音频设备的环境中重复启动，并连续快速切换页面，检查系统不会因为声道不足、缺少设备或重复生成曲目而中断。

音频系统完成后，六款游戏没有增加新规则，桌面也没有增加新软件。但玩家第一次能够通过耳朵区分“按下了按钮”“规则已经生效”“本局已经结束”和“正在切换到另一款游戏”。

主旋律的共同来源把六款游戏继续留在同一台掌机里；不同的变奏、节拍和事件音效，又让它们不至于听成同一款游戏。
