# 第二十二部分：坦克对决完成以后，我第一次认真划定“稳定版本”的边界

---

## 记录 354｜功能已经完整，不代表我能准确说出当前到底是哪一版

坦克对决接入以后，游戏、桌面、存档、成就、档案和音频都已经能连成一条完整流程。继续开发当然没有问题，但我第一次遇到了另一个更基础的麻烦：项目里缺少一个可以被代码、文档和 Git 同时确认的版本边界。

以前我判断“这一阶段做完了”，主要依赖自己记得做过哪些功能。项目规模小的时候还能应付，文件和系统越来越多以后，这种方式开始不可靠：界面上可能写着一个版本，更新记录写着另一个版本，代码里又没有唯一来源。

我决定先停下后续扩展，把包含坦克对决的当前状态冻结成一个稳定版本。这里的目标不是做宣传页面，而是回答三个很实际的问题：

```text
当前稳定版本是什么？
这个版本具体包含什么？
以后怎样确认发布前没有把版本信息写乱？
```

---

## 记录 355｜这次先只做本地发布，不把打包、上传和远程仓库混进来

一开始想到“发布”，很容易顺手把可执行文件、自动打包、远程推送和发布页面全列进范围。但这些事情会引入新的环境和权限问题，也会把“确认代码状态”与“把产物发送出去”混成一次不可逆操作。

我把这次范围压缩为：

```text
确定版本号
整理 CHANGELOG
检查本地 Git 状态
运行现有验证
创建本地标记
```

不生成安装包，不自动推送，不访问远程发布接口。这样即使检查失败，也只会报告问题，不会在失败到一半时留下一个错误标签或半成品发布物。

---

## 记录 356｜版本号必须只有一个代码来源

我新增 `meridian/version.py`，把稳定版本集中在一个位置：

```python
__version__ = "3.2.0"
```

其他工程工具需要版本号时都从这里读取，不再各自维护一份字符串。

这件事看起来很小，但它解决的是后续修改顺序问题。如果版本号散落在启动页、README、更新记录和检查脚本中，每次发布都要靠人记得同步修改所有位置；只要漏一处，项目就会同时声称自己属于两个版本。

界面上的设备名称和工程版本是两件事。这一阶段先建立工程版本来源，暂时不把它等同于世界内的显示文字。

---

## 记录 357｜发布检查器第一次直接导入版本模块，我很快把它改成只读语法解析

最直接的写法是：

```python
from meridian.version import __version__
```

但发布检查器的职责只是读取一个字符串。如果为了拿版本号而导入包，随着包初始化逻辑增加，它可能间接初始化 Pygame、音频或其他运行环境。一个本来应该安静检查文本的工具，会开始依赖游戏能否正常启动。

我改成用 `ast` 解析 `version.py`，只寻找名为 `__version__` 的字符串赋值：

```python
tree = ast.parse(version_file.read_text(encoding="utf-8"))

for node in tree.body:
    if isinstance(node, ast.Assign):
        # 找到 __version__ 后只读取字面量
        version = ast.literal_eval(node.value)
```

这样检查过程不会执行项目代码。它只读取文件、解析语法并验证值，发布检查本身不会制造新的运行状态。

---

## 记录 358｜CHANGELOG 要同时保留“正在做的事”和“已经冻结的事”

过去的更新说明更像连续追加的开发笔记，新的内容很容易和已经发布的内容混在一起。我把它分为两个区域：

```text
[Unreleased]
  之后继续开发但尚未进入稳定版本的内容

[3.2.0]
  本次已经确认的 Tank Duel 与平台变更
```

稳定条目记录坦克对决的本地双人、八种道具、三分钟比赛、骤死、存档 Schema 升级和中英文接入。它的作用不是夸大变化，而是让未来回看时能够知道这个版本的边界在哪里。

新工作继续写入 `Unreleased`，不能悄悄改写已经冻结的 `3.2.0` 内容。

---

## 记录 359｜检查脚本只能报告，不能替我修改仓库

我新增 `tools/check_release.py`，并给它定下一个限制：只允许读取。

它会检查：

```text
version.py 中的版本是否正确
CHANGELOG 是否存在且能按 UTF-8 读取
CHANGELOG 是否包含对应版本条目
工作区是否干净
本地是否已经存在同名标签
```

它不会自动改版本，不会补写 CHANGELOG，不会提交代码，不会创建标签，也不会推送。

发布步骤中最危险的不是检查失败，而是检查器一边发现问题一边继续修改状态。只读设计让我可以反复运行它，失败后根据输出逐项修正，而不必先清理工具自己留下的副作用。

---

## 记录 360｜我给失败情况也写了验证，而不只测试“全部正确”

如果只用当前正确仓库运行一次检查器，它能返回零并不能证明判断逻辑可靠。我补了几类反例：

```text
version.py 中没有 __version__
版本不是字符串
CHANGELOG 缺失
CHANGELOG 不是有效 UTF-8
CHANGELOG 没有对应版本标题
工作区存在未提交修改
同名本地标签已经存在
```

这些情况必须返回明确问题，不能因为解析异常直接留下难以理解的堆栈，也不能把缺少信息当成通过。

这次我开始把“发布失败是否安全”也视为发布流程的一部分。

---

## 记录 361｜第一次版本检查仍然会跟着开发版本漂移

初版检查器从 `version.py` 读取版本，再用读取到的值拼出标签：

```python
release_tag = f"v{version}"
```

表面上它保持了一致，实际却没有守住这次发布的目标。只要有人提前把版本改成 `3.3.0`，脚本就会自然转去检查 `v3.3.0`，完全忘记这次原本要冻结的是 `v3.2.0`。

我把目标标签固定下来：

```python
RELEASE_TAG = "v3.2.0"
```

版本来源负责说明代码当前声称的版本，发布目标负责说明这次流程允许发布哪一版。两者必须相等，但不能由同一个错误值同时推导出来。

---

## 记录 362｜只固定标签还不够，版本和更新记录可以一起“错得很一致”

继续测试后又发现一种情况：如果 `version.py` 改成 `3.3.0`，CHANGELOG 也恰好存在 `[3.3.0]`，两个文件彼此一致，检查仍可能通过。

问题在于检查器验证了“元数据互相吻合”，却没有验证“它们是否属于本次目标”。

我再加入固定发布版本：

```python
RELEASE_VERSION = "3.2.0"
RELEASE_TAG = f"v{RELEASE_VERSION}"
```

读取到的 `__version__` 必须先等于 `RELEASE_VERSION`，然后才检查 CHANGELOG。这样即使两个文件一起漂移，检查器也会明确拒绝。

---

## 记录 363｜README 也暴露了“最新开发状态”和“最新稳定版本”混用的问题

整理元数据时，我发现 README 中的表述会让人把正在开发的内容当成最新稳定发布。过去只有自己使用时问题不明显；一旦项目开始维护稳定边界，这种说法就会让文档先于代码跨入下一阶段。

我把“当前开发内容”与“最新稳定版本”分开写，稳定版本只指向 `v3.2.0`。验证命令也限定在这次实际需要检查的范围，不用一个模糊的“大概全部通过”代替具体步骤。

文档不是发布后的附属品。版本含义如果在 README 中不清楚，即使标签正确，使用者仍然会得到错误判断。

---

## 记录 364｜干净工作区成为创建稳定标记前的硬条件

开发过程中保留未提交修改很正常，但稳定标签不能建立在“磁盘上的代码”和“提交中的代码”不一致的状态上。

如果工作区不干净，我实际测试的可能包含尚未提交的修复，而标签最终只指向不含修复的提交。试玩时看起来正常，重新检出标签后却无法复现。

所以检查器把下面的结果直接视为失败：

```text
git status --porcelain
```

有任何输出都先停止发布。我要么把修改整理成明确提交，要么把不属于发布的工作移出范围，不能假装它不存在。

---

## 记录 365｜已经存在同名标签时，流程必须拒绝覆盖

标签是版本边界，不应成为一个可以随手挪动的书签。检查器会先查询本地是否已经存在 `v3.2.0`。

如果存在，它只报告：

```text
local tag v3.2.0 already exists
```

而不是删除、覆盖或强制重建。

这能阻止一次重复执行悄悄改变历史指向。真要修改已经标记的稳定版本，必须作为单独决策处理，不能由普通检查命令代劳。

---

## 记录 366｜最后创建的是本地带说明标签，而不是一次自动上传

版本、更新记录、测试和工作区都确认以后，我才为当前稳定提交建立本地 `v3.2.0` 标签。

这个标签只存在于本地仓库，不自动推送。发布动作到这里结束，因为我一开始就没有把远程发布授权放进范围。

这种收尾看起来比“一键发布”慢，但每一步都能明确回答发生了什么：代码先被冻结，元数据被验证，已有标签被排除，最后才产生新的版本标记。

---

## 记录 367｜版本验证与游戏验证被分成两条线

发布检查器只能证明版本信息和 Git 状态合理，不能证明游戏本身没有坏。我保留两类验证：

```text
工程验证
  版本、CHANGELOG、工作区、标签

程序验证
  测试、模块编译、关键启动路径
```

二者不能互相替代。测试全部通过但 CHANGELOG 写错，仍然不是可追踪的稳定版本；版本文件完全一致但游戏无法运行，也同样不能发布。

我没有把这些命令塞进一个会自动修改状态的脚本，而是让检查结果保持可读，确认每一类失败究竟属于代码还是发布元数据。

---

## 记录 368｜这次没有增加玩家可见功能，却改变了我继续开发的方式

以前一个阶段结束，通常意味着页面上多了一个按钮、一个游戏或一个系统。这一次玩家几乎看不到新内容，但项目第一次有了明确的稳定边界。

我得到的不是一个“版本号显示”，而是一套约束：

```text
工程版本只有一个来源
稳定内容与未发布内容分开记录
检查过程保持只读
发布目标不能随开发版本漂移
标签只建立在可复现的提交上
```

从这里开始，后续优化可以继续进入 `Unreleased`，而坦克对决完成时的状态仍然能被准确找回。项目不再只依靠我的记忆说明自己走到了哪里。
