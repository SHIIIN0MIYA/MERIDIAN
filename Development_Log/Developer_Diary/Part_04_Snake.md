# 第四部分：第一个新游戏——贪吃蛇

---

## 记录 32｜先用第二款游戏检验这台掌机是不是只能装五子棋

`HAO'S GAME DECK` 的桌面和外壳已经完成，但真正能打开的仍然只有五子棋。其余软件栏即使排列得再整齐，也只是写着 `COMING SOON` 的占位。

我决定开始开发第二款游戏，先做贪吃蛇。

它和五子棋的操作方式差别很大。五子棋等待鼠标落子，每次操作后规则才向前一步；贪吃蛇则要持续移动，玩家只能在有限时间内用键盘改变方向。

如果贪吃蛇也能从桌面进入、持续更新、正确结束并返回，就能证明这套掌机入口不只适合回合制棋盘游戏。

这一轮仍然按之前的节奏来：先把最小玩法循环做通，再实际玩，发现问题后补反馈和界面，最后才把它放上桌面。

---

## 记录 33｜先只做“移动、吃食物、变长、死亡”

贪吃蛇的第一版不需要开始页和设置页，先验证四件事：

```text
蛇按固定节拍前进
   ↓
玩家改变方向
   ↓
蛇头碰到食物后身体增长
   ↓
撞墙或撞到自己后结束
```

蛇身直接保存为一组网格坐标，列表开头是尾部，最后一个坐标是头部：

```python
snake = [
    (mid, mid - 2),
    (mid, mid - 1),
    (mid, mid),
]
```

开局长度为三格，放在棋盘中部，默认向右移动。每次移动先根据方向计算新蛇头，再把它加入列表末尾。

如果没有吃到食物，就删除列表开头的尾部坐标。列表长度不变，画面上看起来就是整条蛇向前移动了一格。如果吃到食物，则暂时不删除尾部，蛇身自然增加一格。

这个写法不需要让每一节身体单独追踪前一节的位置，蛇的整个形状都由坐标列表表达。

## 记录 34｜沿用 504 像素游戏区域，但重新划成 24×24

为了让新游戏放进现有的 `1280×720` 布局，我继续使用五子棋已经占用的主要游戏区域。可用宽度是 504 像素，贪吃蛇划分为 `24×24` 个格子，每格正好 21 像素：

```python
SNAKE_GRID_COUNT = 24
SNAKE_CELL_SIZE = 504 // SNAKE_GRID_COUNT
```

24 格不会少到让蛇很快填满屏幕，也不会密到看不清每一节身体。整数格子还能保证网格线、食物和蛇身都落在完整像素上，不需要用浮点数修正边缘。

我给整个区域画了深色底板和细网格。蛇身与食物都不占满整格，而是向内缩进几像素并保留深色描边，这样相邻身体不会连成一整块无法分辨的色条。

这一版先确认坐标和绘制是一一对应的：逻辑中的 `(row, column)` 必须始终转换为：

```python
x = board_x + column * cell_size
y = board_y + row * cell_size
```

如果行列在某一处写反，蛇会看起来向右，碰撞计算却按向下处理。把转换方式固定下来以后，方向输入、食物位置和碰撞都使用同一套网格坐标。

## 记录 35｜蛇不能每帧移动，只能用计时器控制节拍

主循环以每秒 60 帧运行。如果每次更新都让蛇前进一格，它一秒会移动 60 格，玩家根本来不及转向。

我增加了 `snake_move_timer`。每帧只把计时器加一，达到设定间隔后才真正移动一格：

```python
snake_move_timer += 1

if snake_move_timer < move_interval:
    return

snake_move_timer = 0
move_snake_one_cell()
```

普通速度先定为每 8 帧移动一格，大约每秒移动 7.5 格。键盘事件仍然每帧接收，所以玩家不需要刚好在蛇移动的那一帧按键；输入只负责改变下一次移动使用的方向。

第一次试玩时，这种离散节拍比直接按真实时间连续滑动更适合像素网格。玩家能看清蛇每次进入哪一格，碰撞规则也不需要处理身体处在两个格子之间的情况。

## 记录 36｜方向输入不能直接覆盖当前方向

最初把方向键直接写进 `snake_dir` 时，很容易出现一个问题：蛇正在向右移动，玩家误按左键，下一步蛇头就会直接撞进自己的第二节身体。

这种立即反向不应该被当成正常操作，所以相反方向需要被忽略：

```python
current_dx, current_dy = snake_next_dir
new_dx, new_dy = new_direction

if current_dx + new_dx == 0 and current_dy + new_dy == 0:
    return
```

我还把方向拆成了两个值：

- `snake_dir`：上一轮移动实际使用的方向；
- `snake_next_dir`：玩家已经输入、下一轮准备采用的方向。

这样按键不需要立刻移动蛇，只要先保存意图。移动计时器到点以后，再把 `snake_next_dir` 赋给 `snake_dir` 并计算新蛇头。

蛇头上的两只像素眼睛也改为跟随 `snake_next_dir`。如果仍然使用上一轮的 `snake_dir`，玩家已经按下转向键，蛇头却要等移动以后才转眼睛，操作反馈会慢半拍。现在按键后朝向会先变化，下一次移动再真正进入对应格子。

方向键和 `WASD` 使用同一套 `_set_snake_direction()`，避免两种控制方式分别维护反向判断。

## 记录 37｜食物不能通过“随机到空位为止”来生成

最直接的食物生成方法是随机一组行列，如果落在蛇身上就继续随机。

蛇很短时这种方法通常能用，但随着身体变长，重复命中的次数会越来越多；如果棋盘已经被蛇占满，循环甚至永远找不到空位。

我改为先遍历整个 `24×24` 网格，收集所有不在蛇身中的坐标，再从空位列表中随机选择一个：

```python
snake_cells = set(snake)
empty_cells = []

for row in range(SNAKE_GRID_COUNT):
    for column in range(SNAKE_GRID_COUNT):
        if (row, column) not in snake_cells:
            empty_cells.append((row, column))

food = random.choice(empty_cells) if empty_cells else None
```

这里把蛇身临时转成集合，是为了让“这个格子是否被占用”的判断不必每次从头扫描整个列表。

如果没有空位，食物设为 `None`，绘制和碰撞也先判断它是否存在。即使一般游玩很难真正填满 576 个格子，规则也不应该在这个状态下卡进无限循环。

## 记录 38｜固定速度能玩，但分数提高以后没有压力

核心规则跑通后，我连续玩了几局。普通速度在开局时比较合适，但吃到很多食物以后，蛇虽然变长，移动节拍却完全不变。玩家只需要维持同样的反应速度，难度主要来自身体占用空间，没有明显加速感。

我决定让速度随分数分段提高：每得到 5 分，移动间隔减少 1 帧，但最快不低于 4 帧。

```python
speed_bonus = snake_score // 5
current_interval = max(4, snake_base_interval - speed_bonus)
```

第一次处理加速时，我直接在得分后修改 `snake_base_interval`。后来加入速度选择后，这个写法开始混乱：`snake_base_interval` 既代表玩家选择的难度，又被每次得分持续减小。重新开始或切换速度时，很难判断它现在保存的是基础值还是已经加速后的值。

最后把两件事分开：

- `snake_base_interval` 只保存速度选项；
- `_get_snake_current_interval()` 根据基础值和当前分数临时计算实际间隔。

设置页提供三种速度：

```text
SLOW    11 帧移动一格
NORMAL   8 帧移动一格
FAST     6 帧移动一格
```

无论选择哪一种，分数每增加 5 分仍会在这个基础上加快，最终都受 4 帧下限保护。

## 记录 39｜补上开始页和设置页，让它成为独立游戏

规则原型完成后，如果从桌面点击图标就直接开始移动，玩家还没来得及看操作说明，蛇已经走出了好几格。

所以我给贪吃蛇也拆出自己的页面状态：

```text
SNAKE_MENU
   ↓
SNAKE_PLAYING
   ↓
SNAKE_END

SNAKE_SETTINGS 从菜单进入，再返回菜单
```

开始页提供 `START`、`SETTINGS` 和 `DESKTOP`。按回车或空格也可以直接开始，`ESC` 则返回掌机桌面。

设置页除了慢速、普通和快速，还提供三种不影响规则的蛇身颜色：

```text
GREEN
LIME
RED
```

速度选择改变实际操作难度；颜色选择只改变蛇头和身体的绘制颜色。两类选项都使用明确的选中状态，当前选项会使用亮色填充和角落标记，而不是只依靠玩家记住自己刚才点了哪个按钮。

开始新游戏时，要重新建立三节蛇身、方向、食物、分数、移动计时器和所有临时动画。速度与颜色属于设置，不在重新开始时被覆盖。

## 记录 40｜重新安排对局界面，不让状态文字压住游戏区域

贪吃蛇需要持续观察整个网格，分数和操作提示不能盖在棋盘上。

我沿用现有窗口的三段式空间：左侧窄栏放竖排 `SNAKE` 标志，中间是 `504×504` 的游戏网格，右侧面板显示状态。

```text
┌────────┐  ┌──────────────────────┐  ┌─────────────────┐
│   S    │  │                      │  │     STATUS      │
│   N    │  │      24×24 网格      │  │   SCORE / BEST  │
│   A    │  │                      │  │   SPEED         │
│   K    │  │                      │  │   操作提示      │
│   E    │  │                      │  │                 │
└────────┘  └──────────────────────┘  └─────────────────┘
```

右侧同时显示当前分数、当前运行中的最高分、实际移动间隔，以及 `WASD / ARROWS`、`R: Restart`、`ESC: Menu`。

最高分先只记录本次程序运行期间的结果。每次吃到食物和游戏结束时都用当前分数更新 `snake_best`，重新开一局不会把它清零。

画面颜色改成深青绿色。蛇身使用亮绿，食物使用粉红色，状态框使用青色描边。这套配色与五子棋的木色和黑白棋子明显不同，让玩家从桌面进入以后能立刻知道自己已经处于另一款游戏。

## 记录 41｜吃到食物以后，只增加数字还是太安静

第一版吃到食物时，食物从原位置消失，分数加一，然后另一枚食物出现在新位置。规则完全正确，但反馈太弱。

蛇移动节拍很快，玩家的视线主要跟着蛇头。如果只让右侧分数从 `3` 变成 `4`，有时甚至不会注意到刚才已经得分，只觉得食物突然换了位置。

我给得分增加了两层反馈。

第一层是分数跳动。数字在 8 帧内向上弹起再落回原位，最大位移 6 像素：

```python
offset = sin(progress * pi) * 6
score_y = base_score_y - offset
```

第二层是食物粒子。吃到食物时，从原位置生成 10 个小像素块，向不同方向散开，持续 18 到 28 帧后消失。粒子只负责表现，不参与蛇身和食物碰撞。

这样玩家可以同时从棋盘上的爆散和状态栏的数字跳动确认得分，而不需要把注意力从蛇头完全移到右侧面板。

## 记录 42｜撞墙后立即盖住棋盘，死亡感仍然不够

碰撞规则完成后，最初只要蛇头越界或进入自己的身体，就立即切到写着 `GAME OVER` 的结束面板。

实际试玩时，这个结果有些突然。玩家知道自己输了，却不一定看清最后撞在了哪里，尤其是速度提高以后，结束页像是直接中断了对局。

我保留死亡瞬间的棋盘作为背景，让它在结束面板出现后继续进行 18 帧短暂震动，同时覆盖半透明黑色遮罩和居中的结果面板。蛇的最终位置仍然能从遮罩下面看到，震动也只作用于下方的对局画面，不会让结果按钮一起乱晃。

结束面板显示：

```text
GAME OVER
SCORE
BEST
PLAY AGAIN
MENU
DESKTOP
```

`PLAY AGAIN` 立即重建一局；`MENU` 返回贪吃蛇开始页；`DESKTOP` 直接退出当前游戏并返回掌机桌面。键盘也保留 `R` 重新开始和 `ESC` 返回菜单。

这里继续保持不同层级的返回关系：结束一局不等于退出贪吃蛇，退出贪吃蛇也不等于关闭整个程序。

## 记录 43｜结束面板改过尺寸以后，按钮仍停在旧坐标

结束页第一次排版时，按钮纵坐标直接写成了固定值。后来我调整了结束面板的高度和垂直位置，文字跟着面板移动，按钮却仍然从旧的 `y = 440` 开始排列。

结果是三个按钮与分数区域的间隔不一致，最下面的 `DESKTOP` 还会过分靠近面板边缘。继续微调三个绝对坐标只能暂时修好当前布局，下次移动面板又会出现同样的问题。

我把按钮位置改成相对结束面板计算：

```python
panel = pygame.Rect(
    window_center_x - 280,
    window_center_y - 215,
    560,
    430,
)

button_start_y = panel.y + 250
```

后面的按钮再根据按钮高度和间隔依次排列。这样面板整体移动时，标题、分数和按钮会作为一个完整组件一起移动。

测试鼠标点击时也使用同一组按钮矩形，不再另外写一份命中区域。否则画面上的按钮虽然移动了，实际可点击位置仍可能留在旧坐标。

## 记录 44｜把第一个 COMING SOON 换成真正的软件图标

贪吃蛇内部流程稳定以后，才开始接入掌机桌面。

我用一个可点击的 `SNAKE` 图标替换原来的预留栏。图标内部不是只写游戏名称，而是在一个六格宽的小区域里画出弯曲的蛇身和一枚粉色食物，让它与五子棋的小棋盘图标保持同样的像素表达方式。

点击图标后进入 `SNAKE_MENU`，而不是直接进入对局。贪吃蛇自己的开始、设置、游玩和结束状态都只在打开该软件以后处理；返回桌面后，它们不再接收方向键，也不会继续增加移动计时器。

接入后我反复测试了完整路径：

```text
掌机桌面
   ↓
贪吃蛇开始页
   ↓
选择速度和颜色
   ↓
开始游戏
   ↓
吃食物并提高分数
   ↓
撞墙或撞到自身
   ↓
重新开始 / 返回菜单 / 返回桌面
```

测试中逐项确认：

- 开局始终在棋盘中央生成三节蛇身并向右移动；
- 方向键和 `WASD` 使用相同规则，反向输入不会立即掉头；
- 食物不会生成在蛇身上，吃到后分数和长度各增加一；
- 每 5 分速度提高一级，但不会快于 4 帧一格；
- 重新开始会清理旧蛇身、旧食物、计时器和粒子；
- 游戏结束后仍能看清最后碰撞位置；
- 返回桌面以后蛇不再在背景移动，再次进入时先回到开始页。

五子棋之后，`HAO'S GAME DECK` 终于有了第二款真正可玩的内容。更重要的是，这次开发验证了掌机能够同时容纳两种完全不同的节奏：一种等待鼠标落子，另一种持续接收键盘方向并按帧更新。

第一个 `COMING SOON` 被替换掉以后，桌面不再只是在展示将来的容量，它开始真正被新的游戏填充。
