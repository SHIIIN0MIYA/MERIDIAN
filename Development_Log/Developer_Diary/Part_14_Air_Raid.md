# 第十四部分：代码拆开以后，我开始开发空袭行动

---

## 记录 173｜暂停增加游戏不是永远不再增加，而是要等平台先能承受下一款游戏

六款游戏完成时，我曾经停止继续填满桌面，因为当时开机、关机、转场、音频和代码结构都还不完整。

这些基础问题逐步处理以后，我重新考虑下一款游戏。这次不能只证明“桌面还能多放一个图标”，而是要验证拆分后的结构能否容纳一款体量明显更大的游戏。

我选择了纵向射击方向，并暂定名称为 `AIR RAID`。

它和已有六款游戏的区别很大：玩家需要持续移动，敌人和子弹同时更新，画面中存在大量短生命周期对象，还要处理碰撞、武器、敌机编队和关卡推进。

如果它仍然只能靠把所有内容塞回主程序才能完成，就说明前面的文件拆分只是表面整理。因此这一款游戏从一开始就单独放在自己的模块中，通过现有状态分发、桌面入口、转场和音频接口接入掌机。

## 记录 174｜第一版目标只有四件事：移动、自动射击、生成敌机、被击中后结束

纵向射击很容易从一个小原型迅速膨胀成大量敌人、武器和关卡。我先限制最小闭环：

```text
玩家飞机能够在战斗区域内移动
  → 子弹持续向上发射
  → 敌机从上方进入并向下移动
  → 双方子弹能够造成伤害
  → 玩家耐久归零后进入结束页
```

这一版没有先做复杂菜单，也没有先准备很多 Boss。我要先确认基础移动是否适合键盘，子弹密度是否可读，碰撞范围是否公平。

第一次运行时，只要能够从屏幕底部移动、击毁一个从上方进入的目标，并且被敌弹击中后确实扣除耐久，玩法骨架就成立。

后面的武器、评分和关卡都只能建立在这个循环之上；如果移动与碰撞本身不好玩，增加内容只会放大问题。

## 记录 175｜战斗区域没有占满整个窗口，我在两侧预留了信息面板

掌机窗口是横向的，而纵向射击需要一个较高、较窄的战场。如果让玩家飞机在整个 1280×720 窗口里移动，横向空间过大，敌机和弹幕很难形成压力，状态文字又只能压在战场上方。

我把真正的战斗区域固定为：

```python
AIR_PLAY_RECT = Rect(330, 42, 620, 636)
```

左右各留一块面板。左侧显示机体耐久、护盾、连击、倍率、擦弹和任务进度；右侧显示分数、三条武器路线、导弹充能与实时评级。

第一版只画中央战场时，规则可以运行，但玩家很难同时判断还有多少耐久、当前武器等级和任务完成比例。把信息全部叠在弹幕上又会遮挡安全路线。

固定三栏结构以后，战场中的对象只负责战斗，长期信息留在两侧。玩家视线在紧张时可以集中中央，需要确认状态时再短暂扫向两边。

## 记录 176｜飞机直接跟随按键太生硬，我给速度增加了缓入和惯性

最直接的移动是按住方向键就每帧增加固定坐标，松开立即归零。功能正确，但飞机像一个光标，没有飞行器改变方向时的重量。

我先计算目标速度，再让当前速度逐步靠近它：

```python
target_vx = normalized_dx * speed
target_vy = normalized_dy * speed

vx = vx * 0.65 + target_vx * 0.35
vy = vy * 0.65 + target_vy * 0.35
```

这里还必须归一化斜向输入。如果同时按上和右却分别叠加完整速度，斜线移动会比单方向快约 1.414 倍，玩家会得到没有说明的额外优势。

我让普通速度保持在每帧约 5.2 像素，按住 `Shift` 时降到 2.6。慢速不是单纯让游戏更容易，而是给密集弹幕中的微调留出控制档位。

飞机位置始终限制在战斗矩形内，并在顶部留出约 105 像素的敌方活动空间，避免玩家直接贴到生成区进行近距离无风险输出。

## 记录 177｜主武器改成自动射击，把玩家注意力留给移动和路线判断

最初可以让玩家不断按攻击键发射，但纵向射击中主武器使用频率极高。持续敲击不会增加有意义的判断，只会让移动操作更疲劳。

我让主武器在冷却结束时自动开火：

```python
player["cool"] -= 1

if player["cool"] <= 0:
    fire_current_weapon()
```

武器等级决定弹道数量、伤害和下一次冷却。玩家的主动操作集中在移动、慢速精确控制和蓄力完成后的导弹释放。

第一次测试自动射击时，子弹数量明显增加，如果每一发都保留很长寿命，离开屏幕的子弹仍会停留在列表中。于是玩家子弹同时拥有 90 帧寿命，并在越过战场顶部后立即移除。

自动开火减少了无意义按键，但也要求对象清理更加严格，否则长时间游玩会不断积累已经不可见的子弹。

## 记录 178｜飞机画得很大，但真正判定点必须小，否则密集弹幕没有可躲空间

玩家飞机的像素轮廓包含机翼、机头和尾焰，视觉宽度超过三十像素。如果碰撞范围完全按整个轮廓计算，玩家会觉得自己明明从两颗子弹之间穿过去，却仍然被翼尖擦中。

我把实际受击半径设为 5 像素，并在按住 `Shift` 进入慢速状态时显示中心判定点。画出来的飞机负责识别，中心小圆负责告诉玩家真正需要保护的位置。

受击以后也不能每一帧继续扣血。我加入无敌计时：开局约 90 帧保护，正常受击后约 105 帧；期间飞机通过明暗闪烁提示不可再次受伤。

护盾则单独吸收一次伤害：

```python
if shield > 0:
    shield = 0
    invulnerable_frames = 55
    return
```

测试时我让敌弹停在玩家中心附近，确认同一颗或相邻子弹不会在短时间内连续清空五格耐久。密集弹幕的难度应该来自路线判断，而不是一次碰撞被重复结算。

## 记录 179｜敌机和敌弹按完整速度运行时，普通模式几乎没有观察时间

最初把敌机配置中的速度直接用于普通关卡，单个敌人没有问题；波次增加以后，敌机向下推进、横向摆动和弹幕速度叠在一起，玩家刚看见编队就必须立即躲避。

这不是单纯“难”，而是缺少学习时间。玩家还没有分辨敌机类型，就已经进入失败反馈。

我给普通模式增加两个独立倍率：

```python
enemy_move_scale = 0.70
enemy_bullet_scale = 0.85
```

敌机移动明显放慢，子弹稍微放慢，但两者没有按相同比例降低。这样编队更容易被看清，弹幕仍然保留压力。

我没有直接减少所有敌机生命或删除弹幕，因为问题出在信息出现太快，不是玩家输出不足。调整后第一次进入时能够先认识直射、扇形与环形弹幕，再逐渐适应更密集的组合。

## 记录 180｜八种普通敌机不只修改生命值，还要改变运动和射击职责

我把普通敌机数据集中成八种类型：

```text
scout      低耐久、快速进入、瞄准单发
striker    更快，使用扇形射击
bomber     高耐久，释放环形弹
sniper     横向移动，发射更快的瞄准弹
layer      释放缓慢的大型障碍弹
shield     高耐久并带明显护盾轮廓
carrier    体型更大，承担编队压力
commander  普通敌机中最高耐久，使用多向指挥射击
```

如果敌人只是在同一三角形上修改颜色和血量，玩家无法从画面判断威胁。绘制时，轻型敌机使用尖锐三角轮廓，轰炸与载具类使用更宽的矩形机身，护盾类型增加外圈。

它们的运动也不同：侦察与突击机用正弦轨迹摆动，狙击和护盾机在左右边界反弹，重型单位则以较慢幅度横移。

这样玩家可以在子弹真正发射前，仅根据轮廓和移动方式预判接下来需要躲避哪类攻击。

## 记录 181｜敌机生成位置不能完全随机，否则同一关的难度会大幅漂移

空袭行动需要变化，但如果每一波敌机都在完全随机的位置出现，有时会集中在一侧形成安全通道，有时又会重叠在玩家正上方，让同一关的难度差异过大。

我用波次编号和槽位计算生成位置：

```python
x = left + 50 + ((slot * 97 + wave * 61) % available_width)
```

同一关、同一波的编队位置能够稳定复现，波与波之间又不会完全相同。每波数量从三架起步，随关卡和波次增加，最高限制为七架；部分较后关卡在特定波次额外加入精英单位。

这种确定性对调试很重要。某个弹幕组合过难时，我能够重新进入同一关观察相同编队，而不是等待随机数再次生成相似情况。

随机感主要由轨迹相位和战斗过程产生，关卡骨架本身保持可验证。

## 记录 182｜弹幕模式先做成少量规则，再由敌机和 Boss 组合使用

我没有为每个敌人手工保存一整张子弹时间表，而是先实现一组弹幕生成规则：

```text
aim / snipe       朝玩家位置发射一发或三发窄角弹
fan               以瞄准方向为中心展开五发扇形弹
ring / halo       沿整圆均匀发射十二发或十八发
wall              九个方向中留下规律缺口
spiral            多条旋臂随相位转动
cross             四个垂直方向组成旋转十字
mine              缓慢下落的大半径弹
spawn / command   三发小角度瞄准组合
```

第一版扇形弹使用固定屏幕方向，玩家移动到另一侧后，敌机仍然向旧方向射击，几乎没有互动。最终每次发射前重新用玩家与敌机坐标计算瞄准角度，扇形只负责在这个角度两边增加偏移。

每颗敌弹都保存独立编号、速度、半径、寿命和是否已经擦弹。离开战斗区域或寿命结束后立即删除，避免长时间关卡让列表持续增长。

## 记录 183｜关卡没有一次铺开很多相似波次，而是采用普通任务与 Boss 交替

核心战斗成立以后，我开始扩展关卡。

如果连续十几关都只是增加敌机数量，玩家只能感受到数值变大。我把整个流程拆成八组，每组两关：

```text
第 1、3、5……15 关   普通任务
第 2、4、6……16 关   Boss 战
```

总共 16 关。普通任务负责引入新的敌机、目标和组合，紧接着的 Boss 战集中检验这一组学到的躲避方式。

关卡数据不写进更新循环，而是保存在独立配置中。普通关记录任务类型、波数、敌机种类、目标值和时限；Boss 关记录生命值和三阶段弹幕模式。

这样调整某一关时不需要修改战斗引擎，也避免出现大量 `if level == ...` 分支散落在碰撞和生成代码里。

## 记录 184｜普通关不都以“清空敌人”为唯一目标

只要求击毁所有敌机会让每关的最优策略完全相同。我给普通关安排了八种目标表达：

```text
intercept      击毁指定数量敌机
escort         保持护送进度
nodes          摧毁特定节点型敌机
evac           维持撤离通道
fortress       摧毁重型火力单位
gauntlet       在持续时间内生存
convoy         摧毁载具与指挥单位
breakthrough   完成最终击破目标
```

任务进度统一换算为 0 到 100%，显示在左侧信息面板。击杀型目标读取已击毁数量，护送与撤离目标会因敌机逃脱而下降，生存目标则由已坚持帧数推进。

第一次测试护送类任务时，我只在敌机逃出底部时把它移除，任务条没有变化，玩家无法理解漏怪会造成什么后果。把逃脱与任务值绑定以后，放过敌人才真正成为需要承担的失败风险。

## 记录 185｜每关开始前增加任务简报，避免玩家进入弹幕后才猜目标

任务类型变多后，只在战斗左侧写一行 `OBJECTIVE` 不够。玩家进入后首先关注移动和弹幕，很难同时阅读较长说明。

我在关卡选择与战斗之间增加简报状态：

```text
选择关卡
  → 任务简报
  → ENTER / SPACE 部署
  → 正式战斗
```

简报页显示关卡编号、任务标题、两行说明、雷达图形和明确目标。玩家可以按 `ESC` 放弃进入，只有主动确认后才初始化战斗对象。

这个状态也解决了一个技术问题：关卡数据已经选择，不代表所有子弹、敌机和计时器都应该立刻开始更新。只要 `state` 还停在简报页，战斗更新就不会推进。

## 记录 186｜三条主武器路线必须改变弹道，而不是只增加伤害数字

我设计了三种可升级到 5 级的主武器：

```text
CANNON
  直线、高速、随等级增加并行炮口与单发伤害

SPREAD
  从中心向两侧展开，等级越高覆盖角度越宽

LASER
  速度更快、伤害更高并可以穿透，后期增加侧束
```

拾取武器核心时，该武器等级增加一级并立即成为当前武器。等级统一限制在 5，避免重复掉落让弹幕数量无限增长。

第一版只让不同武器使用不同颜色，实际玩时仍然像同一把枪换皮。把炮口数量、横向速度、穿透和冷却分别交给武器计算以后，玩家才需要根据敌群分布选择路线。

武器信息持续显示在右侧面板，当前路线前加 `>`，避免拾取以后只看颜色却不知道等级变化。

## 记录 187｜掉落不能完全随机，我让补给出现具有可复现的节奏

武器核心、修复与护盾如果完全随机，有时玩家连续得到很多修复，有时整关没有任何成长，评分和难度都会失去可比性。

我根据已击毁数量与关卡偏移计算掉落：

```text
特定间隔         修复
另一固定间隔     护盾
每七次击毁附近   在三种武器核心之间轮换
```

关卡不同会改变起始偏移，因此不会每一关都在完全相同的击杀数掉落同一物品，但同一关重复测试仍然可以得到稳定结果。

补给向下缓慢移动，离开底边后清除；玩家接触后立刻应用效果并产生粒子与音效。修复最多恢复到五格耐久，护盾只保存一次格挡，武器等级最多为五级。

这种确定性让失败后重试不再取决于“这次随机数是否愿意给我修复”，也方便判断关卡本身是否合理。

## 记录 188｜连续击破需要奖励，但倍率不能无限增长

只按每架敌机固定分数计算时，玩家安全地逐个处理和连续穿过危险区域几乎没有区别。

我增加连击计时。每击毁一个目标，连击数加一并把剩余时间重置为 150 帧；计时归零后，连击和倍率回到初始值。

```python
combo += 1
combo_timer = 150
multiplier = min(5.0, 1.0 + (combo // 8) * 0.5)
score += int(enemy_value * multiplier)
```

倍率每八次连续击破增加 0.5，最高 5 倍。这样短连击不会让界面数字频繁跳动，长连击又能形成明确目标。

测试时我一开始只在击杀时刷新倍率，没有在计时结束后归零，结果断开很久后下一架敌人仍然沿用旧倍率。把重置放入每帧效果更新后，连击才真正由连续操作维持。

## 记录 189｜慢速模式不仅用于躲避，还承担“擦弹”的风险奖励

按住 `Shift` 后，飞机速度减半并显示中心判定点。只提供慢速会让它成为纯粹的保守选项，我希望玩家在密集弹幕附近主动使用它。

当慢速状态下敌弹进入判定点外侧约 24 像素的范围、又没有真正命中时，记为一次擦弹：

```python
if focus and not bullet["graze"] and distance <= bullet_radius + 24:
    bullet["graze"] = True
    grazes += 1
    score += int(25 * multiplier)
```

每颗敌弹保存 `graze` 标记，保证同一颗停留在附近的子弹只计算一次。

第一次测试如果没有这个标记，一颗移动较慢的大型弹会在连续多帧内反复增加擦弹数，玩家只要贴着它不动就能快速刷分。加入单弹一次限制以后，擦弹重新变成穿过危险边缘的瞬间奖励。

## 记录 190｜特殊导弹不是无限使用，而是通过击破逐步充能

普通射击已经自动进行，我把 `Space` 留给主动释放的特殊导弹。

击毁普通敌机增加 8 点充能，击毁 Boss 增加更多；达到 100 后状态变为 `READY`。释放时按目标优先级锁定最多八个仍然存活的敌人：

```python
targets = sorted(
    enemies,
    key=lambda enemy: (not enemy["boss"], -enemy["hp"]),
)[:8]
```

导弹每帧重新朝自己的目标修正方向，普通敌人受到足以击毁的伤害，Boss 则受到固定高伤害。目标已经被其他攻击消灭时，对应导弹立即移除，不能继续追逐一个不存在的对象。

我测试了场上十个目标的情况，确认只生成八枚导弹；释放后充能归零、`READY` 清除。未充满时按空格只播放很短的不可用提示，不应该生成半套导弹或消耗已有充能。

## 记录 191｜Boss 使用三阶段生命区间，不能只是血量更高的普通敌机

每个 Boss 都保存三套弹幕模式。根据剩余生命比例切换：

```text
高于 67%          阶段 1
34% 到 67%        阶段 2
低于 34%          阶段 3
```

Boss 在战场上方左右移动，顶部显示生命条和当前阶段。不同 Boss 通过扇形、环形、墙、螺旋、十字等基础模式的组合形成差异。

只增加生命值的第一版测试很快变得重复：玩家确认安全路线后，只需要长时间保持同一种移动。阶段切换以后，战斗会在两个明确血量点改变读法，后半段也不会只是延长前半段。

阶段信息不能只藏在弹幕变化中。我在切换时显示中央阶段提示并播放专属音效，让玩家知道规则已经改变，而不是误以为敌机突然出现了不同攻击错误。

## 记录 192｜阶段切换时如果保留上一阶段全部子弹，新旧弹幕会形成无法预判的叠加

Boss 达到阶段阈值时，旧模式发出的子弹仍然可能布满屏幕。如果立即开始下一种模式，玩家面对的不是经过设计的新阶段，而是两套弹幕随机叠在一起。

我在阶段切换时清空当前敌弹，并让 Boss 暂时关闭弱点：

```python
enemy["pattern"] = next_pattern
enemy["weak"] = False
phase_flash = 100
enemy_bullets.clear()
```

阶段提示前约 55 帧内，Boss 不接受有效伤害；提示逐渐结束后重新开放弱点。

这段短暂停顿同时完成三件事：清理旧弹幕、告诉玩家模式改变、阻止玩家在切换演出中继续无风险削减生命。

我反复把 Boss 生命直接调到 66% 和 33% 附近，确认阶段只前进一次、旧子弹会被清理，并且弱点在提示后重新打开。

## 记录 193｜评级不能只看分数，我把通关表现拆成四部分

如果评级只比较分数，最安全的玩法可能是等待更多敌人出现、刻意延长战斗刷连击，而任务完成质量和剩余耐久没有意义。

我把评级指数拆成：

```text
得分相对目标       40 分
击毁率             25 分
任务完成度         20 分
剩余耐久           15 分
```

总分达到 90 为 S、75 为 A、55 为 B，其余为 C。较高难度下阈值再整体提高 5。

结束页显示最终等级、分数、击毁数量、生成数量、擦弹和剩余耐久。战斗右侧同时显示实时评级，让玩家知道当前表现正在上升还是因为漏怪、受伤而下降。

我用极高分、全击毁、任务满进度和五格耐久构造测试，确认能够得到 S；再分别降低击毁率和耐久，检查等级会按预期下降。

## 记录 194｜重试不能继承刚才临时捡到的全部升级，我保存了关卡入口快照

第一次实现重试时，函数只是重新初始化敌机和子弹，却继续使用失败瞬间的武器等级。玩家可以在关卡中捡到升级、故意失败，再通过重试把临时成长带回关卡起点。

这会让重试结果越来越有利，也让同一关无法保持相同起始条件。

进入战斗时，我保存一份入口快照：

```python
entry_snapshot = {
    "loadout": copy(current_loadout),
    "missile_charge": missile_charge,
    "missile_ready": missile_ready,
    "health": health,
}
```

重试先恢复这份数据，再重新生成战斗对象。普通单关会回到该关标准配置；连续流程则保留进入这一关以前已经获得的成长，但不会保留本次失败途中捡到的物品。

测试时我进入关卡后把激光临时提高到 5 级，再执行重试，确认武器会回到入口等级、耐久恢复为本关起始值。

## 记录 195｜关卡选择与连续流程使用同一套战斗代码，但成长规则不同

完成单关结构后，我增加了两种入口。

关卡选择用于直接练习已经开放的关卡。它根据关卡编号提供一套标准武器配置，进入与退出不会把临时成长带到下一关。

连续流程则从第一关开始，通关后把当前武器等级、累计分数和下一关编号保存下来，再进入下一张简报。十六关依次完成后才算整段流程结束。

```text
单关选择：标准配置 → 当前关 → 结束后回菜单

连续流程：第 1 关 → 保留成长 → 第 2 关 → …… → 第 16 关
```

每次通关保存最高开放关卡和该关最佳评级。如果程序在中途退出，菜单可以识别仍然有效的连续进度；重新开始新流程则明确覆盖旧进度。

我分别从第一关连续推进和直接选择较后关卡，确认两条路径最终都调用相同的战斗初始化，而不是维护两套碰撞与敌机逻辑。

## 记录 196｜完成普通流程后增加高难模式和 Boss 连战，但没有复制一套新引擎

普通十六关能够完成以后，我增加两种高难入口。

高难流程继续使用原关卡数据，但敌机生命乘以约 1.22，移动恢复完整速度，敌弹也更快，评级阈值提高。它不是把所有参数简单翻倍，而是缩短普通模式留给玩家的观察时间。

Boss 连战则只选取八个 Boss 关。玩家用五格耐久开始，每击败一个 Boss 恢复一格耐久，并在三种武器核心中选择一项升级后进入下一个：

```text
Boss 1
  → 耐久 +1
  → CANNON / SPREAD / LASER 三选一
  → Boss 2
  → ……
```

连战中的耐久和武器属于整段运行，不能每场恢复满值。供给页因此不是装饰，而是下一场开始状态的正式组成部分。

我测试连续击败第一名 Boss 后，确认页面进入供给选择、耐久只增加一格、选择的武器提高一级，并在下一场保持这些结果。

## 记录 197｜菜单、战斗和暂停都要使用现有掌机规则，而不是成为独立程序

空袭行动拥有自己的菜单、关卡选择、操作说明、任务简报、战斗和结束页，但导航仍然遵循掌机已有层级。

菜单同时支持方向键与鼠标，按钮只有在按下和松开都位于同一区域时才执行；`ESC` 从菜单返回桌面。战斗中 `P` 暂停，`Space` 释放导弹，`R` 重试，`ESC` 返回本游戏菜单。

暂停后，战斗更新立即停止：敌机、子弹、掉落、连击计时和任务计时都不推进，只绘制暂停遮罩。如果只停玩家移动却继续更新敌弹，暂停会直接变成无法操作的失败状态。

菜单上方还加入一块循环演示区域，依次展示敌机编队、三种武器和导弹锁定。它只绘制示意对象，不修改真实关卡进度，也不启动战斗碰撞。

桌面进入时使用空袭主题转场；音乐则沿用已经建立的共同主旋律，使用更快节拍和更高的周期重音形成自己的变奏。射击、受击、护盾、爆炸、补给、导弹和阶段切换全部接入统一音频管理器。

## 记录 198｜最后测试的不是“子弹能不能打中”，而是整段流程能不能重复并保持公平

完整测试覆盖：

```text
从桌面打开空袭行动
  → 查看操作说明
  → 进入关卡选择并打开任务简报
  → 测试普通移动、斜向移动和 Shift 慢速
  → 分别拾取三种武器并升到更高等级
  → 让护盾吸收一次命中，再让耐久正常扣除
  → 用同一颗敌弹靠近判定点多帧，只记录一次擦弹
  → 充满导弹，在十个目标中只锁定八个
  → 把 Boss 调到 66% 和 33%，检查阶段切换
  → 通关后检查评级与关卡开放
  → 失败后重试，确认恢复入口配置
  → 暂停并等待，确认战斗计时没有前进
```

我还连续绘制菜单、选择、说明、简报、战斗与结束页，确认新增状态都已经接入事件、更新和绘制分发表。

空袭行动最终不只是桌面上又多了一枚可以点击的图标。它验证了拆分后的项目能够承受一款同时包含持续输入、大量对象、关卡数据、多种武器、Boss 阶段和长期进度的游戏。

更重要的是，开发节奏没有改变：先让核心循环成立，再通过试玩调整速度和碰撞，然后逐步增加敌机、目标、成长、Boss、评级与模式，最后用重复测试固定规则。
