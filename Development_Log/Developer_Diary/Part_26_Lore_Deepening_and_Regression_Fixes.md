## 记录 427｜第八个世界加入后，项目里所有“七界”都变成了过期事实

坦克对决被注册为钢铁斗场以后，功能层已经能找到新世界，文案层却还残留大量固定数量：器物起源写着七块碎片，连接之核写着维持七界平衡，档案副标题写着七界记录，README 又开始使用八界一器。

## 记录 430｜固定单行标签容不下“器物 + 八个世界”，钢铁斗场实际上被藏起来了

旧布局只在一行中从左向右画分类。它有一个保护逻辑：下一个标签超过面板右边界时就停止绘制。

加入钢铁斗场后总分类数变成九个，最后一个 Tank 标签正好落在被停止的部分。键盘可能仍然可以改变索引，鼠标用户却看不到也点不到这个世界。

这不是档案数据缺失，而是界面仍然假设“分类永远能放在一行”。我开始让标签区域根据实际数量换行。

## 记录 431｜标签行数、列数和宽度改为从分类数量计算

我把每行上限设为八个，再根据数量计算行列：

```python
tab_rows = max(1, (category_count + 7) // 8)
tab_columns = max(1, (category_count + tab_rows - 1) // tab_rows)
tab_w = (
    tab_area_width - gap * (tab_columns - 1)
) // tab_columns
```

每个分类最终得到一个真实 `tab_rect`。绘制、鼠标命中和布局测试都使用同一组矩形，不再分别重复计算 x 坐标。

分类增加时可以自动形成第二行；数量减少时也不会留下手工空位。

## 记录 432｜标签换行后，条目列表也必须跟着向下并重新计算容量

如果只让标签换行，第二行会直接盖住第一条档案。旧代码中的 `list_y` 和可见条目数量都是按单行标签写死的。

我让布局函数同时返回：

```text
tab_rects
list_y
entry_h
entry_gap
visible_entries
panel
```

列表起点由标签行数决定，可见条目数再根据面板底部剩余空间计算。绘制和点击都从这份布局读取。

动态布局不是只解决“能不能画下标签”，还必须保证下游区域知道上游占用了多少高度。


但它暴露的是一次典型的局部重构遗漏：绘制路径已经迁移，较少执行的鼠标释放路径还残留旧变量。

## 记录 439｜扩写内容单独放进文件，核心注册表保持可读

如果把所有新增长段落直接塞进 `lore.py`，世界注册结构会被数百行正文淹没。以后查一个世界的名称、序章或解锁条件，要先穿过大量叙事文本。

我新增 `lore_expansions.py`，用条目 ID 映射中英文扩写：

```python
ARCHIVE_EXPANSIONS = {
    "meridian_origin": {"en": (...), "zh": (...)},
    "twin_signals": {"en": (...), "zh": (...)},

```

所有世界完成注册后，再把扩写追加到对应正文。如果扩写引用不存在的 ID，初始化时直接抛出 `KeyError`，不允许拼错条目后静默丢失文本。

数据被拆开，但引用关系仍然受到严格检查。

## 记录 440｜正文变长以后，固定“每十行一页”会把段落切得很难看

旧阅读器把换行后的文本按十行直接切片：

```python
start = page_index * 10
page_lines = lines[start:start + 10]
```

短条目没有问题。扩写后某页可能只有一段的最后一句，下一页却塞入两个新段落；空白分隔行还会刚好落在页首或页尾，让页面看起来少了一行或突然向下偏。

我没有单纯增加面板高度，因为 1280×720 的阅读区域已经固定。需要改变的是分页方法。

---

## 记录 441｜分页先确定页数，再把全部行尽量平均分配

新的 `_lore_story_pages()` 先根据最多十行计算需要多少页，再用整除与余数平均分配：

```python
page_count = ceil(line_count / 10)
base_size, larger_pages = divmod(line_count, page_count)
```

前 `larger_pages` 页多一行，其他页使用基础行数。比如 21 行不会变成 10、10、1，而会分为 7、7、7。

我接受每页不一定填满十行，换取页面之间更均衡的阅读节奏。页码仍然来自实际页列表，不再用行数反推最后一页。

---

## 记录 442｜分页后还要清理每页首尾的空白段落分隔

正文换行时，我会在每个原始段落后插入空行。平均切页可能把这个空行分到下一页第一项，造成正文从第二行开始；也可能让一页最后只剩空白。

我在形成每页后移除首尾空字符串，但保留页面内部的段落间隔。阅读页索引也会被限制在新的页数范围内，文本扩写或语言切换后不会停在不存在的旧页。

中文按字符测宽，英文按单词测宽，两种语言最后都进入同一分页过程。这样不是强迫中英文拥有相同页数，而是让各自的断行保持可读。

## 记录 447｜部分街机菜单切换中文时拿不到当前语言状态

本地化函数已经存在，公共模块也导出了 `translate` 和中文字体。后来检查多个街机菜单时，我发现它们还会直接调用 `is_chinese()` 判断是否使用中文专属布局。

这些页面通过 `from .common import *` 取得公共符号，但 `common.py` 当时没有显式导入并暴露 `is_chinese`。菜单代码写得正确，运行到中文分支时却可能出现名称不存在。

我把语言状态函数加入公共导入：

```python
from .localization import (
    contains_chinese,
    get_chinese_font,
    is_chinese,
    translate,
)
```

所有街机菜单从同一入口获得语言状态，不再各自碰运气依赖间接导入。

## 记录 448｜翻译文本和判断布局是两种不同需求

这次错误并不是某条翻译缺失。`translate()` 负责把键转换为当前语言文本，`is_chinese()` 则决定一页显示五行还是六行、标题使用什么倍率、按钮是否需要更大高度。

只测试翻译结果，不能保证布局分支能访问语言状态。我补充检查公共模块确实暴露 `is_chinese`，并让街机菜单在中英文状态下都走一遍绘制。

本地化不是一张字符串表，它还会改变界面的几何结构。

## 记录 449｜贪吃蛇中断恢复后，身体坐标从元组变成列表，碰撞检查无法建立集合

贪吃蛇运行时身体使用坐标元组：

```python
[(row, column), ...]
```

写入 JSON 后，元组会变成数组；读取回来就是 Python 列表。初版恢复直接执行：

```python
self.snake = restore_state["body"]
```

下一次生成食物或检查占用时需要 `set(self.snake)`，列表不可哈希，恢复局立即报错。

我在恢复入口统一规范化：

```python
self.snake = [tuple(segment) for segment in restore_state["body"]]
```

序列化格式和运行时结构不同，反序列化就必须主动恢复类型语义。

## 记录 450｜恢复贪吃蛇时不能无条件重新生成食物

修复身体类型时，我又看到 `_start_snake_game()` 在任何情况下都会调用 `_spawn_snake_food()`。这让快照虽然保存了原食物位置，继续游戏时却随机换成另一处。

中断恢复的目标不只是保持分数，还要保持玩家退出前看到的局面。我改为：

```python
if not restore_state or restored_food in self.snake:
    spawn_new_food()
```

正常新局生成食物；合法恢复局保留原位置；只有恢复数据中的食物与身体重叠时才重新选择安全位置。

## 记录 451｜结束的对局有时仍被保存成“可以继续”

中断存档建立时，系统主要关注玩家按 ESC 离开进行中的游戏。后来沿结束流程测试，我发现五子棋已经决出胜负，或扫雷已经踩雷、已经翻开全部安全格时，旧运行状态仍可能留在存档里。

再次进入菜单就会看到 Continue。点击后恢复的是一个已经完成的局面，玩家没有真正可以继续的操作。

我做了两层处理：五子棋确认胜负时立即清除运行状态；加载存档时再识别已经完成的快照并丢弃。扫雷通过“存在已揭开的雷”或“所有安全格已经揭开”判断完成，五子棋通过 `winner != 0` 判断。

Continue 只应代表一个仍然可以继续做决定的局面。

## 记录 452｜第一次清除运行状态，保存流程又把当前结束画面抓了回来

我最初在结束时调用 `_clear_run_state()`，它随后执行 `_save_now()`。但保存前的统一捕获逻辑会查看当前游戏状态，又把刚刚清除的结束局重新写回待保存数据。

流程变成：

```text
清除 run_state
  ↓
触发保存
  ↓
保存前捕获当前状态
  ↓
同一 run_state 被重新生成
```

我增加 `_run_state_save_suppressed`。清除某款游戏时，保存过程暂时跳过该游戏的捕获，并同时移除等待写入的快照；保存结束后再解除抑制。

这个 Bug 说明“先删再保存”并不总会得到空结果，还要检查保存入口是否会主动重建数据。

## 记录 453｜成就墙底部的分页按钮和返回提示开始互相争位置

成就数量增加后，墙面出现多页。底部既要显示已解锁数量和页码，又要放 PREV、NEXT 与 `ESC RETURN`。

第一次布局把返回提示塞在 footer 右侧，和 NEXT 按钮视觉上挤在同一区域。它们即使没有完全重叠，也让右下角像有两个互相竞争的操作入口。

我把 PREV 与 NEXT 缩到页脚边框内部，`ESC RETURN` 移到面板下方居中：

```text
[ PREV ]   UNLOCKED 18 / 60   1 / 2   [ NEXT ]

                       ESC RETURN
```

页脚负责分页与状态，面板外提示负责退出，两个层级不再混在一起。

## 记录 454｜这一阶段修复的共同点，是旧代码都默认“规模不会再变”

这些问题表面上彼此无关：世界数量写死、档案标签藏住、点击变量遗漏、长文本分页难看、界面版本冲突、坦克恢复菜单拥挤、中文状态未导出、贪吃蛇坐标类型改变、已结束对局还能继续、成就墙底部拥挤。

它们实际来自同一种开发阶段变化：项目已经从若干固定页面成长为会继续增加世界、语言、文本、进度和恢复状态的平台，过去只对一个规模成立的写法开始逐个失效。

这一轮没有用一次大重构掩盖所有问题。我沿真实故障逐项收紧边界：

```text
数量从注册数据生成
布局从实际矩形生成
交互复用同一布局结果
长文本拥有独立分页
工程版本与世界内文字分离
恢复菜单增加入口后仍保持信息层级
恢复入口规范化运行时类型
完成状态不能重新进入 Continue
公共控制各自占据清楚层级
```

MERIDIAN 到这里不只是内容更多了。它开始能够承受内容继续增加时带来的压力，同时也留下了可以被测试复现的修复路径，而不是靠我记住“这里以前好像坏过”。
