# 第二十部分：世界观写出来以后，我才发现故事也需要自己的系统

---

## 记录 293｜序章解决了第一次理解，却没有解决第二次阅读

七界序章加入以后，第一次进入游戏时的氛围明显完整了。但它被设计成只自动出现一次，看过以后，玩家没有入口主动重读。

器物本身的来历、七个世界的深入设定和已经读过的文本散落在开机、菜单与各游戏之间。如果继续往每个菜单上增加按钮，七款游戏都要维护自己的故事页，桌面也会越来越不统一。

我决定把世界观全部集中到一个独立系统中：桌面增加 `LORE`，进入后统一浏览 MERIDIAN 与七界内容。

---

## 记录 294｜档案不是玩家档案的另一个标签，而是独立的阅读应用

玩家档案记录成绩、时间和成就；世界档案记录器物与各界故事。两者信息类型完全不同。

如果把长篇故事塞进玩家档案第三个标签，统计滚动、成就列表和阅读分页会共享越来越复杂的状态。我让它成为桌面第二页上的独立图标，并分成两个页面状态：

```text
LORE_READER
  分类与条目列表

LORE_STORY
  单篇全文阅读
```

从列表进入正文，再回到原分类；从列表按 `ESC` 才返回桌面。阅读层级因此很清楚。

---

## 记录 295｜第一层分类不是按“人物、地点、事件”，而是按器物与七个世界

最初我考虑用传统资料库分类：人物、地点、事件、系统。但这样同一款游戏的内容会被拆到多个标签，玩家想连续了解雷原遗迹时需要来回切换。

我最终按连接来源分类：

```text
MERIDIAN
阴阳棋境
噬码渊
星穹壁垒
数灵海
雷原遗迹
筑天塔
守望者战线
```

设备本体是一个分类，七界各自一个分类。这个结构和桌面入口、序章世界 ID 完全一致，也让新增条目只需要归入对应世界。

---

## 记录 296｜器物分类先放三条基础记录，回答它是什么、怎样连接、为什么选择玩家

MERIDIAN 本身需要比开机提示更完整的说明。我先整理三条设备记录：

```text
器物起源 / The Device
  密封地窖中发现，没有制造者标记与可见能源，屏幕实际是共鸣透镜

连接之核 / The Nexus Link
  核心晶体维持各界平衡，开机过程实际是在校准共鸣

持器者 / The Keeper
  设备并非对所有人响应，能够看到内容的人已经被它选择
```

这三条共同解释外层系统，但不替七个世界讲各自的故事。

---

## 记录 297｜七个世界各自补充一条更深记录，不重复序章原文

序章只建立入口，档案正文应该进一步解释玩法背后的问题。我为每界整理一条独立主题：

```text
阴阳棋境   石语：黑白棋子的材质、频率与记忆
噬码渊     深层代码生态：灵蛇之外的数据生物与吞噬影响
星穹壁垒   砖块图书馆：每块能量砖保存了什么
数灵海     觉醒：数字从 2 到 4096 的意识变化
雷原遗迹   大战争：地雷为何比制造者存在得更久
筑天塔     发送者：方块来自哪里、消行是否是一种回应
守望者战线 主宰的本质：SOVEREIGN 如何从安全系统走向战争网络
```

档案不是把菜单文本复制得更长，而是回答序章留下的问题。

---

## 记录 298｜故事数据继续使用稳定 ID，显示文字与存档身份分开

每条记录使用统一结构：

```python
{
    "id": "tetris_sender",
    "game_id": "tetris",
    "title_en": "The Sender",
    "title_zh": "发送者",
    "content_en": [...],
    "content_zh": [...],
}
```

稳定 ID 用于查找和记录已读状态，标题可以调整或翻译。正文保留为段落列表，阅读器再根据屏幕宽度自动换行，不把显示行宽硬写进数据。

器物条目与游戏条目使用同一种结构，只是 `game_id` 使用设备分类标识。

---

## 记录 299｜我一开始保留了按统计解锁的条件，试玩后决定档案不再复制成就墙

早期数据结构支持这样的条件：

```text
always
stat:snake:best_score:40
achievement:air_campaign
```

最初设想是玩家成绩提高后逐渐解锁故事。真正放进系统后，我发现这会让世界档案变成第二面成就墙：玩家已经需要通过成就确认目标，又要猜为什么某段基础设定不能读。

我最终把阅读器规则改为“档案是世界资料，不是奖励系统”，现有条目全部可读。数据中的条件字段保留下来，便于表达条目来源，但界面不把故事正文当作通关奖励锁住。

这个决定减少了一层游戏化，却更符合“把世界观全部放在里面”的目的。

---

## 记录 300｜存档只记录已读与序章状态，不保存正文副本

档案内容来自代码定义，存档没有必要重复写入整段文本。我只保存轻量状态：

```python
lore = {
    "prologues_seen": [],
    "unlocked_entries": [],
    "read_entries": [],
}
```

`prologues_seen` 控制首次序章；`read_entries` 让列表区分未读与已读。`unlocked_entries` 作为结构兼容字段保留，但当前阅读器不会因为它缺少某个 ID 而隐藏正文。

打开条目时立即写入已读 ID。更改中文标题或补充正文不会让已经读过的身份失效。

---

## 记录 301｜分类、条目和正文各自维护索引，切换分类时必须重置后两层

阅读器有三个位置状态：当前分类、分类内条目、正文页码。

```python
lore_category_index
lore_entry_index
lore_reading_page
```

第一次切换分类时，我只改变分类索引，原分类如果选中第 3 条，新分类只有 1 条，条目索引就会越界。

我让每次切换分类都把条目索引和滚动值归零；开始阅读时页码归零；退出正文只返回列表，不清空分类。这样玩家能从同一位置继续浏览。

---

## 记录 302｜键盘与鼠标使用同一套层级，但动作含义不能混在一起

列表页支持：

```text
A / D 或左右键   切换世界分类
W / S 或上下键   选择条目
Enter / Space    进入正文
ESC              返回桌面
鼠标             点击分类或条目
```

正文页支持左右翻页，`Enter`、空格、`ESC` 或点击返回列表。

我没有让正文中的点击同时选择列表条目，也没有让列表页的左右键翻正文。每个状态只接受当前层级的动作，避免同一个按键在一次事件中被两个页面共同消费。

---

## 记录 303｜点击命中区必须由当前滚动位置推导，不能直接拿可见行号当数据索引

条目列表一次最多显示八行。当列表发生滚动时，画面第一行不再是数据中的第零项。

点击处理需要计算：

```python
entry_index = lore_scroll + visible_row
```

如果只使用 `visible_row`，滚动后点击第三行会打开最前面的第三条，而不是屏幕上真正看到的内容。

我让绘制与点击都使用同一个 `list_y`、行高、间距和 `visible_start`，并在索引进入数据前再次检查范围。

---

## 记录 304｜长英文按单词换行，中文必须按字符测量

故事正文不能直接按固定字符数截断。英文字母宽度不同，中文又没有空格作为天然断点。

我分别处理：

```text
英文
  逐词加入当前行，像素宽度超过面板后换行

中文
  逐字符加入当前行，按实际渲染宽度换行
```

标题如果仍然超过宽度，先降低像素倍率，再在极端情况下截断。正文使用中文字体渲染英文与中文，避免两种语言在同一档案里出现完全不同的字形质感。

---

## 记录 305｜正文按渲染后的十行分页，而不是按原始段落数量分页

一条数据中的一个段落可能在屏幕上换成三四行。若按原始段落分页，某页可能挤出面板，另一页又只剩很少内容。

我先把所有段落转换成实际显示行，在段落之间插入空行，然后每十行切成一页：

```python
start = reading_page * 10
page_lines = wrapped_lines[start:start + 10]
```

只有超过一页时才显示页码。左右翻页始终限制在零和最大页之间，不会翻到空白页。

---

## 记录 306｜八个分类标签刚好能排下，但标题、副标题和标签第一次发生了纵向拥挤

列表页顶部同时有 `LORE ARCHIVE`、说明文字和八个分类标签。初版标签位置过高，中文标题高度增加后，副标题与标签边框几乎贴在一起。

我重新划分固定区域：标题、说明、标签、条目列表、底部提示各占一段纵向空间。标签统一宽度，世界名过长时降低倍率或使用桌面短副标题。

背景使用深色渐变、金色标题与青色选择边框，保持它属于 MERIDIAN 系统，又和玩家档案的统计页面明显区分。

---

## 记录 307｜已读标记只改变列表提示，不应该把正文永久变暗

我最初让已读条目整体降低亮度，想表达“已经看过”。实际效果像条目失效或重新被锁定，玩家反而不愿再次打开。

最后未读与已读都保持可读标题，已读条目在右侧增加小型标记并使用不同强调色。选择与悬停仍然拥有更明显边框。

已读状态是导航辅助，不是完成后把故事藏起来。玩家随时可以重新打开任何条目。

---

## 记录 308｜空袭行动原来的章节故事继续留在游戏里，世界档案只负责更高层设定

空袭行动已经有自己的序章、八章故事和游戏内故事回看。如果把这些全部复制到全局档案，两个页面会显示相同内容，后续修改也容易不一致。

我把边界定为：

```text
空袭行动内部故事
  记录具体任务、章节推进和 WARDEN 的战役过程

MERIDIAN 世界档案
  记录守望者战线与 SOVEREIGN 的世界层背景
```

全局档案解释世界，游戏内故事解释事件。它们互相补充，但不复制。

---

## 记录 309｜无效条目 ID 不能让阅读器停在空白状态

正文页通过稳定 ID 查找内容。测试存档或开发过程中如果某个条目被改名，旧的 `reading_entry_id` 可能找不到定义。

我没有让绘制函数继续访问空对象，而是在查询失败时返回条目列表。已读列表中多出的旧 ID 也不会影响当前条目集合。

这使世界文本可以继续调整，同时避免一个失效引用让整个系统页面报错。

---

## 记录 310｜世界档案完成后，MERIDIAN 不再只靠第一次进入时的一段文字证明世界观存在

最终测试从桌面进入档案，依次检查八个分类、键盘和鼠标选择、长文本换行、正文分页、返回层级、语言切换与已读保存。

```text
第一次打开条目
  → 正文从第一页显示
  → ID 写入 read_entries

返回并再次打开
  → 分类位置保留
  → 条目仍可阅读

重启程序
  → 已读标记存在
  → 正文继续来自当前代码与当前语言
```

做到这里，世界观才从概念变成了系统：七款游戏拥有入口叙事，MERIDIAN 拥有自己的器物背景，所有内容又能在一个地方持续回看。

平台的框架已经能够接纳新的世界。接下来我想验证的，是它能不能承载一款与之前七款都不同、需要两名玩家同时参与的对战游戏。
