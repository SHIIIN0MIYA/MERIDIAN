# 第十三部分：一个文件已经装不下整台掌机，我开始拆分代码

---

## 记录 159｜真正推动拆分的不是某一次报错，而是每次修改都越来越不敢动

音频系统接入六款游戏以后，主程序继续同时承担开机、密码、桌面、转场、音频调用、六款游戏、公共动画和主循环。

问题已经不只是文件长。一次搜索 `settings`，会同时命中五子棋设置、贪吃蛇设置、打砖块设置和页面状态；搜索 `end`，会看到六款游戏的结束处理、关机流程和动画计时。很多变量都挂在同一个游戏对象上，只靠前缀区分属于谁。

我开始出现一种很明显的维护压力：修扫雷时会先确认自己没有碰到俄罗斯方块，调整桌面事件时又要担心分支顺序是否让某款游戏收不到输入。

代码仍然可以运行，但定位问题所需的阅读范围越来越大。单个功能明明只涉及几十行，我却经常需要在整个文件中来回确认初始化、事件、更新和绘制是否齐全。

这说明文件体量已经从“不方便”变成了实际技术债。我决定在继续增加内容以前先拆分结构。

---

## 记录 160｜我先把旧文件里的职责画出来，避免只按行数平均切块

如果只把一个大文件平均拆成几个小文件，很可能得到 `part1.py`、`part2.py` 和 `part3.py`，代码行数下降了，职责关系却没有变清楚。

我先按运行职责整理旧结构：

```text
HAOS_GAME_DECK.py
├── 窗口、颜色、字体、公共工具
├── 棋盘模型与粒子
├── 开机、密码、桌面、关机
├── 页面转场
├── 音频系统
├── 五子棋
├── 贪吃蛇
├── 打砖块
├── 2048
├── 扫雷
├── 俄罗斯方块
└── 事件循环、更新循环、绘制分发
```

真正自然的边界不是“每五百行一个文件”，而是某一组状态、事件、更新和绘制是否共同服务同一个功能。

我据此确定拆分原则：每款游戏拥有自己的模块；掌机外壳按照开机、桌面、密码和转场拆开；公共常量与基础模型单独存放；最外层只负责把这些部分组合起来。

## 记录 161｜我没有趁拆文件重写所有游戏，而是选择保留同一个运行对象

拆分时有两个方向。

一种是把六款游戏全部改成独立对象，每个对象定义统一的 `handle_event()`、`update()` 和 `draw()` 接口。长期看边界更干净，但这意味着同时重写状态访问、页面切换、字体、音频和公共动画，回归风险很高。

另一种是先使用 Mixin：把方法按职责移动到不同类中，最后仍由一个 `Game` 对象组合。各模块继续通过 `self` 使用共同屏幕、字体、音频和状态，只改变代码所在位置。

我选择第二种。

```python
class Game(
    ShellMixin,
    GomokuMixin,
    MinesMixin,
    Game2048Mixin,
    BreakoutMixin,
    SnakeMixin,
    TetrisMixin,
):
    pass
```

这不是最彻底的插件架构，但能够把结构风险限制在“方法有没有正确迁移”上，而不是在同一次改动里连对象关系和游戏规则一起推翻。

## 记录 162｜最外层启动文件最后只负责创建游戏并进入主循环

旧入口文件既是启动脚本，也是整个项目本体。拆分后，我希望双击或打包仍然只有一个明确入口，但入口不再存放具体玩法。

最终启动文件保留的内容很少：

```python
from haos_game_deck.common import *
from haos_game_deck.app import Game


if __name__ == "__main__":
    game = Game()
    game.run()
```

包的 `__init__.py` 只公开少数真正需要从外部访问的对象，例如 `Game`、棋盘模型、颜色集合和粒子。

这样做以后，入口文件不再因为增加一种碰撞、按钮或动画而变化。它的责任只有两件事：找到组合完成的游戏类，并启动它。

---

## 记录 163｜公共模块必须位于依赖关系最底部，否则拆分后很容易互相导入

把函数移动到多个文件后，第一个结构风险是循环导入。

例如五子棋需要窗口尺寸、颜色、字体渲染、缓动和 `Board`；桌面也需要窗口尺寸与颜色；主程序又要导入五子棋和桌面。如果这些基础内容仍然放在主程序里，各游戏模块就必须反过来导入主程序，形成互相等待。

我把不依赖具体游戏状态的内容放入 `common.py`：

```text
common.py
├── pygame 初始化与窗口常量
├── 颜色集合 C
├── 字体和像素文字绘制
├── 缓动、纹理与边框工具
├── Particle
└── Board
```

依赖方向固定为：

```text
common
  ↑
各游戏与掌机外壳
  ↑
app
  ↑
启动文件
```

只要公共模块不反向导入具体游戏，拆分后的包就不会因为加载顺序而找不到类。

---

## 记录 164｜每款游戏文件同时带走自己的状态、事件、更新和绘制

我没有只把“规则计算”移出去、继续把菜单和画面留在主文件。那样修改一款游戏时仍然要跨三个位置。

每个游戏模块都尽量形成纵向切片：

```text
gomoku.py
  _init_gomoku
  菜单与设置事件
  落子和胜负规则
  游戏、结束页和设置页绘制

snake.py
  _init_snake
  菜单、对局与结束事件
  移动、食物和碰撞
  蛇身与反馈绘制

……其余四款游戏使用相同边界
```

文件名不再只是代码分类，而是维护入口。以后出现“俄罗斯方块旋转后碰撞错误”，首先进入 `tetris.py`；“扫雷旗帜计数不对”则进入 `mines.py`，不需要先在整台掌机里过滤同名变量。

这次拆分没有做到每一行都绝对归属。五子棋的磁吸预览、连线、结束延迟、粒子与屏幕震动更新仍然保留在 `app.py` 的公共更新尾部，因为它们和主循环的全局动画顺序耦合最深。先保留这些代码，比在第一次拆分中强行搬走并改变更新顺序更安全，也成为之后仍可继续整理的边界。

## 记录 165｜掌机外壳也需要拆分，因为桌面并不是一个普通游戏

开机、密码、桌面和转场都属于掌机外壳，但它们的修改原因不同。

我把外壳拆成：

```text
shell_boot.py          开机、系统就绪、关机
shell_password.py      密码输入与错误反馈
shell_desktop.py       桌面图标、翻页和关机确认
shell_transitions.py   公共转场控制器与六种专属效果
shell.py               组合以上四个 Mixin
```

`shell.py` 本身只负责组合：

```python
class ShellMixin(
    BootMixin,
    DesktopMixin,
    PasswordMixin,
    TransitionMixin,
):
    pass
```

这样修改密码抖动时不需要翻过整段桌面图标绘制，增加转场效果也不会把开机计时器混进同一个区域。

## 记录 166｜音频系统独立成模块以后，游戏只保留事件名称

程序化音频本身包含采样生成、波形、曲目缓存、状态映射、双声道淡化和短音效构建。如果继续放在主程序里，它会成为另一个体量很大的公共区域。

我把它完整移动到 `audio.py`，对外只保留 `AudioManager`。

```text
audio.py
├── 波形与 PCM 生成
├── 主旋律和六款变奏
├── 短音效构建
├── 曲目缓存
└── AudioManager
```

各游戏模块继续写 `self.audio.play("breakout_brick")`，但不需要导入采样率或音符表。主程序只在初始化时创建一次音频管理器，并在更新循环同步页面状态。

音频的拆分也验证了职责边界是否有效：一套系统如果只能依附在巨型主文件里运行，说明它还没有真正形成接口。

## 记录 167｜`Game` 仍然是唯一运行实例，但初始化必须显式调用每个模块

Mixin 不会自动执行自己的初始化方法。把类写进继承列表以后，如果忘记调用 `_init_snake()`，蛇的事件方法虽然存在，第一次打开时却会缺少分数、位置和计时器。

我在 `Game.__init__()` 中明确列出初始化顺序：

```python
self._init_transition()
self._init_boot()
self._init_desktop()
self._init_password()
self._init_gomoku()
self._init_snake()
self._init_breakout()
self._init_2048()
self._init_mines()
self._init_tetris_state()
```

第一次迁移时，最容易出现的不是语法错误，而是某一模块方法已经移动，初始化字段却还留在旧位置，或者新的 `_init_*()` 没有加入列表。程序能启动，直到玩家打开特定游戏才报属性不存在。

我因此把“六款游戏能否分别开始一次”列为结构重构后的首要冒烟测试，而不是只验证桌面能够出现。

## 记录 168｜主循环不再堆积长串 `if state == ...`，改为三张状态分发表

拆分文件后，主程序仍然需要决定当前由哪个模块处理输入、更新和绘制。如果继续写越来越长的条件链，每增加一个页面都要在三处插入分支，而且顺序错误可能让两个页面逻辑同时执行。

我建立三张映射：

```python
EVENT_DISPATCH = {
    DESKTOP: "_handle_desktop_event",
    SNAKE_PLAYING: "_handle_snake_playing_event",
    TETRIS_END: "_handle_tetris_end_event",
}

UPDATE_DISPATCH = {
    SNAKE_PLAYING: ["_update_snake", "_update_snake_visual_effects"],
    TETRIS_PLAYING: ["_update_tetris"],
}

DRAW_DISPATCH = {
    DESKTOP: "_draw_desktop",
    SNAKE_PLAYING: "_draw_snake_game",
    TETRIS_END: "_draw_tetris_end",
}
```

主循环只根据当前 `state` 取出方法名并调用。状态常量仍然集中在 `Game` 中，具体实现则分散到各自模块。

## 记录 169｜只移动函数、不补齐分发表，会出现“能操作但不更新”或“在运行却没画面”

分发表让主循环更短，也带来一种新的遗漏方式。

一个页面需要三类连接：事件、更新和绘制。迁移时如果只把事件处理加入表，按钮可能能够修改状态，但动画不推进；只加入更新和绘制，页面看起来在运行，键盘却完全没有反应。

我把检查方式改成逐状态核对：

```text
状态常量是否存在
  → EVENT_DISPATCH 是否有事件入口
  → UPDATE_DISPATCH 是否列出需要的更新
  → DRAW_DISPATCH 是否有绘制入口
  → 初始化方法是否准备了这些入口访问的字段
```

对没有更新需求的静态页面，我也明确记录为空列表，而不是依靠“没写所以应该没事”。这样看到映射时可以区分“有意不更新”和“迁移时漏掉”。

## 记录 170｜物理拆分完成了，但模块之间仍共享 `self`，我没有把它伪装成完全解耦

Mixin 方案保留了大量共享状态。五子棋模块可以访问 `self.screen`、`self.audio` 和 `self.state`；桌面也能访问同一个对象上的动画、按钮和游戏状态。

这意味着拆分解决了定位与维护范围，却没有把六款游戏变成可以单独实例化的插件。

公共导入仍然比较宽：

```python
from .common import *
```

它减少了迁移时逐项调整名称的风险，但也让每个模块可以看到比自己真正需要更多的公共对象。我把这视为保留下来的技术债，而不是把“文件变多”直接等同于“架构完全解耦”。

这一阶段的目标是先让代码按职责可读、可维护，并保证玩法行为不变。更严格的接口和更小的依赖范围可以以后继续收紧，但不应该与第一次拆分同时进行。

## 记录 171｜重构后的测试重点是行为没有变化，而不是新目录看起来是否整齐

文件能够成功导入只说明路径和语法基本正确，不能证明拆分没有改变游戏。

我给重构后的验证分成几层：

```text
启动层
  入口能够创建 Game，开机流程正常开始

页面层
  桌面、六款菜单、六款对局和结束页可以绘制

规则层
  2048 压缩合并结果不变
  扫雷首击与翻格逻辑不变
  俄罗斯方块暂存、旋转与消行不变

导航层
  每款游戏能够进入自己的 PLAYING 状态
  ESC、菜单和桌面返回仍到达原目标

系统层
  音乐仍根据页面状态切换
  转场期间仍然阻止输入
```

我还会先启动一款游戏、返回桌面，再立即打开另一款，确认拆分后没有让隐藏模块继续更新。

## 记录 172｜拆分完成后的结构第一次能够直接表达项目是什么

最终结构不再是一条很长的源文件，而是：

```text
HAOS_GAME_DECK.py

haos_game_deck/
├── __init__.py
├── app.py
├── common.py
├── audio.py
├── shell.py
├── shell_boot.py
├── shell_password.py
├── shell_desktop.py
├── shell_transitions.py
├── gomoku.py
├── snake.py
├── breakout.py
├── g2048.py
├── mines.py
└── tetris.py
```

`app.py` 仍然是组合中心，但它主要保留状态、初始化顺序、三张分发表和主循环；每款游戏的完整实现已经拥有明确位置。

这次更新没有增加新游戏，也没有修改胜负规则。它的结果主要体现在后续维护方式上：要修改某款游戏时，不再先面对整台掌机；要增加一个外层系统时，也不需要把代码继续塞进已经失去边界的单文件。

项目仍然共享一个运行对象，但第一次拥有了可以继续扩展的目录结构。
