# 第十一部分：我开始给六款游戏分别设计从桌面打开的方式

---

## 记录 123｜开机和关机补完整以后，中间这段“打开游戏”的跳切反而更明显了

开机、解锁和关机流程完成后，我重新从头使用了一遍掌机。

这一次最不自然的地方不再是程序怎样开始和结束，而是点击桌面图标以后发生的事：鼠标刚松开，桌面就立刻消失，下一帧直接变成游戏菜单；按下返回时也是一样，游戏菜单瞬间被桌面替换。

单独看两张页面都没有明显问题。桌面有掌机外壳、状态区域和软件图标，各款游戏也有自己的开始界面。但它们之间没有任何连接过程，感觉更像在同一个窗口里轮流显示几张互不相关的画面。

这个问题在开机系统完成后变得更突出。玩家已经看过屏幕亮起、系统准备和密码解锁，进入桌面时有完整的过程；真正打开一个游戏时却只剩一次生硬跳切，前后体验的完成度不在同一个层级。

我暂时没有继续调整游戏规则，而是把这一阶段的目标定为：让桌面和六款游戏之间的切换也成为掌机体验的一部分。

---

## 记录 124｜第一版先只做统一淡出，确认“切换过程”本身是否必要

我没有一开始就给六款游戏分别画复杂动画，而是先做了最简单的黑色淡出。

点击图标后，当前页面逐渐被黑色遮住；画面全黑时切换到目标页面，再让黑色遮罩逐渐消失。最基础的绘制只有一层带透明度的表面：

```python
overlay = Surface((window_width, window_height), SRCALPHA)
overlay.fill((0, 0, 0, transition_alpha))
screen.blit(overlay, (0, 0))
```

这版没有游戏主题，也没有额外图形，目的只是验证两个问题：

- 页面不直接跳切以后，玩家能不能更清楚地感受到自己完成了一次“打开软件”；
- 过渡会不会拖慢进入游戏的节奏。

实际试玩后，淡出确实解决了最明显的割裂。桌面不再凭空消失，游戏菜单也不再突然顶替前一张画面。只要时间控制得足够短，它不会像加载页面一样让人等待。

但这只是证明转场值得做，还没有解决每款游戏之间缺少区别的问题。

## 记录 125｜我把转场做成独立状态，没有让每个图标各自管理计时

六个桌面图标都会触发页面切换。如果直接在每个点击分支里写一套透明度和计时，后面调整速度、阻止重复点击或修改切换时机时，就要同时维护六份相似逻辑。

我把转场需要的公共信息集中到一组状态中：

```python
transition_active = False
transition_type = "fade"
transition_target_state = None
transition_frame = 0
transition_max_frames = 24
transition_phase = "out"
transition_alpha = 0
```

图标点击时不再立刻改变页面，只提交三个信息：要去哪里、使用哪种效果、整个过程持续多少帧。

```python
start_transition(target_state, transition_type, frames)
```

公共更新逻辑只负责推进帧数和切换阶段，公共绘制入口再根据 `transition_type` 选择具体动画。这样六款游戏可以拥有不同的外观，但共享同一套开始、切页和结束规则。

这一步最重要的不是少写了多少代码，而是把“页面切换”从图标点击的附带结果，变成了可以单独检查的一段流程。

---

## 记录 126｜真正的页面切换不能发生在动画开始时，必须等遮罩完全盖住旧页面

转场有两个方向：先覆盖当前页面，再揭开目标页面。

```text
out 阶段：桌面仍然存在，转场图形逐步覆盖屏幕
                     ↓
                覆盖达到 100%
                     ↓
              把 state 切换到游戏菜单
                     ↓
in 阶段：目标页面已经存在，转场图形反向离开屏幕
```

如果点击图标时就立刻修改 `state`，随后才开始播放淡出，玩家会先看到游戏菜单突然出现，再看见它被黑色遮住。动画虽然运行了，却没有掩盖跳切，反而把错误顺序完整展示出来。

所以我把真正的状态替换放在两个阶段的交界处：

```python
if transition_phase == "out" and transition_frame >= half:
    state = transition_target_state
    transition_phase = "in"
    transition_frame = 0
```

到达中点时，旧页面已经被完全覆盖。状态在这一帧下面完成替换，但玩家看不见；接着遮罩打开，露出来的已经是目标页面。

测试这部分时，我不只看动画是否流畅，还会逐帧注意中点附近有没有出现桌面和游戏菜单重叠、闪白或提前露出的缝隙。转场能不能成立，关键就在这次不可见的状态交换。

## 记录 127｜转场播放期间继续接收输入，会让一次点击跨过两张页面

第一次把页面切换包进动画后，我又检查了快速点击和连续按键。

转场持续时间虽然不到一秒，但事件循环仍然每帧接收鼠标和键盘输入。如果玩家点击图标后马上再次点击，第二次点击可能发生在桌面被遮住时，却在中点切页以后落到游戏菜单上。一次打开游戏的动作，就可能连带按下菜单里的开始按钮。

键盘也有同样的问题。转场尚未结束时按下 `ESC`，有可能被旧页面当作返回，也可能在目标页面出现后被重新解释。玩家看到的只是一段动画，程序内部却已经连续执行了两次导航。

我给事件入口增加了统一限制：

```python
for event in events:
    if transition_active:
        continue
    handle_current_page_event(event)
```

转场开始后，旧页面和目标页面都暂时不接收新的操作；动画结束，输入权才交给已经完全显示的页面。

我随后连续点击同一个图标、在动画中点击原本属于菜单按钮的位置，并快速敲击 `ESC`。预期结果都只有一个：完成当前切换，不顺带执行下一张页面的动作。

---

## 记录 128｜统一淡出解决了跳切，却让六款游戏更像同一个程序换了六张皮肤

公共淡出运行稳定以后，我连续打开了六款游戏。

功能上已经比直接切页自然，但每次操作的节奏完全相同：点击图标、屏幕变黑、游戏菜单出现。五子棋、贪吃蛇和俄罗斯方块的规则差异很大，离开桌面的方式却没有任何区别。

这带来了另一个体验问题。桌面图标有不同造型，各游戏菜单也有不同配色，可中间的黑屏把两边的识别信息全部切断。玩家知道自己打开了一个程序，却无法从动作本身感受到打开的是哪一个。

我没有删除统一淡出。它仍然适合不需要强调身份的普通页面切换，也可以在某个专属效果无法识别时作为保底方案。但从桌面进入游戏这一级切换，需要比黑屏更明确。

因此我决定保留公共转场控制器，只替换从桌面打开游戏时绘制的内容：六款游戏分别使用自己的视觉语言，状态切换规则仍然保持一致。

## 记录 129｜专属转场不能只是把游戏图标放大，我先定了四条限制

如果点击图标后只把同一个图标放大到全屏，确实能区分游戏，但它更像启动页插图，不像一次正在发生的动作。

我给专属转场定了四条限制：

```text
1. 不依赖游戏名称，单看运动方式也应该能认出玩法
2. 到达转场中点时必须完全遮住屏幕，保证状态切换不可见
3. 每一帧的图形位置必须连续，不能因为重新随机而跳动
4. 只使用玩法符号，不读取当前对局，避免转场泄露或伪造游戏状态
```

最后一条尤其重要。扫雷转场不能显示真实地雷位置，2048 转场也不能拼出一盘看似可以继续操作的数字。它们应该让玩家联想到游戏，而不是假装自己就是一局游戏。

我也没有把这类大转场塞进每一次重新开始、暂停和结算。它主要负责从桌面打开游戏菜单这一层边界；游戏内部较短的页面变化仍然使用更轻的处理。否则每次重开一局都播放接近一秒的主题动画，辨识度会变成重复等待。

## 记录 130｜五子棋转场没有铺满棋子，而是让棋盘色块沿对角线闭合

五子棋最容易想到的符号是黑白棋子。但如果屏幕上突然铺满棋子，很像某一局已经结束的棋盘，也容易让人误以为这些落子具有真实胜负关系。

我最后选择表现棋盘本身。整个窗口被拆成 16 列、9 行，每个区域使用两种棋盘色交替绘制，再加一层深色描边。色块不是同时出现，而是根据行列之和依次启动：

```python
delay = ((row + column) / max_diagonal) * 0.45
local_t = clamp((t - delay) / 0.55, 0.0, 1.0)
```

左上角最先闭合，右下角最后跟上。这样仍然是一张棋盘，却带有明确的推进方向，不会像普通马赛克遮罩一样整齐缩放。

每块色板的尺寸使用带轻微回弹的缓动，最大允许超过目标尺寸约 15%，随后再落回完整大小。这个过冲很小，但能延续五子棋落子时先吸附、再稳定下来的手感。

进入游戏时，棋盘色块一格格盖住桌面；离开覆盖层时，顺序反过来，游戏菜单从同一张棋盘结构下面被揭开。

---

## 记录 131｜五子棋色块有回弹以后，我又处理了边缘露缝和最后一格到达太晚的问题

这类分块转场最危险的地方不是中间，而是窗口最右侧和最下方。如果直接使用整数除法计算格子宽高，16 份宽度相加可能小于窗口宽度，最边缘会留下一条没有被遮住的细线。

我把单格尺寸改成向上取整，并让绘制矩形额外多出少量像素：

```python
cell_w = ceil(window_width / 16)
cell_h = ceil(window_height / 9)
rect = Rect(x, y, width + 2, height + 2)
```

多出来的部分会和相邻格重叠，不会在中点留下桌面残影。

另一个要检查的是错峰时间。对角线延迟虽然让运动更清楚，但延迟过大时，右下角还没长满，公共控制器就已经准备切换页面。最后我把延迟只占整个覆盖进度的 45%，剩余 55% 留给最晚出现的色块完成回弹。

测试时我重点盯着右下角和窗口四边，并反复从桌面进入、再返回桌面。只有所有格子都在状态交换前完成覆盖，这个对角线节奏才不会破坏公共转场的中点规则。

## 记录 132｜贪吃蛇转场不是一条直线扫过，而是让蛇真正走遍屏幕

贪吃蛇如果只用一条绿色横线从左扫到右，虽然颜色正确，却无法表现转向和连续移动。它和普通扫描线的区别太小。

我先用 28 像素作为一个移动单元，在屏幕外侧多留几行、几列，然后生成一条蛇形路径：偶数行从左向右，奇数行从右向左。

```python
for row in range(rows):
    if row % 2 == 0:
        append_cells_left_to_right(row)
    else:
        append_cells_right_to_left(row)
```

随着进度增加，路径前方的位置不断推进，屏幕上只保留一段会增长的蛇身。蛇长从约 18 格逐渐增加到约 64 格；靠近尾部使用阴影色，中段使用身体色，最前方换成更亮的头部色。

蛇头额外扩大描边，并根据当前行的移动方向调整两枚小眼睛的位置。这样即使整个画面很快，仍能看出它正在左右折返，而不是一串没有方向的方块。

蛇身走过的位置会逐步留下深色网格，转场因此既有移动主体，也有持续累积的覆盖结果。

---

## 记录 133｜只有一条蛇在移动时，中点仍会留下大量空白，我补上了最后 22% 的封屏过程

贪吃蛇路径已经能识别，但第一次按“蛇身本身负责遮屏”的思路计算时，出现了结构性问题：为了让头尾都看得清，蛇不能长到覆盖整张屏幕；如果只画当前蛇身，中点一定会留下大量可以看见旧页面的空格。

我没有把蛇无限拉长，而是让走过较久的区域沉淀为深色格子。蛇继续前进，后方逐渐变成已经占领的网格。

即便如此，路径末端仍可能因为错位和屏幕边缘留下小块空隙。所以当进度超过 78% 后，我再加入一层完成覆盖：

```python
if t > 0.78:
    finish_t = (t - 0.78) / 0.22
    draw_dark_fill(finish_t)
    draw_full_grid(finish_t)
```

这 22% 不是突然盖上一张纯色图。深色底层逐渐增强，同时横纵网格线跟着显现，最后仍然保持贪吃蛇的棋盘结构。

我测试了蛇头刚进入下一行、蛇头位于窗口外缘以及进度接近 100% 的画面。最终目标不是让每一格都真的被蛇身体踩中，而是让“蛇走过屏幕”的视觉逻辑与“中点必须完全遮住”的技术要求同时成立。

## 记录 134｜打砖块转场先让砖块从上方落下，但只画砖块时很容易和五子棋混在一起

打砖块的第一层识别来自砖墙。我使用约 86×34 像素的长方形砖块，从屏幕上方分行落下。

每一块的启动时间同时参考行和列，但行的权重更高：

```python
delay = (row * 0.75 + column * 0.18) / max_distance * 0.42
```

这样整体运动主要从上向下，又带一点斜向错峰。砖块使用紫色、橙色、蓝色和亮色交替排列，内部保留一条短高光；落到目标位置时同样有很轻的回弹。

只做到这里时，转场已经像一面彩色砖墙，却仍然可能被看成另一种分块遮罩。五子棋也是很多矩形逐步铺满屏幕，两者只有比例和颜色不同，玩法动作还没有真正出现。

我给砖墙补了一颗运动中的球。它不从第一帧出现，而是在进度超过 18% 后才从左向右穿过屏幕，纵向位置沿正弦曲线上下摆动。玩家先看见可碰撞的砖块形成，再看见球在其中穿行，打砖块的关系才建立起来。

---

## 记录 135｜打砖块的球不能在空屏上漂，砖墙也不能刚好只铺到窗口边缘

调整打砖块转场时，我主要处理了两个细节。

第一是球出现的时机。如果球从动画第一帧就开始移动，它前面还没有任何砖块，画面看起来只是一个黄色圆点划过桌面。把球延后到 18% 以后，背景中已经有几排砖落下，它的运动才有明确对象。

球的横向位置使用整个窗口宽度，纵向围绕屏幕约 35% 的高度上下摆动：

```python
ball_x = window_width * ball_t
ball_y = window_height * 0.35 + sin(ball_t * tau * 2.5) * 120
```

第二是砖墙覆盖范围。只按可见窗口计算列数和行数时，最左侧半块偏移、回弹缩放和砖间缝隙会让四周露出旧页面。我在正常计算结果之外多生成两行、两列，并让第一列从半块砖的负坐标开始。

多出来的砖大部分位于屏幕外，但它们保证整面墙下落完成时，窗口四边不会因为整除误差或间距出现亮缝。测试时我把注意力放在球经过边缘的一刻，确认运动主体不会把遮罩边界的问题掩盖过去。

## 记录 136｜2048 也使用方块，但我让它从中心向外扩张，并且没有写任何数字

2048 和五子棋、打砖块一样都可以用规则排列的矩形表示。如果继续使用从左上到右下的顺序，它们只会变成三套换色后的同类动画。

我把 2048 的传播起点放在屏幕中心。窗口以 80 像素为一个方块单位，每块根据自己到中心的距离决定延迟：越靠近中心越早放大，越靠近四角越晚出现。

```python
distance = hypot(row - center_row, column - center_column)
delay = (distance / max_distance) * 0.42
```

方块使用从低值到较高值的六种棋子颜色循环排列，尺寸从零开始放大，最大只轻微超过目标尺寸约 10%，再稳定到完整网格。

我没有在方块上绘制 `2`、`4`、`8` 等数字。转场中的格子并不属于真实对局，如果放上数字，就会形成一盘看似有合并关系、实际却不能操作的假棋局；快速变化的几十个数字也只会增加视觉噪声。

保留颜色和由中心向外扩张的运动，已经足以让人想到数字方块不断出现和占满棋盘，同时与五子棋的对角闭合、打砖块的向下坠落区分开。

## 记录 137｜扫雷转场没有使用真实棋盘，我改用雷达、目标点和低空烟雾表达危险区域

扫雷最直接的专属元素是地雷，但在转场里铺一张真实格盘会带来问题：玩家可能把标记位置理解为游戏提示，甚至误以为转场提前展示了下一局雷区。

我把它改成一张象征性的探测画面。深色面板先压低原页面亮度，屏幕中心向外扩张四圈雷达环，一条带有 18 层残影的扫描线持续旋转；七个预设目标点按顺序出现，并在红色和亮色之间闪烁。

```text
深色覆盖
   + 四层扩张雷达环
   + 旋转扫描线及衰减残影
   + 七个延迟出现的危险标记
   + 缓慢漂移的矩形烟雾
```

这些标记使用固定的屏幕比例坐标，只承担危险提示的视觉作用，不读取扫雷棋盘，也不会与下一局地雷位置发生关系。

烟雾没有做成细致粒子，而是使用许多透明度较低、大小不同的矩形色块。它们在深色背景上形成低空遮蔽，又能保持整套掌机界面的像素化边缘。

## 记录 138｜扫雷烟雾和俄罗斯方块都需要随机分布，但“每帧重新随机”会让物体瞬移

转场中的烟雾需要看起来分散，俄罗斯方块也不能每次整齐排成几列，所以两者都要使用随机位置。

但动画绘制函数每帧都会重新执行。如果每次调用都从一个不断变化的随机序列中取坐标，同一团烟雾上一帧还在左侧，下一帧就会跳到右上角。那不是漂移，而是整张画面在闪烁。

我给扫雷转场使用固定随机种子 `2026`。每一帧重新计算时，相同编号的烟雾都会得到相同的基础位置、尺寸和透明度；真正的移动只来自连续变化的动画计时：

```python
rng = Random(2026)
base_x = rng.randint(-80, window_width + 40)
drift = sin(animation_tick * 0.03 + index) * 18
x = base_x + drift
```

这样随机只负责生成构图，正弦偏移负责生成运动。烟雾会缓慢左右漂动，而不是每帧换一批位置。

我反复暂停观察同一目标点附近的烟雾，确认它的大小和纵向位置保持稳定，再继续播放检查横向漂移是否连续。随机效果只要进入逐帧动画，就必须区分“随机生成一次”和“每一帧随机一次”。

## 记录 139｜俄罗斯方块转场需要真正从上方落下来，所以它的时间比其他游戏更长

俄罗斯方块的核心动作不是格子出现，而是方块从上向下落。我生成了 42 组四格图形，让它们从窗口上方分批进入。

颜色循环使用七种方块配色，但轮廓没有强行把七种标准形状全部塞进一张快速动画。为了控制密度和识别度，我主要使用正方形与带拐角的四格轮廓，再根据进度交换横纵坐标，形成简化旋转。

```python
shape = square_offsets if index % 3 == 0 else hook_offsets
angle = int(local_t * 3) % 4

cell_x = x + (offset_y if angle % 2 else offset_x) * 30
cell_y = y + (offset_x if angle % 2 else offset_y) * 30
```

每组图形先在屏幕上方等待，根据编号错开启动时间，再用三次缓出落到窗口下半部分或屏幕外。开始时速度明显，接近目标位置时逐渐稳定，不会像匀速下雨。

这套动画同样使用固定随机种子 `425`。每块的横向位置和目标高度在不同帧中保持一致，只有下落进度与简化旋转连续变化。

因为方块需要走完一段真实的纵向距离，如果硬压到和五子棋一样快，只能看到屏幕突然多出很多彩色格子。我最终给它留下六款游戏中最长的转场时间，让“下落”能够被看清。

## 记录 140｜六个效果不能机械地使用同一帧数，我按运动距离重新调整节奏

专属动画全部接入后，我先尝试用同一个持续时间播放。结果五子棋和 2048 的分块扩张显得拖沓，俄罗斯方块和贪吃蛇却来不及完成主要动作。

原因是它们虽然共享同一套 `out → 切页 → in` 结构，画面里的运动距离完全不同：

```python
transition_effects = {
    "gomoku": "gomoku_grid",
    "snake": "snake_scan",
    "breakout": "breakout_bricks",
    "2048": "g2048_tiles",
    "mines": "mines_radar",
    "tetris": "tetris_drop",
}
```

```text
五子棋       44 帧   对角线色块闭合
贪吃蛇       50 帧   蛇形路径推进并完成封屏
打砖块       48 帧   砖墙下落，同时让球穿过
2048         44 帧   从中心向四角扩张
扫雷         50 帧   雷达扩散、扫描和目标出现
俄罗斯方块   58 帧   方块从屏幕上方完成较长距离下落
```

这些数值包括覆盖和揭开两个阶段，不是让玩家在黑屏上等待相同长度。短动画主要依靠错峰和回弹产生节奏，长动画则要给路径移动与坠落留下可辨认的时间。

我连续切换六款游戏，重点比较的不是哪一个“更炫”，而是点击后多久能理解动作、什么时候开始觉得在等待。最后保留不同帧数，让公共系统统一切换规则，不强迫所有视觉内容使用同一种速度。

## 记录 141｜专属转场第一次完成后只用在进入游戏，返回桌面仍然是普通淡出

六个桌面图标都接入专属效果后，我按最初的测试习惯只检查了“点击图标能不能正确打开游戏”。这一方向没有问题。

真正完整走一次路径时，新的不一致马上出现：进入五子棋时棋盘格沿对角线闭合，按返回后却只是屏幕变黑；进入贪吃蛇时蛇走过整个屏幕，离开时同样退回普通淡出。

```text
桌面 → 五子棋：棋盘格转场
五子棋 → 桌面：黑色淡出

桌面 → 贪吃蛇：蛇形扫描
贪吃蛇 → 桌面：黑色淡出
```

功能上返回完全正确，但体验像只做了半套。专属动画被理解为游戏的“开场表演”，没有成为桌面与该游戏之间稳定的连接方式。

这个问题也暴露了原来的测试盲区：只验证入口，会认为六个效果都已经完成；把进入和退出当成一对动作，才会发现另一半仍然留在统一淡出的旧方案里。

## 记录 142｜返回桌面虽然仍用淡出，但返回前必须清掉上一款游戏的临时视觉状态

这一版的公共返回入口仍然固定使用黑色淡出：

```python
start_transition(DESKTOP, "fade")
```

专属效果只在点击桌面图标、打开相应游戏时触发。返回方向还没有保存“刚才打开的是哪款游戏”，所以公共函数无法自动选择对应效果。

不过返回不能只提交一个桌面目标。在开始淡出前，我会清理当前游戏留下的临时视觉状态，包括粒子、涟漪、无效落子标记、撤销动画、屏幕震动、预览棋子、悬停位置和仍处于按下状态的按钮。

这些内容在桌面上不会继续绘制，但如果不清理，下一次重新进入同一游戏时可能突然恢复旧预览或残留动画。淡出负责把游戏画面交还给桌面，清理步骤则确认上一段交互已经真正结束。

这也让我把两个问题分开看：返回能不能稳定结束当前游戏，是状态清理问题；进入和返回是否拥有对称的专属动画，是转场识别问题。前者已经处理，后者仍然保留在待调整项里。

## 记录 143｜最后一次测试不再只看动画，而是检查转场前后有没有多执行一次操作

这一阶段的完整测试路径变成了：

```text
进入桌面
   → 打开五子棋，检查棋盘格是否完全盖住屏幕
   → 在转场中连续点击并按 ESC
   → 确认只到达五子棋菜单，没有顺带开始对局
   → 返回桌面，确认黑色淡出能够正常结束且不残留临时状态
   → 再次打开，确认没有残留预览和按钮按下状态
   → 对其余五款游戏重复相同过程
```

我还分别检查了每种效果最容易出问题的位置：五子棋的右下角是否晚到，贪吃蛇最后封屏时是否露格，打砖块四周是否有缝，2048 四个角能否在中点前长满，扫雷烟雾会不会逐帧跳动，俄罗斯方块会不会因为下落过快只剩杂乱色块。

全部走完后，六款游戏的规则和菜单内容没有改变，桌面也没有增加新的软件。变化发生在玩家过去很容易忽略的一小段时间里：从按下图标到真正看见游戏。

统一转场控制器保证切页在完全覆盖时发生，也阻止输入跨越页面；六种专属动画则让相同的打开操作保留各自玩法的身份。到这里，打开游戏不再只是程序把 `state` 换成另一个值，而更像掌机真的启动了一款软件。

返回桌面仍然使用普通淡出，这一处不对称没有被写成已经解决的问题。它是这轮测试留下的明确缺口：专属进入已经成立，但“同一款游戏应该怎样离开”还没有进入统一方案。
