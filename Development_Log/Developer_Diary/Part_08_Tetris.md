# 第八部分：状态最多的一款游戏——俄罗斯方块

---

## 记录 83｜这次要同时处理下落、旋转、预览、暂存和消行

扫雷完成以后，我决定继续做俄罗斯方块。

前面的游戏通常只有一个主要对象或一张固定棋盘。俄罗斯方块则需要同时保存已经锁定的方块、正在下落的方块、下一块、暂存块、分数、行数、等级、下落计时和暂停状态。

它看起来仍然是一个网格游戏，但规则组合比贪吃蛇和 2048 更复杂：移动与自动下落同时发生，旋转后还要重新做碰撞判断，方块落地后才能进入棋盘，满行又会改变所有上方数据的位置。

我先把开发顺序拆开：

```text
七种方块与旋转形状
   ↓
棋盘碰撞与自动下落
   ↓
锁定和消行
   ↓
软降、硬降和等级速度
   ↓
NEXT、HOLD、落点预览
   ↓
暂停、结束和桌面接入
```

## 记录 84｜可见棋盘是 10×20，内部再多保留两行

俄罗斯方块使用 10 列、20 行的标准可见区域，每格 25 像素，所以游戏区域为 `250×500`。

```python
TETRIS_COLS = 10
TETRIS_VISIBLE_ROWS = 20
TETRIS_HIDDEN_ROWS = 2
TETRIS_ROWS = 22
TETRIS_CELL = 25
```

内部棋盘实际保存 22 行。最上面的两行不直接绘制，用来容纳刚生成、还没有完全进入可见区域的方块。

绘制时使用：

```python
visible_row = internal_row - TETRIS_HIDDEN_ROWS
```

只有 `visible_row >= 0` 的格子才出现在屏幕上。

如果只保存可见的 20 行，长条或旋转后的方块刚生成时容易被迫完全塞进第一行，顶部碰撞会显得很拥挤。隐藏行给生成和旋转留下缓冲，也让“方块堆到顶端”可以由内部碰撞统一判断。

## 记录 85｜七种方块的旋转不能在运行时临时猜

我为 `I、O、T、S、Z、J、L` 七种方块分别写出四种旋转状态。每种状态都由四个相对坐标组成：

```python
"T": (
    ((1, 0), (0, 1), (1, 1), (2, 1)),
    ((1, 0), (1, 1), (2, 1), (1, 2)),
    ((0, 1), (1, 1), (2, 1), (1, 2)),
    ((1, 0), (0, 1), (1, 1), (1, 2)),
)
```

`O` 方块旋转后外形不变，因此四个状态使用同一组坐标。其他方块则显式保存每个方向，不在运行时用矩阵公式临时旋转。

这样数据虽然多一些，但每一种结果都可以直接检查。碰撞、预览、暂存卡片和游戏图标也都能读取同一份形状表。

每种方块拥有独立颜色。棋盘中不只保存“这个位置被占用”，而是保存占用它的方块种类，绘制时再从种类映射到颜色。

## 记录 86｜完全随机会长时间不给某一种方块

最初每次都从七种方块中独立随机。试玩时可能连续出现很多相同方块，也可能很久都等不到长条 `I`，已经留好的四格空位只能一直被迫等待。

我改成七袋随机：

```python
if not bag:
    bag = ["I", "O", "T", "S", "Z", "J", "L"]
    random.shuffle(bag)

kind = bag.pop()
```

每一袋一定包含七种方块各一次，只是顺序不同。取完以后再重新打乱下一袋。

这不能保证玩家想要的方块立刻出现，但可以保证任意一种方块不会无限期缺席。`NEXT` 预览也从同一袋中提前取值，不能为了显示下一块另外做一次随机，否则预览内容和真正生成内容会不一致。

## 记录 87｜移动、旋转和生成都必须经过同一个碰撞函数

当前方块保存种类、横坐标、纵坐标和旋转编号。判断碰撞时，先根据这四项换算出它实际占用的四个棋盘格，再逐格检查：

- 列小于 0 或大于等于 10，发生左右越界；
- 行大于等于 22，发生底部越界；
- 行在棋盘内且对应位置已有方块，发生堆叠碰撞。

行小于 0 时暂时不算碰撞，因为方块可能仍有一部分位于顶部之外。

左右移动、向下移动、旋转、暂存换回和新方块生成都调用同一个 `_tetris_collides()`。只有目标状态不碰撞，才真正修改当前方块。

新方块从 `x = 3, y = 0` 生成。如果刚生成就与已有堆叠重合，说明顶部已经没有容纳空间，这时直接结束游戏。

共用碰撞函数避免出现“方向键认为这里能放，旋转逻辑却认为不能放”的规则分叉。

## 记录 88｜按住方向键时，不能每帧都横移一格

单次按下左右键时移动一格没有问题。但玩家为了快速移动方块会按住方向键，如果每个 60 FPS 更新帧都移动一次，方块几乎瞬间撞到墙边。

我给每个横向按键保存独立重复计数：

```python
if key_is_held:
    repeat[key] += 1

    if repeat[key] > 10 and repeat[key] % 3 == 0:
        move_horizontal()
else:
    repeat[key] = 0
```

第一次按键仍由键盘事件立即移动一格；持续按住超过 10 帧后，才每 3 帧重复移动。

这样短按可以精确调整一格，长按又能快速横移。`A/D` 和左右方向键各自使用相同规则，松开后立即清零计数，下一次按下重新从单步开始。

## 记录 89｜靠墙旋转失败后，尝试把方块向旁边让开

只在原地测试旋转时，方块贴近左右墙就经常无法转向。旋转后的形状虽然有空间，但其中一格暂时越过边界，整个操作就被拒绝。

我没有实现一套很复杂的旋转标准，而是加入一组固定位置修正：

```python
kicks = (
    (0, 0),
    (-1, 0),
    (1, 0),
    (-2, 0),
    (2, 0),
    (0, -1),
)
```

旋转时先尝试原地；失败后依次向左一格、右一格、左两格、右两格，最后尝试向上一格。找到第一个不碰撞的位置就采用，否则保持原状态。

第一次测试只尝试左右一格，`I` 方块贴墙时仍可能没有足够空间，所以又补了左右两格。

旋转成功后清零落地计数，让玩家在方块接触堆叠时仍有一次调整机会；旋转失败则不改变坐标和旋转编号。

## 记录 90｜第一次做锁定计数，才发现“计数”不等于固定延迟

自动下落由 `tetris_fall_tick` 控制。等级 1 时，每 48 帧尝试向下一格；等级提高后，间隔每级减少 4，最低为 4。

```python
fall_interval = max(4, 48 - (level - 1) * 4)
```

我希望方块触底后不要在所有情况下立刻锁死，所以增加了 `tetris_lock_tick`。当一次向下移动失败时，用当前下落间隔增加锁定计数；累计达到 24 后，把当前方块写入固定棋盘。

```python
if not move_down():
    tetris_lock_tick += fall_interval

    if tetris_lock_tick >= 24:
        lock_piece()
```

第一次测试后我发现，这并不是严格的“触底后等待 24 帧”。等级 1 的下落间隔是 48，一次失败就会让计数直接越过 24，方块仍然立即锁定；速度提高、间隔小于 24 后，反而可能经历多次失败才锁定。

也就是说，我把下落节拍的数值误当成了经过时间。当前实现只能算一套随速度变化的锁定计数，还不是稳定的固定时长延迟。

横向移动或旋转成功仍会清零计数，避免调整后沿用之前的落地累计。这一版先保证不会悬空、重复锁定或穿过堆叠，但锁定手感仍然需要放进整体试玩中继续观察。

锁定时把四个格子写入棋盘。如果其中仍有格子位于顶部之外，说明堆叠已经超过可用区域，直接进入结束状态。

锁定完成后再检查满行，最后生成下一块。顺序不能反过来，否则新方块可能在旧方块尚未写入棋盘时错误地通过碰撞检查。

## 记录 91｜软降和硬降需要不同的风险与得分

按住下方向或 `S` 时，自动下落间隔改为 2。每成功向下一格增加 1 分，表示玩家主动加快了风险。

空格键执行硬降：循环向下移动，直到下一格发生碰撞，记录总下落距离，再立即锁定。

```python
distance = 0

while move_down():
    distance += 1

score += distance * 2
lock_piece()
```

硬降每格得到 2 分，比软降更高，因为按下以后不能再调整落点。

第一次只把方块瞬间移到底部却不立即锁定，玩家还能在落点处继续左右移动，硬降就失去了“确认放置”的含义。改成移动结束后直接锁定，输入结果才与玩家预期一致。

## 记录 92｜消行不是把满行清空，而是让上方所有行整体下移

当前方块锁定后，遍历 22 行，找出十个位置都非空的行。

如果只是把这些行改成空行，上方堆叠会悬在原地。正确处理是先移除所有满行，再在顶部补入相同数量的空行：

```python
remaining = [
    row
    for index, row in enumerate(grid)
    if index not in cleared_rows
]

grid = empty_rows(len(cleared_rows)) + remaining
```

分数按一次同时消除的行数计算：

```text
1 行   100 × 当前等级
2 行   300 × 当前等级
3 行   500 × 当前等级
4 行   800 × 当前等级
```

累计每消除 10 行提升一级，等级变化同时缩短自动下落间隔。

每条被消除的行保留 18 帧亮色闪光，锁定方块则在各格产生少量粒子。规则已经先完成下移，闪光只记录刚才被消除的原行位置。

## 记录 93｜NEXT 和 HOLD 不能只是界面上的两张卡片

`NEXT` 保存下一种方块。当前方块锁定后，用 `NEXT` 创建新方块，再从七袋中补充新的预览。

`HOLD` 则允许玩家按 `C` 暂存当前方块：

```text
暂存区为空：把当前方块放入 HOLD，生成 NEXT
暂存区已有方块：与当前方块交换
```

交换回来的方块重新使用默认生成坐标和初始旋转，再进行碰撞检查。

第一次实现后，如果允许连续按 `C`，玩家可以让两个方块无限互换，永远不让不想要的方块落下。我增加 `tetris_can_hold`：一枚方块从生成到锁定之间只能暂存一次。

新方块生成时恢复暂存权限；完成一次暂存后立即关闭，直到当前方块真正锁定并进入下一块。

右侧面板分别显示 `NEXT` 和 `HOLD` 卡片。两张卡片都从同一份方块形状表读取初始朝向，并根据形状实际宽高居中，不为七种方块分别写显示坐标。

## 记录 94｜落点预览解决的是“我以为会放这里”

方块堆高以后，只看当前方块的横坐标很难准确判断它最终会落在哪一层。尤其使用硬降时，一旦判断错就没有恢复机会。

我增加幽灵方块。它从当前方块的纵坐标开始，不断测试下一行是否碰撞，直到找到最后一个合法位置：

```python
ghost_y = current_y

while not collides(y=ghost_y + 1):
    ghost_y += 1
```

幽灵只绘制空心描边，不写入棋盘，也不参与碰撞。当前方块移动或旋转后，每帧重新计算落点。

这和五子棋的磁吸预览解决的是同一类问题：在真正提交操作之前，先让玩家看见程序理解的目标位置。但这里不是鼠标命中，而是预测连续下落的最终结果。

## 记录 95｜暂停必须冻结下落，而不是只盖一层文字

俄罗斯方块不像 2048，可以停下来慢慢思考。玩家离开键盘时如果没有暂停，方块会继续下落并结束游戏。

按 `P` 或点击左侧 `PAUSE` 按钮后，`tetris_paused` 切换为真。更新入口首先检查暂停状态并直接返回，因此自动下落、按住方向键重复和锁定计数都不会继续。

输入处理在暂停时也不执行移动、旋转、软降、硬降和暂存，只保留恢复、返回菜单和重新开始这些控制。

画面在棋盘区域覆盖半透明黑色遮罩并显示 `PAUSED`，左右状态栏仍然可见。恢复后继续使用暂停前的方块、位置和计时状态，而不是重新生成一块。

如果暂停只画遮罩却仍然执行更新，玩家回来时会发现棋盘已经在看不见的情况下变化，所以冻结规则和显示提示必须来自同一个状态。

## 记录 96｜开始页不能只有标题，我让背景自己演示一局

俄罗斯方块的开始页如果只放 `TETRIS` 和开始按钮，左侧会留下很大空白。静态堆几块方块又不能表现它的下落节奏。

我做了一套只属于菜单背景的预览棋盘。它使用独立的 `10×20` 数据、独立方块和固定随机种子 `425`，不会修改正式对局。

预览每 7 帧让方块下降一次，每 22 帧随机尝试横移或旋转。落地后同样写入棋盘并清除满行；堆到顶部时显示 `GAME OVER`，等待 120 帧后重新生成一局预览。

固定随机种子让每次启动看到的演示顺序一致，便于调整布局和复现问题。预览画面先绘制到 `330×380` 的独立表面，再缩小后放大，使它变得稍微柔和，不会抢过菜单标题和按钮。

正式对局和菜单演示只共用方块形状与颜色，棋盘、计时和随机状态完全分开。

## 记录 97｜俄罗斯方块接入后，桌面已经有六款可玩内容

对局界面把 `250×500` 棋盘放在中间，左侧显示 `SCORE`、`LINES`、`LEVEL` 和暂停按钮，右侧显示 `NEXT`、`HOLD` 与完整操作说明。

每个方块使用深色外框、主体颜色、顶部高光和底部阴影，避免不同颜色只是平涂矩形。游戏结束时保留棋盘背景，覆盖暗色遮罩，并让结果面板在 22 帧内回弹出现。

桌面图标使用几种不同颜色的四格方块拼成小型堆叠，替换新的 `COMING SOON` 栏位。点击后先进入带动态演示的游戏菜单。

这轮接入测试并不是一次通过。我先开始了一局俄罗斯方块，已经堆下几枚方块并产生分数，然后按 `ESC` 返回游戏菜单。菜单里正常出现了 `CONTINUE`，但点击后并没有回到刚才的棋盘，而是直接生成了一局全新的游戏：堆叠消失，分数、行数和等级全部回到初始值。

因为按钮确实显示出来了，我最初怀疑的是退出时没有保存完整棋盘。继续往下追踪后发现，问题不只是“有没有存”，而是同一个按钮使用了两个不同的状态来源：

```text
是否显示 CONTINUE
    → save_data 中的 run_active

点击 CONTINUE 后读取什么
    → pending_run_states 中的 tetris
```

`pending_run_states` 只在程序启动、读取磁盘存档时填充；开始一局游戏后，这份待恢复数据就会被清掉。同一次运行中从对局返回菜单时，`save_data` 已经足以让 `CONTINUE` 出现，待恢复数据里却没有俄罗斯方块。点击按钮最终取到的是 `None`，而开始函数把 `None` 理解为“没有旧局，需要创建新局”，所以表现出来就像继续按钮偷偷调用了重新开始。

我把修复拆成两个位置。第一处是在俄罗斯方块仍处于游玩状态时，收到 `ESC` 先立即记录当前局，再进入菜单；第二处是让 `CONTINUE` 直接读取决定它是否显示的同一份 `run_state`，不再绕到只供启动恢复使用的待处理数据。

```python
if key == ESC:
    save_current_run()
    open_tetris_menu()

continue_state = save_data["progress"]["tetris"]["run_state"]
start_tetris_game(restore_state=continue_state)
```

修好俄罗斯方块以后，我没有只验证它自己，而是回头检查其他带 `CONTINUE` 的游戏。扫雷也暴露了相近问题，但原因不同：扫雷的继续按钮本来就从 `save_data` 读取，问题出在按 `ESC` 离开前没有立即保存。自动保存可能停留在更早的时刻，造成棋盘和翻开格已经变化，`started`、计时、翻开数量与旗帜数量却还是旧值。恢复后有时看起来像重新开局，有时则是一张画面和内部计数对不上的棋盘。

扫雷不需要更换继续按钮的数据来源，只需要在离开游玩状态以前同步保存一次。这样菜单出现时，棋盘、翻开状态、旗帜、是否已经生成地雷、计时和两个计数都来自同一帧。

最后我把测试改成先保存一组明显可辨认的局面，再执行真实返回路径：俄罗斯方块使用非空棋盘、当前方块、`NEXT`、`HOLD`、七袋剩余内容、分数、行数、等级和下落计时；扫雷则使用已经生成的雷区、翻开格、旗帜、计时和计数。两边都必须经过 `ESC → MENU → CONTINUE`，恢复后的数据逐项相同，才算真正修复，而不是只让按钮看起来可用。

最终测试覆盖了这一款游戏最长的一条状态链：

- 七种方块的四种旋转都保持四个格子；
- 七袋取完前不会缺失或重复某一种方块；
- 方块不能越过左右边界、底部或已经锁定的格子；
- 靠墙旋转会依次尝试位置修正，全部失败时保持原状；
- 短按横移一格，长按经过延迟后连续移动；
- 软降和硬降分别按实际下降距离计分；
- 一次消除 1—4 行时，上方数据正确整体下移；
- 每累计 10 行提升一级，下落间隔不会低于 4；
- 同一枚方块只能暂存一次，下一块生成后恢复权限；
- 幽灵落点不会写入棋盘，也不会遮住真实方块；
