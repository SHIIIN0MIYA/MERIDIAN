# 第二十五部分：统计越来越多以后，我开始回答“整台 MERIDIAN 还剩多少没有完成”

---

## 记录 408｜玩家档案能告诉我做过什么，却不能告诉我还差什么

玩家档案已经能展示总时长、局数、胜率、最高分和成就进度。实际打开几次以后，我发现它更像一份历史记录：我能看到在贪吃蛇吃过多少食物、俄罗斯方块消过多少行，却很难判断自己对整台 MERIDIAN 的探索究竟到了哪一步。

只看成就数量也不够。某个世界可能解锁了几个容易成就，但关键挑战没有完成，档案也几乎没接触；另一个世界可能完成了主要目标，却因为成就总数不同显得进度更低。

我决定增加“跨世界完成度”，让它回答两个层次的问题：

```text
每个世界完成到什么程度？
八个世界合在一起完成到什么程度？
```

---

## 记录 409｜完成度不作为一个新数字保存，而是每次从事实重新计算

最初可以在存档里直接写：

```json
{"global_completion": 63}
```

但这个数字没有独立意义。只要后来调整权重、新增目标、修复统计或删除旧成就，保存的 63 就可能与真实数据不一致，还要编写迁移去猜它应该变成多少。

我只保存原始事实：成就、统计、档案解锁和游戏进度。打开玩家档案或检查阈值时，再根据这些事实计算完成度。

这样公式变化后结果会自动更新，不会出现“同一份存档同时保存旧百分比和新统计”的冲突。

---

## 记录 410｜每个世界由成就、关键目标和档案三部分组成

我把单世界完成度拆成：

```text
成就      40%
关键目标  35%
档案      25%
```

计算公式为：

```python
total = int(
    achievement_percent * 0.40
    + objective_percent * 0.35
    + lore_percent * 0.25
)
```

成就权重最高，因为它已经覆盖多类玩法里程碑；关键目标补足每款游戏真正重要但不一定逐项做成成就的挑战；档案让世界探索也进入长期进度。

我没有让任何一个部分单独决定 100%。只刷成就、不触碰关键目标和世界内容，不能被视为完整理解这个世界。

---

## 记录 411｜组合函数先钳制输入，再返回不可变结果

统计迁移、开发数据或未来修改都有可能暂时传入负数或超过 100 的值。组合前先把三项限制到 `0..100`，避免一个异常字段把总完成度推到范围外。

单世界结果使用不可变数据结构：

```python
@dataclass(frozen=True)
class WorldCompletion:
    achievement: int
    objectives: int
    lore: int
    total: int
```

界面拿到结果后只能显示，不能顺手修改其中一项再把它当成真实进度。计算层负责事实，绘制层只消费结果。

---

## 记录 412｜全局完成度让八个世界等权，而不是让内容多的世界占据大部分比例

各世界的成就数和目标数并不相同。如果直接把所有完成项放在一个分母里，内容最多的游戏会天然决定全局进度，五子棋和 2048 可能只占很小一角。

我先分别算出八个世界各自的总百分比，再取整数平均：

```python
global_percent = sum(world.total for world in worlds) // len(worlds)
```

这样每个入口都拥有相同权重。复杂系统可以在本世界内部拥有更多细分，但不能因为条目多就压过其他世界。

全局完成度表达的是连接是否均衡，不是项目里哪款游戏写了最多统计字段。

---

## 记录 413｜成就分母必须来自定义表，不能相信存档里有多少键

最初很容易用下面的方式计算：

```text
存档中以 tank_ 开头的成就数
÷ 存档中所有以 tank_ 开头的键数
```

但旧版本可能留下已经删除的成就 ID，损坏或手工编辑的数据也可能增加未知字段。用存档自己决定分母，会让不存在的条目抬高或扭曲完成度。

我从当前 `ACHIEVEMENTS` 定义表取得某个世界的合法 ID，只统计存档与定义的交集：

```text
合法且已解锁的数量
÷ 当前定义中的合法总数
```

未知旧字段既不加分，也不增加分母。

## 记录 414｜关键目标不能用一套模板套在八款玩法上

我没有统一成“玩一局、赢十局、得一百分”。每款游戏的规则结构不同，关键目标也必须表达它自己的成长路径。

例如五子棋包含：

```text
完成第一局
黑方获胜一次
白方获胜一次
累计胜利十局
```

2048 则使用最高方块：

```text
达到 512
达到 1024
达到 2048
```

这些条件都从已有统计读取，不额外保存“目标是否完成”。事实一旦达到阈值，目标自然成立。

## 记录 416｜坦克道具目标专门测试了七种与八种的边界

“使用全部道具”不是简单检查总使用次数。连续使用十次维修仍然只代表一种道具。

我分别读取维修、护盾、过载、地雷、EMP、穿甲、烟幕和跃迁的使用统计，只计算大于零的种类数：

```python
variety = sum(item_uses > 0 for each_item)
```

测试中七种道具都用过时，这一项目标仍然是未完成；第八种第一次使用后才完成。坦克一共有四项关键目标，因此这一刻 objectives 会增加 25 个百分点。

边界测试防止把“至少七种”或“总共使用八次”误写成设计目标。

## 记录 417｜档案部分只统计需要形成进度的世界条目

每个世界都有用于建立基本背景的常驻条目，也有带统计或成就条件的深入条目。常驻内容如果直接算作已完成，新存档会在没有任何探索时自动获得档案分数。

所以 Lore 百分比只选取 `unlock != "always"` 的世界条目，再查看它们是否出现在：

```python
save_data["lore"]["unlocked_entries"]
```

没有可计入条目时使用安全分母，不允许除零。档案进度与“条目是否读过”分开，打开页面但没有形成对应解锁事实，不能自动算作完成。

---

## 记录 418｜全新存档和旧存档都必须从 0 安全开始

完成度是后来加入的，旧存档不一定有完整的统计子字段、Lore 列表或坦克数据。计算函数全部使用带默认值的读取，不要求先运行一次迁移才能打开玩家档案。

我用空数据验证：

```text
八个世界都能返回 0 / 0 / 0 / 0
全局结果为 0
没有 KeyError
没有除零
没有为了计算而写入存档
```

只读计算很重要。玩家只是打开完成度页面，不应该因此悄悄改变任何进度。

## 记录 419｜玩家档案增加第三个标签，而不是另做一个桌面应用

完成度本质上仍是玩家档案的一部分。我在原来的成就和统计旁增加：

```text
ACHIEVEMENTS
STATISTICS
COMPLETION
```

键盘左右键在三个标签间循环，鼠标点击也重置各自滚动位置。返回按钮继续位于同一层级。

这样玩家查看“完成了什么”“积累了什么”“还差什么”时不需要在桌面多个应用之间来回切换。

## 记录 420｜全局进度条下面放八张世界卡片

完成度页面顶部显示全局百分比和一条横向进度条。下方按四列两行放置八张世界卡片。

每张卡片包含：

```text
世界名称与总完成度
ACHIEVEMENTS 百分比
OBJECTIVES 百分比
LORE 百分比
```

我没有只显示一个总数，因为 60% 可能来自完全不同的情况。玩家需要看出自己是缺少挑战、成就还是档案，而不是面对一个没有解释的分数。

标题继续使用安全宽度适配，中文名称变长时不会把百分比挤出卡片。

## 记录 421｜跨世界进度到达四个阈值时，连接之核才出现新记录

全局完成度不只是玩家档案里的统计。我设置四个共鸣阈值：

```text
25%
50%
75%
100%
```

每次统计发生变化后重新计算全局完成度。达到阈值且对应条目尚未解锁时，把 `resonance_25`、`resonance_50`、`resonance_75` 或 `resonance_100` 写入档案解锁列表。

这里只保存“某个共鸣条目已经解锁”，不保存完成度本身。即使以后百分比公式调整，已经见证过的阶段性记录也不会消失。

## 记录 422｜共鸣提示复用成就通知队列，但不伪装成普通成就

项目已经有成熟的右上角通知动画。如果为四条共鸣记录另写一套队列、叠放和生命周期，功能相同却会增加新的状态。

我把解锁条目的中英文标题放入已有通知队列，复用显示节奏。通知内容来自档案标题，不给它虚构一个成就 ID，也不增加成就计数。

这让玩家在达到阈值时立即知道发生了变化，同时真正的正文仍然留在世界档案中阅读。

---

## 记录 423｜开发者测试不能污染真实完成度和共鸣解锁

开发模式会快速修改统计、解锁内容或跳转状态。如果这些操作照常触发完成度写入，测试一次页面就可能永久解锁共鸣档案。

我让 `_record_stat()` 和 `_unlock_completion_lore()` 在 `dev_mode` 下不写入真实进度。开发者仍然可以构造界面状态查看 25%、50% 或 100% 外观，但退出后存档不会把它当成玩家达成。

展示测试和进度获得必须分开，否则内部工具会成为最容易误触的作弊入口。

## 记录 424｜四篇共鸣记录讲的是世界之间开始互相回应

四个阈值没有简单写成“恭喜完成 25%”。它们分别记录连接之核观察到的变化：

```text
25%｜初次共鸣
  棋境、代码深渊与星穹壁垒出现同一节拍

50%｜交汇航路
  数灵海、雷原与筑天塔开始回应同一坐标

75%｜又一信号
  战火长空与钢铁斗场暴露新的共振频率

100%｜子午共鸣
  所有已知世界达到平衡，持器者补完整条回路
```

完成度因此不只是平台外的收集数字，而是连接之核逐步理解诸界的过程。

## 记录 425｜100% 的桌面变化必须克制，而且不能隐藏任何功能

达到 100% 后，我给桌面增加一圈共振边框。它只改变外围装饰，不移动图标、不改变点击区域，也不弹出持续遮挡操作的庆祝页面。

完整动画模式可以让边框轻微脉动；关闭动画时显示静态版本，不能因为玩家关闭动画就看不到完成标记。

我希望它像设备终于稳定后的状态，而不是一个打断使用的通关烟花。MERIDIAN 仍然是一台可以继续进入每个世界的设备。

## 记录 426｜完成后我留下了一个没有掩饰的数据断点

重新沿着档案数据检查时，我发现普通世界条目与完成度之间仍有一处没有完全接上：档案阅读器为了让世界观随时可读，会直接放行所有非 `completion:` 条目；但 Lore 完成度只统计 `unlocked_entries` 中的非 `always` 条目。

当前阅读普通条目时只会写入 `read_entries`，不会自动把它加入 `unlocked_entries`。因此一份新存档可能已经读过深入档案，卡片上的 Lore 百分比却仍然是 0。

这不是推测出来的玩法问题，而是当前两条数据链的真实差异：

```text
可阅读状态  → _is_lore_unlocked()
完成度计数  → lore.unlocked_entries
阅读记录    → lore.read_entries
```

这一轮我没有假装它已经解决。跨世界完成度的成就、关键目标、阈值与界面已经形成闭环，但普通档案究竟应该按“解锁”还是按“已读”计入，仍需要统一规则。它成为这个系统留下的明确技术债。

---

## 记录 427｜后续修缮把“可读、已读、已达成”重新接成一条明确的数据链

这处断点后来没有用“打开即完成”来掩盖。普通世界正文仍然可以随时阅读，打开后只写入 `read_entries`；带 `stat:` 或 `achievement:` 条件的条目，只有条件真正满足时才进入 `unlocked_entries` 并获得 Lore 完成度信用。四篇 `completion:` 共鸣档案则继续由 25%、50%、75% 和 100% 的全局阈值控制，未解锁时标题显示为 `???`。

统一条件求值支持统计、成就、常驻和完成度四类条件。五子棋的 `wins` 聚合黑白双方胜场，无法识别或格式非法的条件安全返回未满足。启动时先记录本次 launch，再根据旧存档已有统计和成就静默回填；运行中每次统计或成就变化后重新同步。写入保持单调和幂等，不删除旧存档中的未知条目 ID，开发模式也不会把测试结果持久化。

鼠标和键盘随后改为调用同一个阅读门禁，避免不同输入路径得出不同权限结果。这样三条数据链终于各自承担单一职责：

```text
普通正文可读性  → 阅读器展示规则
是否已经读过    → lore.read_entries
是否满足完成条件 → lore.unlocked_entries
```

在所有成就、关键目标和条件 Lore 都完成后，每个世界与全局完成度都可以达到 100%，最终共鸣条目和桌面外观也有了正常可达的数据路径。记录 426 保留了问题被发现时的真实状态，而这条记录只追加后来完成的修缮，不倒写此前的开发历史。
