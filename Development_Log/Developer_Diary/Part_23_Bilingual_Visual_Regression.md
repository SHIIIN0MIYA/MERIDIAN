# 第二十三部分：中英文都能运行以后，我开始测试“画面有没有悄悄坏掉”

---

## 记录 369｜逻辑测试通过了，中文标题仍然可能挤出按钮

稳定版本完成以后，我继续检查平台界面。现在很多规则已经有自动测试，但文字宽度、按钮对齐、标签遮挡和像素边缘仍然主要靠我逐页打开确认。

这个问题在中英文切换后尤其明显。同一个按钮，英文可能是一行短词，中文会使用不同字形和字号；某次修改只动了公共字体函数，却可能让桌面、设置、档案和坦克结算同时发生细小位移。

这些页面仍然能正常点击，状态也完全正确，所以普通测试不会失败。玩家看到的却可能是：标题被裁掉、右侧信息越界、两行文字重叠，或者像素字体落在半像素缩放后的模糊位置。

我决定为关键页面建立视觉回归，而不是继续依靠“我应该已经看过了”。

---

## 记录 370｜视觉测试不是截一张随机运行中的画面

最直接的方案是启动游戏后截图，再和上一次截图比较。但实际运行画面里包含时间、随机粒子、动画帧、随机道具和存档进度。即使代码没有变化，两次图片也可能不同。

我先把目标改成“构造一个确定场景”：

```text
同一分辨率
同一语言
同一随机种子
同一动画时刻
同一存档内容
同一局内状态
```

视觉回归只有在输入完全相同时才有意义。否则图片差异告诉我的只是随机数变了，而不是界面退化了。

---

## 记录 371｜首批场景选择了六个系统页面和六个坦克页面

我没有一次覆盖所有游戏的每个状态，而是先选最容易暴露双语和新布局问题的十二个页面：

```text
desktop_page_1
desktop_page_2
system_settings
profile_statistics
achievement_wall
lore_list

tank_menu
tank_controls
tank_playing
tank_paused
tank_sudden_death
tank_end
```

每个场景都生成英文和简体中文两份，因此基线一共是 24 张图片。

这个范围同时覆盖桌面图标、多标签页面、密集文字列表、操作说明、HUD、暂停遮罩、骤死提示和双人结算。它不能证明所有画面完美，但能守住当前最容易被公共改动波及的区域。

---

## 记录 372｜渲染环境固定为 1280×720，并使用无窗口视频与音频驱动

界面本来就是按 1280×720 逻辑分辨率设计的，我让视觉场景始终使用这一尺寸。测试环境启用 dummy 视频和音频驱动，不要求真实窗口、声卡或人工操作。

这样在不同机器上运行时，不会因为窗口管理器位置或音频设备缺失而失败。

中文仍然使用项目内置的像素字体，而不是让系统临时选择替代字体。否则同一段文字会因为机器安装字体不同而改变宽度，基线失去可重复性。

---

## 记录 373｜时钟、电量、粒子和动画都要冻结

我为场景工厂设置固定输入：

```python
random.seed(330)
game.anim_tick = 120
game.transition_active = False
game.desktop_particles.clear()
game.screen_shake_enabled = False
game._get_desktop_time_text = lambda: "12:34"
game._get_battery_text = lambda: "BAT 88%"
```

随机种子让装饰与战斗对象可复现，固定动画计数避免同一按钮每次处于不同呼吸阶段。转场、桌面粒子和震屏被关闭，因为这些效果会让当前页面在同一状态下仍产生大量像素差异。

时钟和电量也不能使用真实值。否则测试每过一分钟就会有一组必然变化的像素。

---

## 记录 374｜第一次把随机数和时间做成全局测试夹具，结果污染了其他测试

初版为了省事，我写了自动生效的夹具，在每个测试开始前统一冻结随机数与时间。视觉测试稳定了，但不属于视觉范围的规则测试也被迫共享同一环境。

有些测试本来需要自己控制随机序列，有些只想验证真实的状态初始化。全局夹具让它们产生了与测试目标无关的耦合，单独运行与整套运行可能得到不同结果。

我删除全局冻结，把所有视觉专用设置移进 `build_scene()`。只有显式构造视觉场景时才固定随机、时钟和动画，其他测试继续拥有自己的环境。

视觉稳定不能以整套测试失去隔离为代价。

---

## 记录 375｜每个视觉场景都必须使用隔离存档

如果场景工厂读取真实存档，玩家已经解锁的成就、语言、统计和档案会改变截图；更危险的是，创建 `Game()` 时可能触发默认保存或数据迁移，测试反过来修改正在使用的存档。

我让视觉测试为每个运行创建临时目录，并通过 `MERIDIAN_SAVE_PATH` 指向其中的 `save.json`。退出时恢复原环境变量并删除临时内容。

这样场景看到的进度完全由测试设置，视觉验证不会读取或覆盖真实玩家数据。

---

## 记录 376｜临时文件最初放在仓库附近，运行一次测试就可能改变 Git 状态

最初只想到“不要用真实存档”，临时路径仍然靠近项目目录。测试中途失败或清理遗漏时，仓库会多出保存文件，随后发布检查又报告工作区不干净。

我改用系统提供的唯一临时目录，并确保无论生成成功还是抛出异常都执行清理。测试产物与仓库内容彻底分开，基线图片只有在明确更新时才写入受版本管理的目录。

临时状态如果会进入 Git 视野，就不是真正的测试隔离。

---

## 记录 377｜场景构造和画面提取分成两步

我把接口拆成：

```python
game = build_scene(name, language)
surface = render_scene(name, language)
```

`build_scene()` 负责建立精确状态，测试可以继续检查页面字段；`render_scene()` 调用一次绘制并返回图像。

返回时必须使用：

```python
return game.screen.copy()
```

如果直接返回 `game.screen`，后续绘制或清理会继续修改同一个 Surface，已经取得的“截图”也会跟着变。复制后的画面与游戏屏幕脱离，比较器拿到的才是那个时刻的真实快照。

---

## 记录 378｜坦克战斗画面不能依赖默认开局，我手动固定所有可见状态

坦克页面包含的变量最多。只进入 `TANK_PLAYING` 还不够，默认出生点、剩余时间和道具都会让画面信息过少，也无法覆盖 HUD 的极端情况。

我固定了一局进行到 108 秒的对战：

```text
剩余 72 秒
红 2 : 1 蓝
红方 2 HP，持有穿甲
蓝方 1 HP，持有烟幕
场上保留一发穿甲炮弹和一片烟幕
```

暂停、骤死和结束页面都从这份固定状态继续修改。结算场景还设置双方独立射击、命中和道具使用数据，确保双语统计卡真正被绘制出来。

---

## 记录 379｜烟幕第一次写成固定过期时间，画面里却总是看不到它

我最初给测试烟幕写了一个绝对过期值：

```python
expires_at_ms = 90000
```

但固定比赛的 `elapsed_ms` 已经是 108000。对引擎来说，这片烟幕早在十八秒前就过期了，场景虽然创建成功，绘制时却不会出现。

我改成相对当前规则时间：

```python
expires_at_ms = engine.elapsed_ms + 6000
```

这次问题提醒我，确定性不等于把数字写死。凡是有时间关系的状态，必须保持“当前时间与截止时间”的语义，而不是随便挑两个固定常量。

---

## 记录 380｜基线图片是经过确认的参考，不是测试自己即时生成的答案

如果测试开始时先用当前代码生成一张“期望图”，再用当前代码生成实际图，两张当然永远一致，无法发现回归。

我把 24 张经过人工查看的 PNG 保存为基线：

```text
tests/visual_baselines/en/
tests/visual_baselines/zh_hans/
```

普通测试只读取它们。只有我明确决定某次视觉变化正确时，才重新生成并审查基线。

因此基线不是“最新画面”，而是“最后一次被接受的画面”。

---

## 记录 381｜比较器按像素统计变化比例，而不是只返回图片相等或不等

完全逐字节相等对像素界面很有价值，但有些渲染边缘或受控抗锯齿可能产生极少差异。比较器会计算：

```text
changed_pixels
total_pixels
changed_ratio = changed_pixels / total_pixels
```

默认允许比例设为 `0.0005`，也就是万分之五。超过阈值才判定失败。

阈值不能大到遮住真实位移。一个按钮整体移动几像素会改变成片区域，远远超过微小渲染噪声；少量孤立像素则可以通过比例看出规模。

---

## 记录 382｜尺寸不同必须立即失败，不能先缩放再比较

比较器先检查两张图片尺寸。只要宽高不同就直接报告错误。

我没有把实际图缩放到基线大小，因为缩放会掩盖最重要的布局回归：逻辑分辨率被改了、截图区域裁错了，或者某个页面意外生成了不同尺寸 Surface。

视觉测试要验证的是原始输出，而不是经过修补后看起来相近的图片。

---

## 记录 383｜失败时生成洋红色差异图，避免只看到一个百分比

只有“变化了 2.4%”仍然很难定位原因。我让比较器在失败时输出差异图：相同区域压暗，发生变化的像素用洋红色突出。

这样打开图片后能直接分辨：

```text
整块标题移动
一行中文超出边界
按钮宽度改变
HUD 右侧锚点偏移
整个页面颜色被改动
```

数值告诉我变化有多大，差异图告诉我变化发生在哪里。二者结合才足以支持修复。

---

## 记录 384｜更新基线必须显式输入 `--yes`

基线工具会覆盖 24 张参考图片。如果它默认直接执行，开发者看到测试失败时可能顺手运行一次，把错误画面也全部批准掉。

我给命令增加确认门槛：

```text
python tools/update_visual_baselines.py
  只显示目标路径并拒绝覆盖

python tools/update_visual_baselines.py --yes
  明确确认后才写入全部基线
```

这个参数不能代替人工检查，但至少让“修复代码”和“接受新外观”成为两个不同动作。

---

## 记录 385｜基线生成器也曾碰到真实存档，我把隔离放进工具本身

视觉测试已经使用临时存档，但第一次写基线更新工具时，我只复用了渲染函数，没有在工具入口建立同样的存档环境。

这意味着测试是安全的，手动更新基线却仍可能读取或写入真实进度。它是一个很隐蔽的不一致：两个入口做相同渲染，却只有一个遵守隔离规则。

我把临时存档上下文移到更新工具内部。无论从测试调用还是命令行运行，原 `MERIDIAN_SAVE_PATH` 都会在结束时恢复；中途失败也会清理临时目录。

工具是否安全不能依赖调用者恰好记得先设置环境。

---

## 记录 386｜自动图片比较之后，我仍保留一份双语人工检查清单

像素比较能发现“和上次不同”，却不能判断上次本身是否设计合理，也不能理解翻译语义。我补了一份人工检查清单，逐页查看：

```text
是否使用正确的中英文字体
标题和按钮是否在安全边界内
左右锚定信息是否稳定
标签、正文和返回提示是否重叠
像素缩放是否保持整数倍
中英文是否表达同一操作
差异图是否来自预期修改
```

这套系统最终解决的不是“自动给界面打分”，而是让我能够在改公共 UI、字体或本地化以后，迅速知道哪一页发生了变化，再决定它是正确更新还是回归。

从这里开始，中文界面不再只是能切换出来；它和英文一样拥有可重复、可对照的画面状态。
