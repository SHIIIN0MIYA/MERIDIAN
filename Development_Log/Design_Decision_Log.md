# MERIDIAN 设计决策档案

## DD-01：从五子棋原型转向合集

- **背景**：五子棋是项目起点。
- **决定**：不把它停留为单一小游戏，而是建立多个小游戏的选择入口。
- **原因**：开发者希望把后续作品放入同一环境；最初目标是“方便选择”，尚未形成完整平台。
- **影响**：产生了菜单、入口与统一容器的需求，也为后来的桌面系统埋下方向。

## DD-02：从选择界面升级为 HAO'S GAME DECK

- **背景**：桌面初步完成后，简单集合仍不像一台真实设备。
- **决定**：以 HAO'S GAME DECK 命名并塑造成掌机平台，桌面预留 12 个 `COMING SOON` 软件栏。
- **原因**：预留位既表明扩展性，也让“尚未完成的内容”成为平台成长状态的一部分，而不是杂乱菜单。
- **影响**：后续不再只讨论游戏本身，而要考虑开机、认证、退出、桌面和系统设置。

## DD-03：停止以游戏数量为唯一目标

- **背景**：五款扩展游戏依次完成后，项目已有内容规模。
- **决定**：暂停盲目新增玩法，优先补齐体验层。
- **原因**：数量并不能自动产生统一感；缺失的设备壳层、声音和进入/退出节奏会让合集显得拼接。
- **影响**：开机/密码/结束流程、转场和音频系统成为后续主线。

## DD-04：用共同主旋律，而非彼此无关的配乐

- **背景**：不同游戏需要独立氛围，但平台也要有可辨认身份。
- **决定**：确定一条主旋律，并为每个游戏使用变奏 BGM。
- **原因**：保留玩法差异，同时让切换游戏仍像在同一台设备内。
- **影响**：Tank Duel 设计也继承该规则；后期进一步把音乐和音效纳入主音量混音。

## DD-05：从单文件到模块化组合

- **背景**：单文件不断堆入游戏、UI、状态和系统逻辑，维护成本变高。
- **决定**：拆分模块；v3.0 进一步把 `Game.__init__` 拆为多个 Mixin 初始化单元，以状态分发表驱动界面。
- **原因**：新增游戏和系统不应持续放大中心文件的耦合。
- **影响**：当前形成 shell、街机公共层、各游戏 Mixin、持久化、音频、本地化和系统模块；新游戏可通过注册 API 接入。

## DD-06：从成就数据到成就墙与玩家档案

- **背景**：成就本身只能记录完成条件，难以让玩家感到跨游戏积累。
- **决定**：先有成就系统，再以成就墙呈现，再以玩家档案承接统计和进度。
- **原因**：鼓励通关需要可见的、可回顾的长期目标，不只是一次弹窗。
- **影响**：后期世界档案和跨世界完成度也能复用这一进度语义。

## DD-07：正式更名为 MERIDIAN，并引入世界观

- **背景**：掌机外壳、多个游戏和玩家进度已形成平台，但仍缺乏解释“它们为何共存”的框架。
- **决定**：正式更名 MERIDIAN，将每款游戏定义为通向独立世界的模块；加入序章、风味文字、Lore 和双语文本。
- **原因**：世界观不是附加宣传，而是把原本并列的小游戏转化为同一设备上的“诸界”。
- **影响**：世界档案、解锁条件、游戏注册接口和后续 Tank Duel 的世界条目都有共同归宿。

## DD-08：Tank Duel 采用纯规则引擎与表现层分离

- **背景**：本地双人对战引入同时输入、碰撞、公平性、随机重生和恢复等复杂规则。
- **决定**：`tank_engine.py` 不依赖 Pygame，负责固定时间步规则；`tank_battle.py` 负责输入、渲染、声音和界面。
- **原因**：把规则从帧率和绘制中隔离，才能可靠测试顺序无关碰撞、对称性和快照恢复。
- **影响**：Tank Duel 的错误可以局部定位，确定性视觉测试也能围绕稳定状态构建。
