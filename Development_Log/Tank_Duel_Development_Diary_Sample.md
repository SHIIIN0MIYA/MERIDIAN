## 2026-07-10 12:17｜先把坦克对决限制住

今天决定给 MERIDIAN 增加一款本地双人游戏：**Tank Duel / 坦克对决**。

第一反应其实是可以做很多东西：单人 AI、多地图、地图编辑器、联网对战。但把这些都放进首版，最可能的结果是规则、界面和平台接入一起失控。所以我先明确了首版不做什么：不做 AI、不做联网、不做地图编辑器，也不先抽象一个“通用竞技游戏框架”。

首版只做一张左右镜像地图，两个人共用一块键盘：

- 红方用 `WASD` 移动，`F` 使用道具；
- 蓝方用方向键移动，`Enter` 使用道具；
- 双方自动射击，把注意力集中在走位、掩体和道具争夺上；
- 每方 3 HP，标准对局 3 分钟；
- 时间结束平分时进入骤死，下一次非同时击毁决定胜负。

这里有一个我比较在意的问题：两个人同时操作时，不能让规则因为“代码先更新红方还是先更新蓝方”而偏向某一边。只要出现这种偏差，本地双人对战就会显得不公平，而且玩家很难说清楚为什么。

所以架构上没有直接把所有规则塞进 Pygame 页面。我把它拆成两层：

```text
tank_engine.py
    只处理移动、碰撞、计时、射击、道具、重生和胜负
    不导入 Pygame

tank_battle.py
    处理键盘输入、菜单、绘制、音效、转场和 MERIDIAN 系统接入
```

表现层把按键转换成 `PlayerCommand`，再调用：

```python
events = engine.update(dt_ms, commands)
```

引擎返回的是 `shot`、`tank_hit`、`pickup`、`tank_destroyed` 这样的领域事件。表现层只根据事件播放声音、粒子和震屏。这样做的好处是，我以后测试“同时命中”时不需要真的打开窗口，也不会让帧率决定规则结果。

今天另外先把测试存档隔离了。MERIDIAN 有真实持久化数据，如果测试直接使用默认存档路径，跑一次测试就可能污染玩家自己的进度。这个问题和坦克玩法本身无关，但不先处理，后面测试中断恢复时会非常危险。

下一步：先做移动引擎，暂时不画坦克。

## 2026-07-10 18:57｜移动看起来简单，实际先碰到输入优先级

先完成了纯规则移动。

地图采用 `24 × 12` 格，左右镜像。除了出生位置对称，我还需要保证所有可行走区域连通，不能出现一方能进入、另一方没有对应路线的区域。

移动支持八个方向，但斜向不能比直线快。最后使用归一化向量：

```python
length = math.hypot(move_x, move_y)
move_x /= length
move_y /= length
```

这样同时按右和下时，速度仍然与只按右相同。

更麻烦的是相反按键。例如玩家先按住 `A`，再按住 `D`。我不希望两个方向相互抵消后坦克停住，因为实际操作时玩家通常是在表达“改向”。因此记录每个键的按下顺序，让后按下的方向生效；释放后按键后，如果之前的键还按着，再恢复之前的方向。

```text
按住 A       → 向左
继续按住 D   → 向右（后按优先）
释放 D       → 恢复向左
```

这一点后来有独立测试，不只验证红方，也验证红蓝双方可以同时斜向移动。

引擎内部使用固定时间步累积，而不是直接把每次渲染的 `dt` 当成规则时间。原因是不同电脑的帧率不能改变移动距离、射速和碰撞结果。测试里还专门覆盖了“不完整帧时间如何累计到下一步”。

完成移动后，我暂时没有急着画 UI。当前阶段最重要的是确认：镜像地图、八向速度、碰撞和双方同时移动都能在没有渲染的情况下重复得到同样结果。

## 2026-07-10 19:05｜第一次战斗规则跑通，但三发炮弹暴露了顺序 Bug

加入了自动射击和基础伤害：

- 常规射击间隔 650ms；
- 每名玩家同时最多保留 2 发炮弹；
- 炮弹可打碎砖墙，钢墙只阻挡不损坏，草丛不阻挡；
- 坦克受击扣 1 HP；
- 同一时间步内的伤害先收集，再统一结算，避免先后顺序偏向某一玩家。

两发敌对炮弹相撞时同时消失，这个用例一开始是通过的。但把测试扩展到三发炮弹后出了问题：两发红方炮弹和一发蓝方炮弹挤在同一个碰撞范围内，结果会随着 `bullets` 列表顺序变化。

第一次实现大概是这种思路：

```python
for first in bullets:
    for second in bullets:
        if clash(first, second):
            remove(first, second)
            break
```

问题在于，循环过程中一边发现碰撞一边删除，相当于“先遇到谁就先结算谁”。第三发炮弹是否还能参与判断，已经被前一次循环改变了。

我为三发炮弹生成了所有排列顺序，要求每种排列都得到相同结果。修复时不再立即删除，而是先收集本时间步内所有参与碰撞的下标：

```python
participants = set()

for first_index, first in enumerate(bullets):
    for second_index in range(first_index + 1, len(bullets)):
        second = bullets[second_index]
        if first.owner != second.owner and clash(first, second):
            participants.update((first_index, second_index))

removed.update(participants)
```

同一方的炮弹不能互相抵消，也补了单独测试。

这次问题让我确认，实时对战里“遍历列表”不只是实现细节，它可能直接变成隐藏规则。凡是声称“同时发生”的事情，都应该先收集、后统一结算。

## 2026-07-10 19:20｜先做四种道具，不让系统一下子膨胀

首轮道具只做了四种：维修包、护盾、过载和地雷。

道具每隔 12–18 秒尝试在地图中央的镜像争夺点刷新，场上最多存在一个未拾取道具。每名玩家也只有一个道具槽，已有道具时不能用新道具覆盖。

这个限制是刻意的。如果可以囤积多个道具，玩家需要额外的切换 UI；如果刷新在各自出生点，道具又会变成免费资源。放在中央区域，才能逼双方离开安全路线。

四种道具的设计目的不同：

- 维修包恢复 1 HP，满血使用时不消耗；
- 护盾抵挡下一次伤害，最长维持 15 秒；
- 过载临时提高移动和射击速度；
- 地雷留在当前位置，每名玩家最多放一枚，死亡时清除自己布置的地雷。

这一阶段还把正常计时结束、平分骤死、暂停冻结全部规则时间加了进去。暂停不只是停止画面：比赛计时、射击冷却、道具刷新、增益持续时间都必须一起停止。

第一天结束时，玩法规则已经能跑，但还没有证明它“好玩”，也没有证明它能安全地保存和恢复。

## 2026-07-11 14:20｜试玩后第一次调平衡：过载太强，重生也有顺序偏差

继续测试道具和重生时，发现两个设计问题。

第一个是过载。最初移动加成用了 `1.5`，实际效果过于明显：拿到过载的一方既能更容易追击，又能快速脱离，加上射击提速，优势叠得太多。最后把移动倍率降到 `1.25`，持续 6 秒；射击间隔从 650ms 缩短到 430ms。这样仍能感受到强化，但不会让普通走位失去意义。

第二个问题比数值更严重：双方同时被击毁时，旧的重生逻辑按玩家顺序逐个选点。先处理的玩家先拿到最优点，后处理的玩家只能避开已经占用的位置。代码即使每次都稳定，也不代表公平，因为稳定地优待红方仍然是不公平。

我把重生改成联合分配：枚举候选点的组合，同时评价两名玩家的位置。目标不是单纯让总分最高，而是先最大化两者中较差的那个分数，再比较总分。

```text
重生方案评分 = (
    min(红方安全分, 蓝方安全分),
    红方安全分 + 蓝方安全分
)
```

安全分会考虑敌方距离、敌方视线、可逃离方向、墙体、地雷和当前炮弹威胁。选中位置后还有 1500ms 受击保护和 400ms 射击锁定，避免刚出现就立即交换击毁。

后续测试覆盖了三件事：联合分配优先保护较差的一方；交换红蓝标签后结果仍然对称；多个同分方案在不同随机种子下不会固定偏向某一边。

今天的结论是：平衡问题不全是参数问题。像出生点分配这种算法，如果边界设计错了，调多少 HP 和速度都补不回来。

## 2026-07-11 14:28｜中断恢复不是“把坐标存下来”

开始接入 MERIDIAN 的存档系统，Schema 从 v4 升到 v5，为 Tank Duel 增加统计和运行状态。

一局对战可能进行到一半退出，所以快照需要保存：

- 地图砖墙损坏状态；
- 双方位置、朝向、HP、持有道具和各种计时；
- 炮弹、地雷和场上拾取物；
- 比分、剩余时间、阶段和骤死状态；
- 下次道具刷新时间；
- 随机数生成器状态。

随机状态也要保存，否则同一个存档恢复后，之后的道具刷新和重生选择会走向另一条时间线。为确认恢复是确定的，我让相同快照在相同命令流下产生相同事件和最终状态。

我没有保存 Pygame 对象，也没有保存玩家当时按住了哪些实体键。恢复后输入必须回到中立状态，否则玩家松开键盘再进入游戏，坦克仍可能自动移动。炮塔朝向可以保存，但实时按键不能当作持久状态。

## 2026-07-11 14:32｜快照校验漏了“合法上界”和零朝向

给快照加入校验后又发现两个边界问题。

地图宽 24 格时，合法横坐标应满足 `0 <= x < 24`，但通用数值校验允许了 `x == 24`。这个值看起来没有超过最大值，实际上已经在地图外。坦克、地雷和拾取物的横纵坐标都需要使用“排他上界”。

另一个问题是朝向 `(0, 0)`。范围检查只验证每个分量在 `-1..1`，所以零向量也能通过。自动射击时会用朝向长度做除数，零向量最终可能导致除零。

修复后增加了专用坐标校验：

```python
def _snapshot_coordinate(data, key, limit):
    value = _snapshot_number(data, key, 0, limit)
    if value >= limit:
        raise TankSnapshotError(f"{key} must be inside the arena")
    return value
```

同时拒绝 `(0, 0)` 朝向，并为坦克、地雷、拾取物的每个坐标边界做参数化测试。

非法快照不能把整个 MERIDIAN 存档一起清空。恢复失败时只丢弃 Tank Duel 的中断对局，保留累计统计、成就和其他游戏进度，并在菜单显示可本地化提示。

## 2026-07-11 14:41｜终于开始画，但表现层只消费事件

规则稳定后开始做 Pygame 表现层。

加入了四个状态：

```text
TANK_MENU
TANK_CONTROLS
TANK_PLAYING
TANK_END
```

菜单、操作说明、对局 HUD、暂停层和结算页先完成最小版本。坦克、墙、子弹和拾取物全部用硬边像素块绘制，不做平滑缩放。红蓝双方除了颜色外，炮塔纹理也不同，避免完全依赖颜色区分。

表现层不重新判断命中。它只消费引擎事件：`tank_hit` 触发震屏，`tank_destroyed` 触发爆炸，`pickup` 播放拾取声音。这样不会出现画面认为命中、规则认为没命中的两套真相。

草丛的绘制顺序也有规则含义：它不阻挡移动和炮弹，但应该遮挡坦克，所以必须最后画在坦克上方。这个细节看似只是图层，实际决定掩体是否成立。

## 2026-07-11 20:29｜暂停时按 F，恢复后竟然使用了道具

今天遇到一个典型的输入边沿 Bug。

道具键不是持续状态，而是只在按下那一帧产生一次脉冲：

```python
use_item = self._tank_item_pulses[player_id]
self._tank_item_pulses[player_id] = False
```

暂停时引擎更新直接返回，但按键事件仍然把脉冲记了下来。结果是玩家暂停期间按 `F`，当时没有反应；恢复后的第一帧却自动使用了道具。

修复分两层：暂停时直接拒绝道具键；暂停更新分支也主动清空双方脉冲。随后写了两个测试：暂停期间的输入恢复后必须为 `False`；正常按键必须只影响一帧，下一帧自动回到 `False`。

这个 Bug 提醒我，暂停不能只冻结“时间”。一次性输入如果被保留下来，就会在恢复时变成延迟命令。

## 2026-07-11 20:38｜接入 MERIDIAN 后，才算是一款平台游戏

把 Tank Duel 接入桌面、状态分发、音频场景、统计和存档流程。

新增游戏不能只在桌面加一个图标。需要确认事件、更新和绘制三张分发表都有对应状态；进入、退出、暂停和结算路径都能回到正确位置；游戏时间会进入玩家档案；中断时能捕获运行状态。

接入后马上暴露了恢复流程不完整的问题。有效快照虽然已经能反序列化，但菜单没有 `CONTINUE`，玩家没有入口继续；开始新对局时也必须明确消耗旧快照，不能让它再次出现。

修复后，存在待恢复状态时，菜单显示：

```text
CONTINUE
NEW MATCH
CONTROLS
DESKTOP
```

选择继续会恢复比分、时间、损坏墙体和跟踪数据，并立即消费待恢复快照；选择新对局会丢弃旧快照并重置引擎。无效快照只显示恢复失败提示，然后允许开始新对局。

## 2026-07-12 07:50｜成就不是列十二个名字就结束了

开始加入 12 项 Tank Duel 成就，包括完成首局、第一次胜利、命中率、破坏砖墙、使用全部道具、1 HP 击毁、骤死获胜、地雷命中、护盾抵挡、过载连续击毁、落后逆转和完成 50 局。

难点不是把条件写进列表，而是保证统计不会重复、不会在恢复后丢失。

例如一局比赛中已经发射 8 发炮弹，退出后恢复，再发射 2 发，命中率成就应基于整局 10 发计算。为此，快照除了引擎状态，还要保存表现层的对局跟踪数据：双方发射数、命中数、使用道具数、最大落后分差、过载击毁数和是否进入骤死。

第一版成就加入后，很快又补了“持久化 Tank 成就跟踪”的修复。说明只保存规则状态还不够；派生进度如果参与成就判定，也必须跟随对局恢复。

最终结算还要求幂等。同一个 `match_ended` 事件不能因为页面重复更新而累计两次完成局数，所以使用 `_tank_match_stats_recorded` 保证只记录一次。

## 2026-07-12 16:26｜以为完成了，复查时才发现验收口径还不够

Tank Duel 已经可以从桌面进入、完成对局、结算并重开。我一度认为已经“完成”，但随后又专门补了一条测试：红蓝双方是否真的都能移动。

这件事有点尴尬，但也很典型。单元测试覆盖了移动数学，不代表平台输入映射一定覆盖两名玩家；页面能画出来，也不代表蓝方方向键真正进入了引擎。于是补了双方移动的验收测试，而不是用“红方能动，所以蓝方应该也能动”代替证据。

最终复查又发现几处统计语义不准确：

- 逆转成就最初只记录“是否曾经落后”，但设计要求至少落后 3 分；
- 结算页只有全局命中率，无法分别展示红蓝双方；
- 玩家档案缺少 Tank Duel 统计区；
- 砖墙事件名称与声音映射不一致；
- 护盾抵挡需要由明确的 `shield_blocked` 事件统计，不能把所有免伤都算进去。

我把布尔值 `was_behind` 改成双方各自的 `max_deficit`，只有最大落后分差达到 3 才满足逆转条件。双方射击、命中和道具使用也改为独立跟踪，结算页才能给出各自的命中率。

这里的经验是：统计字段的名字就是规则。如果名字含糊，成就条件迟早会偏离设计。

## 2026-07-12 16:42｜中文不是最后统一替换字符串

Tank Duel 已经有中文文本，但实际绘制时仍出现混用英文的问题。

结算比分最初直接写成：

```python
f"RED {red_score} : {blue_score} BLUE"
```

改成分别翻译 `RED` 和 `BLUE` 后，中文结算才完整。玩家档案里的 `MATCHES`、`ACCURACY` 也曾直接绘制英文键，后来统一在绘制前调用 `translate()`。

还出现过字体缓存生命周期问题：Pygame 字体子系统退出再初始化后，缓存里仍保留旧的 Font 句柄。测试单独运行可能没事，连续初始化/退出时就会暴露。修复方式是在 `pygame.font.quit()` 和 `pygame.quit()` 时清理字体缓存，并测试重启后能创建新的字体对象。

这不是 Tank 规则 Bug，但它是在 Tank 中文页面回归时被发现的。说明新增内容经常会把公共系统的旧假设一起带出来。

## 2026-07-12 17:03｜声音方向推翻了一部分原设想

最初设计要求 Tank Duel 延续 MERIDIAN 主旋律变奏。真正放进对局后，我觉得它听起来仍像“另一款街机游戏的变奏”，机械对抗的辨识度不够。

最后代码里为 Tank Duel 单独建立了一个不对称的七步动机，而不是继续直接复用 `THEME_MELODY`。它包含低频方波、履带噪声、错拍噪声和后段无线电短音。菜单、常规、最后一分钟、最后冲刺、骤死使用同一动机的不同速度层级：

```text
menu   0.240s / step
normal 0.180s / step
final  0.150s / step
sprint 0.125s / step
sudden 0.105s / step
```

这算是对早期统一音乐原则的一次有意识偏离：平台需要统一，但统一不应该牺牲游戏的身份。Tank Duel 仍然使用 MERIDIAN 的程序化音频系统、状态切换和混音方式，只是旋律材料独立。

同时加入 `tank_crossfire` 专属转场。开始和继续进入对局时播放 42 帧，结算前播放 46 帧。射击、炮弹相撞、砖墙、命中、爆炸、拾取、道具和骤死提示各自设置音量，避免所有效果音都以同样响度争抢注意力。

## 2026-07-12 17:44｜临近完成又把四种道具扩成八种

这是本阶段最大的一次范围变化。

最初设计只有维修、护盾、过载、地雷四种道具。玩法完成后，我又加入 EMP、穿甲弹、烟幕和跃迁器，使道具从四种扩成八种：

- EMP：让对方自动射击锁定 3 秒；
- 穿甲弹：接下来 3 发炮弹可穿过砖墙，对坦克造成双倍伤害；
- 烟幕：持续 6 秒，作为绘制层遮蔽战场信息；
- 跃迁器：从安全候选点中选择较优位置，并提供 700ms 保护。

这个改动并不只是往枚举里多写四行。每种道具都影响了规则事件、统计字段、成就“使用全部道具”、操作说明页、中文文本、拾取物图标、音效和快照格式。

为了兼容已有快照，新字段采用可选读取：旧存档没有 `piercing_shots`、`piercing` 或 `smokes` 时使用默认值，而不是直接报废整局。

烟幕还再次验证了规则层和表现层的边界。引擎只保存烟幕位置、归属和结束时间；具体画多少个半透明圆、使用什么颜色，由表现层决定。草丛继续保持最后绘制，烟幕则在坦克之后、草丛之前绘制。

操作说明页从简单四行文字扩成八张道具卡。拾取物最初只是同一个亮色方块，扩展后用不同颜色和字形区分，后来又进一步发展成独立像素图标。

这次扩展确实增加了收尾成本，但它也让中央争夺不再只有“拿到一个增益”的单一结果：不同道具改变追击、封锁、视野和脱离方式。

## 2026-07-12 17:55｜最后三次修复都不是规则，而是中文桌面标题

功能和测试基本完成后，连续三次提交都在修桌面文本：

1. 中文标签需要保持 2 倍整数像素缩放，不能因为存在副标题被压成 1 倍；
2. “坦克对决”占用标题行后，“本地双人对战”副标题与图标发生拥挤，因此中文 Tank 图标不再显示第二行副标题；
3. 为中文标题固定主标签基线，并增加冒烟测试检查实际传给渲染函数的缩放值。

这个过程很能说明“做完”和“看起来完成”不是一回事。规则引擎已经能处理同时击毁和存档恢复，但玩家首先看到的仍然是桌面上的四个汉字。如果它比其他图标小一圈或者压住图案，整款游戏就会像临时接进去的插件。

最终 HUD 也改成分别渲染红方、生命格、道具、中央计时和蓝方信息。蓝方区域使用右侧锚定，而不是依赖英文长度计算固定横坐标，这样中英文切换不会推动生命格和道具标签。

## 2026-07-13｜合并与 v3.2.0

Tank Duel 分支合并进主线，并整理为 `v3.2.0` 稳定节点。

回头看，这个版本并不是按照最初设计一次完成的。实际路径是：

```text
限制首版范围
  ↓
先做无 Pygame 规则引擎
  ↓
移动与自动射击
  ↓
发现同时碰撞的顺序偏差
  ↓
四种道具与比赛流程
  ↓
发现过载和联合重生不公平
  ↓
版本化快照与 Schema v5
  ↓
发现坐标上界、零朝向和暂停输入问题
  ↓
接入桌面、存档、统计、成就和 Lore
  ↓
复查双方输入、中文布局和统计语义
  ↓
独立机械音乐动机、专属转场
  ↓
四种道具扩为八种
  ↓
继续修桌面标题与像素缩放
```

最终留下的不是只有一款双人游戏，还有几项可以继续复用的工程经验：

1. 对战中的“同时”必须先收集再结算，不能让列表遍历顺序变成隐藏规则。
2. 公平性不仅是双方参数相同，资源和重生的分配算法也必须对称。
3. 运行状态、成就跟踪和实时输入属于不同种类的数据，不能用同一套保存策略。
4. 暂停需要冻结计时并丢弃一次性输入，不能把命令延迟到恢复后执行。
5. 本地化需要实际绘制和截图验证；字符串存在不代表页面完成。
6. 新游戏只有接入菜单、转场、音频、存档、统计、成就和世界观后，才真正属于 MERIDIAN。
